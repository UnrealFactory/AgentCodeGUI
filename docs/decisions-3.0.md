# AgentCodeGUI 3.0 — 결정 장부

라운드 R28j `DECIDE` · 2026-08-26 · `feature/3.0.0-beta` @ `57e55e6`
앞 문서: `docs/critic/final-parity-r5.md`(최종 파리티 감사 R5 — 치명 0 · 출하 차단 해제) ·
`docs/m1-report-r4.md`(성능) · `docs/m12-report-r1.md`·`-r2.md`(패키징)

이 문서는 **결정의 장부**다. 보고서가 아니다.
사용자가 내린 결정을 한 자리에 모으고, 각 결정에 **무엇을 · 왜 · 근거 수치 · 무엇이
미결로 남는가**를 붙인다. 다음 사람은 이 문서만 읽고도 "왜 이렇게 돼 있나"에 답할 수
있어야 한다.

규칙 셋을 지킨다.

1. **근거 없는 줄을 쓰지 않는다.** 모든 수치에 어느 파일의 어느 필드인지를 단다.
2. **제안과 결정을 섞지 않는다.** 사용자가 정한 것은 「결정」, 내가 계산한 합격선은
   「제안」이라고 적는다.
3. **불리한 수치를 빼지 않는다.** 이번 라운드에서 **가장 중요한 발견은 3.0에 불리한
   쪽**이다(§1.4 · §1.6-A).

## 1. 결정 ① — 성능 목표를 **비율 목표**로 재정의한다

### 1.1 왜 절대치가 불가능한가 — 두 개의 바닥값

목표를 못 지킨 게 아니라 **목표가 물리적으로 도달 불가능**이라는 것이 실측으로 확정됐다.
근거는 두 개의 바닥값이다.

**(a) 메모리 바닥값 — 빈 문서(`about:blank`)**

`bench/gpuprobe.mjs`가 살아 있는 앱의 문서를 통째로 언로드하고(`Page.navigate about:blank`)
같은 프로세스 트리를 다시 잰다. **해제 검증**이 붙어 있다 — DOM 노드·리스너가 90% 이상
사라져야 그 값을 바닥값이라 부른다(`release.verdict`).

| 측정 | 4패널 기준선 WS | **빈 문서 바닥 WS** | 앱 몫 WS | 출처 |
|---|---:|---:|---:|---|
| 3.0 (R4 크리틱 exe `682ad089` · 3.8MB) | 398.8 | **351.5** | 47.3 | `bench/results/critic-r4-gpuprobe.json` |
| 3.0 (R28j · exe `4cdf7788` · 6.3MB) | 574.2 | **515.9** | 58.3 | `bench/results/gpu-css-probe-r28j-dec-tauri.json` |
| **2.6.2 (R28j — 이번에 처음 쟀다)** | 699.5 | **643.1** | **56.4** | `bench/results/gpu-css-probe-r28j-dec-electron.json` |

> **exe 주의**: 바닥값 두 주행(3.0/2.6.2)은 **같은 세션에서 연달아** 돌렸고, 그때 3.0 팔이
> 쓴 exe는 워크트리에 이미 있던 `target/release/agentcodegui.exe`(08-24 · `4cdf7788`)다.
> §1.4의 주 게이트는 그 뒤에 **HEAD를 깨끗한 트리에 풀어 새로 구운** exe(`7b9b659c` · 6.6MB)로
> 쟀다. 두 수를 섞어 빼지 마라 — 앱 몫은 **같은 실행 안에서** 뺀 값이라 이 차이에 둔감하다.

> **유휴 WS 목표 356은 3.0의 빈 문서 바닥값(351.5)보다 4.5MB 높을 뿐이다.**
> UI를 한 글자도 안 그려야 4.5MB가 남는데 우리 UI는 47~58MB를 쓴다. 레버로 좁히는 문제가
> 아니다 — R3·R4 크리틱이 서로 다른 exe에서 세 번 같은 결론에 닿았다.

**(b) 시간 바닥값 — 웹 런타임 기동(spawn → `timeOrigin`)**

| 팔 | spawn → timeOrigin | 출처 |
|---|---:|---|
| 3.0 (`tauri-3.0.0+default`) | **199 ms** | `bench/results/boot-breakdown.json` |
| 2.6.2 (`electron-2.6.2+default`) | **199 ms** | 〃 |
| 3.0 `--single-process` | 165 ms | 〃 |

**두 앱이 같다.** 콜드 첫 창 ≤168ms는 웹 콘텐츠를 한 픽셀도 안 그려도 불가능하고,
`rootMs ≤211`의 이론 하한은 199 + 49.2(재로드 마운트) = **248ms**다.

### 1.3 ★ 바닥값을 뺀 「앱 몫」 비율 — 이번 라운드의 신규 수치

총량 비율은 두 앱이 **어쩔 수 없이 지고 가는 런타임 바닥값**을 분자·분모에 같이 담는다.
바닥값을 빼야 우리가 쓴 코드의 값이 남는다. 그래서 **2.6.2의 빈 문서 바닥값을 같은
하네스·같은 픽스처·같은 세션에서 처음 쟀다.**

| | 4패널 기준선 | − 빈 문서 바닥 | = **앱 몫** |
|---|---:|---:|---:|
| 3.0 WS | 574.2 | 515.9 | **58.3** |
| 2.6.2 WS | 699.5 | 643.1 | **56.4** |
| **앱 몫 WS 비율** | | | **1.03** |
| 3.0 Private | 335.3 | 289.9 | **45.4** |
| 2.6.2 Private | 485.2 | 399.3 | **85.9** |
| **앱 몫 Private 비율** | | | **0.53** |
| 런타임 바닥값 WS 비율(우리 성과 아님) | | | 515.9 / 643.1 = **0.80** |

3.0 쪽을 R4 크리틱 exe로 바꿔 넣으면 앱 몫 WS 47.3 → 비율 **0.84**(교차 세션이라 참고값).

> **바닥값 515.9에 붙는 주의**: 이 수에는 §1.4의 LSP 헬퍼 3프로세스(145.5MB)가 들어 있다 —
> 문서를 언로드해도 LSP 서버는 안 죽으니 당연하다. **앱 몫은 그 영향을 안 받는다**
> (기준선에도 바닥값에도 똑같이 들어 있어 뺄 때 상쇄된다). 그래서 「앱 몫」 비율은
> 이 라운드에서 가장 튼튼한 수이고, 「바닥값」 비율(0.80)은 LSP 때문에 3.0에 불리하게
> 부풀어 있다(LSP를 빼면 3.0 바닥 ≈ 370, 비율 ≈ 0.58 — R4가 잰 351.5와 같은 대역).

> **정직한 결론: WS의 승리는 거의 전부 런타임 바닥값의 차이다.**
> 우리 UI가 WS로 쓰는 몫은 2.6.2와 **같거나 조금 많다**(0.84~1.03). 같은 React 트리를
> 그대로 이식했으니 당연한 결과이기도 하다 — 3.0의 렌더러는 2.6.2 렌더러의 이식본이다
> (`docs/renderer-divergence.md`).
> **Private에서는 진짜 승점이 있다(0.53).** 그리고 시간 축의 앱 몫도 승점이다:

| | rootMs | − 런타임 기동(199ms) | = 앱 몫 | 비율 |
|---|---:|---:|---:|---:|
| 3.0 | 348 | 199 | **149 ms** | |
| 2.6.2 | 443 | 199 | **244 ms** | **0.61** |

**바닥값을 어떻게 쟀나(재현 가능):**

```bash
node bench/gpuprobe.mjs tauri    --tag=<t> --port=<n> --out=<파일>
node bench/gpuprobe.mjs electron --tag=<t> --port=<n> --out=<파일>
#  6단계: Page.navigate about:blank → DOM 노드·리스너 90%+ 감소 검증(release.verdict)
#  판정 근거: 3.0 노드 8513→6 · 리스너 672→4 / 2.6.2 노드 8476→4 · 리스너 635→0
```

`--out`/`--tag`/`--port`는 이번 라운드에 넣었다. 그전에는 파일명이 고정이라 새 주행이
기준 결과 파일(`bench/results/gpu-css-probe.json`)을 말없이 덮었다.

`src-tauri/src/ipc/lsp.rs`의 **`boot_prewarm()`** 이 부팅 때 활성 채팅의 cwd를 읽어
LSP를 미리 띄운다(M7에서 들어갔다 — R4 측정 시점에는 **없던 코드**다). 벤치 픽스처의

**그런데 2.6.2 팔에서는 안 뜬다.** 2.6.2도 같은 프리웜을 부르지만
(`src/renderer/src/App.tsx:706`) 서버가 **앱 홈에 설치돼 있어야** 뜨고
(`src/main/lsp/manager.ts:1649` → `installState('cs')` 계열), 벤치 격리 홈은 비어 있다.

> **즉 주 게이트는 지금 두 앱에서 같은 것을 재고 있지 않다.**
> 3.0 팔에만 LSP 헬퍼 **3프로세스 · WS 145.5MB · Private 105.0MB**(3회 중앙값)가 얹히고
> 2.6.2 팔은 **0개**다(`ratios-r28j-dec.json`의 `lspSplit`). 이 사실을 모르고 비율만 인용하면
> **3.0을 부당하게 나쁘게** 평가한다. 반대로 빼고만 말하면 **사용자가 실제로 부팅 직후
> 겪는 상태를 숨긴다.** 그래서 `bench/ratios.mjs`가 두 수를 **같이** 낸다
> (`lspSplit` 블록 — `procDetail`에서 `node`/`conhost`/`clangd`/roslyn 계열을 헬퍼로 분리).

### 3.3 규약 준수 — 위반 0건

`app/src/lib/i18n.ts`가 명시한 금지 규약 중 기계로 검사 가능한 것:

| 검사 | 3.0 | 2.6.2 |
|---|---:|---:|
| `t()` 인자가 2개가 아닌 콜사이트 | **0** | 0 |
| `en` 쪽에 한글이 남은 콜사이트 | 2 → **실제 0** | 2 → 실제 0 |
| ko와 en이 같은 문자열 | **0** | 0 |
| **모듈 스코프 `t()`**(import 시점 언어로 박제되는 함정) | **0** | 0 |

- `en` 한글 2건은 **거짓 양성**이다 — `t(op, op === '설치' ? 'Install' : …)`
  처럼 **한국어 op 값을 영어로 옮기는 식**이 en 인자에 있는 것이다. 두 앱에 **같은 모양**으로
  있다(3.0 `Settings.tsx:2133,2136` / 2.6.2 `Settings.tsx:1914,1917` — 코드가 같다).
- 모듈 스코프는 초판이 4건을 냈는데 넷 다 `() => t(...)` **화살표 지연 평가**였다
  (`accounts.ts:429,430` · `useLimitResume.ts:27` · `i18n.ts:31`은 정의 자체).
  규약이 **시키는** 형태라 도구를 고쳐 제외했다. 고친 뒤 두 트리 모두 **0건**.

### 3.4 찾은 구멍 — **이번 라운드는 보고만 한다**

**A. 호스트(Rust) 쪽 문자열이 렌더러만큼 번역돼 있지 않다.**

| | `t(ko,en)` 콜사이트 | 고유 ko |
|---|---:|---:|
| 2.6.2 호스트 (`src/main`, 39파일) | **238** | **194** |
| 3.0 호스트 (`src-tauri/src`+`crates`, 145파일) | **54** | **37** |

두 호스트 모두 같은 문법을 쓴다(2.6.2 `src/main/lang.ts` · 3.0 `ccg_fs::t` +
`ipc/parity/aimsg.rs::t`). 차이의 상당 부분은 **문자열이 렌더러로 옮겨간 것**으로 보이지만
(3.0 렌더러가 ko를 198개 더 가졌다) 그 대응을 한 줄씩 맞춰 보진 않았다 — **미검증**이다.

**B. 확인된 실물 회귀 1건 — 첨부 파일 대화상자가 한국어 고정.**

```
3.0   src-tauri/src/ipc/parity/dialog.rs:45-49          2.6.2  src/main/index.ts:1355-1360
  .set_title("첨부할 파일 선택")          ← t() 없음      title:  t('첨부할 파일 선택', 'Choose files to attach')
  .add_filter("첨부 가능한 파일", &all)   ← t() 없음      name:   t('첨부 가능한 파일', 'Attachable files')
  .add_filter("이미지", &IMAGE)          ← t() 없음      name:   t('이미지', 'Images')
  .add_filter("텍스트·문서", &TEXT)       ← t() 없음      name:   t('텍스트·문서', 'Text & documents')
```

**네 문자열 전부 2.6.2는 번역하고 3.0은 안 한다.** UI 언어를 `en`으로 둬도 네이티브 파일
선택 창의 제목과 필터 이름만 한국어로 남는다. M8 크리틱 S4(「UI 언어가 en인데 트레이
메뉴만 한국어」)와 **같은 계열**의 자리이고, 그때와 같은 처방(`ccg_fs::t` 감싸기)으로 닫힌다.

**C. 파리티라서 회귀는 아닌 것**(참고):
탐색기 우클릭 라벨은 3.0 `AgentCodeGUI3으로 열기`(`src-tauri/nsis/hooks.nsh`),
2.6.2 `AgentCodeGUI로 열기`(`build/installer.nsh:16,21`) — **둘 다 한국어 고정**이다.

**D. 하드코딩 후보 수(같은 자로 잰 비교값).**
따옴표 문자열 리터럴만 세고 패치노트(ko 원문이 그대로 있는 게 정상)를 뺀 값:
**3.0 = 58 · 2.6.2 = 49.** 같은 오차가 양쪽에 걸리므로 **차(+9)만 의미가 있고**,
그 대부분은 `app/src/api/shim.ts`의 개발자용 진단 문구(`백엔드 미구현 채널` 등 9건 —
2.6.2에 대응 파일이 없다)다. 절대값을 「번역 누락 58건」으로 읽으면 안 된다.

### 3.5 미결로 남는 것

- **A**의 대응 여부(호스트 문자열을 한 줄씩 맞출지) — 비용이 크고 사용자 체감이 작다.
- **B**는 4줄이면 닫힌다(`ccg_fs::t` 감싸기). **다음 라운드의 수정 항목.**
- 도구의 정밀도: `scripts/i18n-sweep.mjs`의 `string-tpl`/`jsx-text` 후보는 JSX·템플릿 안에서
  스캐너가 자리를 잃어 **잡음이 많다**(초판은 정규식 리터럴 안의 백틱에 걸려 20여 건을
  거짓 보고했고, 그건 고쳤다). 본문 수치는 전부 `string` 종류만 썼다.
