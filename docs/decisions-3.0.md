> 앱 몫 Private **0.53은 우리 코드가 아니다** — 같은 파일을 역할별로 가르면 렌더러만
> 뗐을 때 3.0이 **더 많이** 쓴다(§1.3). 수치는 그대로고, **그 수에 붙었던 문장을 고쳤다.**

이 문서는 **결정의 장부**다. 보고서가 아니다.
사용자가 내린 결정을 한 자리에 모으고, 각 결정에 **무엇을 · 왜 · 근거 수치 · 무엇이
미결로 남는가**를 붙인다. 다음 사람은 이 문서만 읽고도 "왜 이렇게 돼 있나"에 답할 수
있어야 한다.

규칙 셋을 지킨다.

1. **근거 없는 줄을 쓰지 않는다.** 모든 수치에 어느 파일의 어느 필드인지를 단다.
2. **제안과 결정을 섞지 않는다.** 사용자가 정한 것은 「결정」, 내가 계산한 합격선은
   「제안」이라고 적는다.
3. **불리한 수치를 빼지 않는다.** 이번 라운드에서 **가장 중요한 발견은 3.0에 불리한
   쪽**이다(§1.4 · §1.6-A).

## 1. 결정 ① — 성능 목표를 **비율 목표**로 재정의한다

### 1.1 왜 절대치가 불가능한가 — 두 개의 바닥값

목표를 못 지킨 게 아니라 **목표가 물리적으로 도달 불가능**이라는 것이 실측으로 확정됐다.
근거는 두 개의 바닥값이다.

**(a) 메모리 바닥값 — 빈 문서(`about:blank`)**

`bench/gpuprobe.mjs`가 살아 있는 앱의 문서를 통째로 언로드하고(`Page.navigate about:blank`)
같은 프로세스 트리를 다시 잰다. **해제 검증**이 붙어 있다 — DOM 노드·리스너가 90% 이상
사라져야 그 값을 바닥값이라 부른다(`release.verdict`).

### 1.3 ★ 바닥값을 뺀 「앱 몫」 비율 — 신규 수치, 그리고 그 수를 부르면 안 되는 이름

총량 비율은 두 앱이 **어쩔 수 없이 지고 가는 런타임 바닥값**을 분자·분모에 같이 담는다.
바닥값을 빼면 **「문서를 언로드하면 돌아오는 몫」** 이 남는다. 그래서 **2.6.2의 빈 문서
바닥값을 같은 하네스·같은 픽스처·같은 세션에서 처음 쟀다.**

> **★ 수정 R1의 정정 — 이 수를 「우리 코드」라고 부르면 안 된다.**
> 초판은 앱 몫 Private **0.53**을 *「진짜 승점 · 우리가 쓴 코드의 값」* 이라고 적었다.
> **같은 파일이 그 문장을 반박한다**(확인 크리틱 S2-2 · 내가 기계로 재계산해 확인).
> `byRole` 분해는 §1.3-b에 있고, 결론은 이렇다: **우리 문서가 붙드는 몫(renderer)만 떼면
> 3.0이 두 축 다 더 많이 쓴다.** 0.53을 만드는 것은 2.6.2의 **비-렌더러** 프로세스가
> 언로드 때 Private을 44.9MB 반납하는 것이고, 그건 Chromium의 프로세스 구조다 —
> §1.3이 빼겠다고 선언한 바로 그 종류의 값이다.
> 그러니 앱 몫은 **「언로드로 회수되는 몫의 비율」** 이라고만 불러라. 총량 비율
> (Private 0.507)로 「3.0이 Private을 덜 쓴다」고 말하는 것은 **여전히 참**이고,
> 그 주장에는 앱 몫 논증이 애초에 필요 없다.

| | 4패널 기준선 | − 빈 문서 바닥 | = **앱 몫** |
|---|---:|---:|---:|
| 3.0 WS | 574.2 | 515.9 | **58.3** |
| 2.6.2 WS | 699.5 | 643.1 | **56.4** |
| **앱 몫 WS 비율** | | | **1.03** |
| 3.0 Private | 335.3 | 289.9 | **45.4** |
| 2.6.2 Private | 485.2 | 399.3 | **85.9** |
| **앱 몫 Private 비율** | | | **0.53** |
| 런타임 바닥값 WS 비율(우리 성과 아님) | | | 515.9 / 643.1 = **0.80** |

3.0 쪽을 R4 크리틱 exe로 바꿔 넣으면 앱 몫 WS 47.3 → 비율 **0.84**(교차 세션이라 참고값).

> **바닥값 515.9에 붙는 주의**: 이 수에는 §1.4의 LSP 헬퍼 3프로세스(145.5MB)가 들어 있다 —
> 문서를 언로드해도 LSP 서버는 안 죽으니 당연하다. **앱 몫은 그 영향을 안 받는다**
> (기준선에도 바닥값에도 똑같이 들어 있어 뺄 때 상쇄된다). 그래서 「앱 몫」 비율은
> 이 라운드에서 가장 튼튼한 수이고, 「바닥값」 비율(0.80)은 LSP 때문에 3.0에 불리하게
> 부풀어 있다(LSP를 빼면 3.0 바닥 ≈ 370, 비율 ≈ 0.58 — R4가 잰 351.5와 같은 대역).

> **정직한 결론: WS의 승리는 거의 전부 런타임 바닥값의 차이다.**
> 우리 UI가 WS로 쓰는 몫은 2.6.2와 **같거나 조금 많다**(0.84~1.03). 같은 React 트리를
> 그대로 이식했으니 당연한 결과이기도 하다 — 3.0의 렌더러는 2.6.2 렌더러의 이식본이다
> (`docs/renderer-divergence.md`).
> **시간 축의 앱 몫은 승점이다**(아래 표 0.61). **메모리 축에서는 앱 몫이 승점이 아니다** —
> 초판이 여기서 0.53을 들었던 자리이고, 그 귀속은 §1.3-b가 철회한다.

|---|---:|---:|---:|---:|
| 3.0 | 348 | 199 | **149 ms** | |
| 2.6.2 | 443 | 199 | **244 ms** | **0.61** |

### 1.3-b ★ 앱 몫을 **역할별로** 가르면 — 0.53의 진짜 출처 (수정 R1 신규)

같은 두 파일(`gpu-css-probe-r28j-dec-{tauri,electron}.json`)의 `byRole`로
**기준선 − 빈 문서**를 역할별로 가른 값. `node bench/ratios.mjs`가 `roleSplit`으로 낸다
(손으로 옮겨 적지 않는다 — 그게 이 절이 생긴 이유다).

| 역할 | 3.0 ΔWS / ΔPriv | 2.6.2 ΔWS / ΔPriv |
|---|---:|---:|
| **renderer**(문서가 붙드는 몫) | **53.2 / 46.2** | **39.7 / 41.0** |
| browser | 8.2 / −0.2 | 17.1 / 20.6 |
| gpu-process | (역할 없음) | −0.9 / **23.5** |
| crashpad · utility | −3.1 / −0.5 | 0.4 / 0.8 |
| **합 = 앱 몫** | 58.3 / 45.5 | 56.3 / 85.9 |

  ★**정정**(확인 크리틱 R2 F5): 초판은 괄호에 큰 둘만 적어 **20.6+23.5=44.1**이 되어

> ① 3.0의 `browser` 역할 묶음에는 Rust 호스트와 **LSP 헬퍼 3프로세스가 같이 들어 있다**

> Δ에서는 거의 상쇄된다(3.0 비-렌더러 Δ가 −0.7인 이유).

### 1.4-b ★★ 「있는 그대로」는 벤치가 만든 상태다 — 세 자리에서 다시 쟀다 (수정 R1)

**질문**: `605.1`(프로세스 8개)이 정말 사용자가 부팅 직후 겪는 상태인가?

내가 `HEAD`(`e44af03`)를 깨끗한 트리(`git archive`)에 풀어 새 `CARGO_TARGET_DIR`
(`target-r28j-dec-r1`)로 구운 **한 개의 exe**(sha256 `0a3e5384cea48ba8…` · 7,066,624 B)를
**세 자리에서** 돌렸다. 픽스처·정착·반복(3회)·세션은 전부 같고, **바뀐 것은 exe 위치와
프로세스 cwd뿐**이다.

| 주행 | exe 위치 / 프로세스 cwd | 프로세스 | LSP 헬퍼 | 유휴 WS | 유휴 Private |

| 2.6.2(분모) | 레포 | 7 | 0 | 718.6 | 508.9 |

**세 번째 주행이 원인을 못 박는다**: 같은 자리·같은 exe인데 `CCG_LSP_MODULES` 한 줄로
헬퍼가 **0 → 3**으로 돌아온다. 즉 원인은 「위치」라는 마법이 아니라 **`node_modules`
해석 하나**다.

**코드의 자백**(`crates/ccg-lsp/src/launch.rs::shipped_module()`): ① `CCG_LSP_MODULES`
② **exe 폴더에서 위로** ③ **프로세스 cwd에서 위로** 훑어 `node_modules`를 찾는다.
벤치는 exe가 `…\target-*\release\`(레포 안)라 **항상 레포의 `node_modules`를 문다.**
설치 폴더(`%LOCALAPPDATA%\AgentCodeGUI3` — `AgentCodeGUI3.exe`와 `uninstall.exe`
**두 파일뿐**)와 그 조상(`…\Local` · `…\AppData` · `…\User` · `C:\`)에는 `node_modules`가
없다 — 내가 하나씩 확인했다. 같은 파일 머리말이 이미 적어 뒀다: *「3.0은 아직 Node
런타임을 번들하지 않는다 … 지금은 개발/벤치 경로 = 레포의 `node_modules` + 시스템 `node`」*.

> ★**정정**(확인 크리틱 R2 F1 · 2026-08-26). 이 문단의 초판은 *「프로젝트 폴더에

> 것이 사실이지만, **프로세스 cwd에서 위로 훑는 경로 ③이 있다**
> (`crates/ccg-lsp/src/launch.rs:68`). 그래서 헬퍼의 유무를 가르는 것은 「배포 위치」
> 하나가 아니라 **exe 폴더 사슬 ∪ 프로세스 cwd 사슬**이다 — §1.4-b가 스스로 그렇게
> 적어 놓고(②③) 결론 문장만 「위치」로 좁혔다.

> 크리틱 실측(같은 exe · sha256 `feaddb64…` · **배포 위치 그대로**, cwd만 프로젝트로):

> 프로젝트 폴더에서 연 셸이 그 cwd를 만든다.

> 벤치 경로 쪽(0.83대)으로 움직인다. **그때는 2.6.2 팔에도 LSP를 설치해야 두 팔이
> 같아진다** — 실사용 2.6.2 사용자는 서버를 이미 받아 뒀기 때문이다(오히려 실사용에서는

### 1.5-b ★★ 합격선 **확정** — 그리고 확정하려고 재보니 결론이 뒤집혔다 (GATES R1)

> **사용자 승인 2026-08-31.** 결정 셋: **① 메모리 게이트의 잣대는 「LSP 제외」** ·
> **② 설치 풋프린트 0.10 → 0.25** · **③ 확정 전에 2.6.2 분모를 한 번 다시 잰다.**
> **③이 ①의 근거를 무너뜨렸다.** 숨기지 않고 여기 적는다.
>
> **무엇이 틀렸었나.** §1.4가 *「그런데 2.6.2 팔에서는 안 뜬다 … 서버가 앱 홈에 설치돼
> 있어야 뜨고, 벤치 격리 홈은 비어 있다」*고 적었고 §1.4-b·§1.5가 그 위에 「LSP 제외」를
> 회귀 추적선으로 세웠다. **그 전제가 거짓이다.** 2.6.2의 TS·Python 서버는 **앱 홈 설치를
> 요구하지 않는다** — `shippedModule()`이 `app.getAppPath()/node_modules`를 물고
> (`src/main/lsp/manager.ts:773-785`), `ELECTRON_RUN_AS_NODE=1`로 **`electron.exe`가 곧
> 노드**다(`:788`). 설치를 타는 것은 C#·C++뿐이다.
> 즉 벤치의 2.6.2 팔은 **처음부터 tsls + tsserver 둘을 지고 있었고**, 「2.6.2 헬퍼 0」은
> 측정이 아니라 `bench/ratios.mjs`의 **이름 정규식이 `electron.exe`를 못 문 것**이었다
> (LSPDIST R1 §6.5가 발견 · 그 확인 크리틱 C5가 **「G1은 가장 둔감한 수가 아니라 가장
> 오염되기 쉬운 수다」**라고 예고한 바로 그 자리다. 예고가 맞았다).
>
> **그래서 「LSP 제외」는 두 팔에서 같은 규칙이었지만 같은 효과가 아니었다** — 3.0에서는
> 100MB대를 빼고 2.6.2에서는 0을 뺐다. 분류를 **명령줄 기반**으로 고치고 같은 세션에서
> 다시 재니 이렇게 갈린다:
> **분자는 안 움직였다**(배포 경로·LSP 제외 유휴 WS `450.5` → `454.5`MB).
> **분모가 200MB 넘게 내려왔다**(`718.6` → LSP 제외 `512.9`MB).
> 결과: **G1·G3가 미달로 뒤집힌다.** 비율·여유는 `bench/results/ratios-gates-r1.json`이
> 낸다 — **여기 손으로 안 적는다**(§1.5의 규칙 그대로).
>
> **확정돼 코드에 박힌 것** (`bench/ratios.mjs`의 `G` 상수와 `gates` 블록):
> · 메모리 게이트(G1·G3·G4)는 **「LSP 제외」 행에만** 걸린다. 「있는 그대로」 행은 전부
>   `gate: null` 참고 행으로 내렸다(옛 파일에서 온 행들도 같이).
> · `footprint` **0.25**. 옛 `0.10`은 LSPDIST 이후 설치기(30.9MB ÷ 157.5MB)에서 **이미
>   미달**이었다. 게이트가 막아야 하는 것은 「크롬을 도로 안고 오는 것」이지 「언어 서버를
>   실은 것」이 아니다.
> · 나머지(G5 창당 · G7 콜드 · G12 앱 몫 콜드)는 제안값 그대로이고 **전부 통과**다.
> · ★ 산출물의 블록 이름이 `proposedGates` → **`gates`**로 바뀌었다(위 §1.5 마지막 문단의
>   이름은 그 시점 기록으로 둔다).
>
> **★ 열린 채로 남는 것 — 잣대 자체를 다시 물어야 한다.** 두 앱의 LSP 몫은 축에 따라
> 다른 이야기를 한다: **WS에서는 `208.3` 대 `115.5`MB(2.6.2가 1.8배)인데 Private에서는
> `111.3` 대 `101.6`MB로 거의 같다.** WS가 프로세스마다 공유 이미지 페이지를 다시 세고
> 2.6.2는 서버를 **Chromium 바이너리로** 띄우기 때문이다. 즉 **「LSP 제외 WS」는 분모에서
> 부풀린 값을 빼는 잣대**이고, 그 뺄셈이 **3.0의 실제 승점(같은 기능을 절반 값에 지고
> 간다)을 표에서 지운다.** 갈래 셋:
> ① 그대로 두고 3.0이 미달임을 받는다 · ② 메모리 게이트를 **Private 축**으로 옮긴다

> 대조표와 근거는 `docs/parity-fix-gates-r1.md`.

### 1.5-c ★★★ 합격선 **최종 확정** — 잣대를 뒤집었다 (GATES R2)

> **★확정 2026-08-31(리드 결정) · 실측·배선 2026-09-01.**
> **잣대 = 「있는 그대로」(사용자가 겪는 값 · 배포 경로).** 「LSP 제외」는 `gate:null`
> 참고 행으로 **강등한다.** §1.5-b가 배선한 것과 **정확히 반대**이고, 그 절이 열어 둔
> 「갈래 셋」 중 **③**을 고른 것이다.
>
> **왜 뒤집히나 — 잣대가 아니라 제품이 움직였다.**
> §1.5-b의 배선은 「배포본에 언어 서버가 실리면서 『있는 그대로』가 성능이 아니라
> **적재물의 함수**가 됐다」는 사실 위에 서 있었다. **그 사실이 LSPIDLE로 사라졌다** —
> 프리웜이 「기동」에서 「준비만」으로 바뀌어 **코드 뷰어를 안 여는 유휴에는 언어 서버가
> 애초에 안 뜬다**(`docs/parity-fix-lspidle-r1.md`). 그 결과 셋이 한꺼번에 성립한다:
> · **(ⅰ)** 3.0 쪽에서 「LSP 제외」가 빼는 값이 **0**이다 → 두 잣대가 3.0에서 **같은 수**다.
> · **(ⅱ)** 그런데 2.6.2에서는 여전히 뺀다 → 「LSP 제외」는 이제 **분모에서만 빼는 자**다.
>   §1.5-b가 「열린 채로 남는 것」에 적어 둔 **WS 과대계상 뺄셈**(2.6.2를 Chromium
>   바이너리로 띄워 공유 이미지가 부풀려지는 문제)이 R1 때보다 **더 커졌다.**
> · **(ⅲ)** 「적재물의 함수」라는 강등 사유도 함께 사라졌다 — 적재물이 늘어도 **유휴
>   메모리는 안 움직인다**(디스크 풋프린트에만 얹히고, 그건 G9가 따로 본다).
>
> **합격선을 고른 규칙**(값이 아니라 규칙을 먼저 못 박는다 — `bench/ratios.mjs`의 `G` 상수
> 주석에 같은 문장이 있다): **오늘 실측 위에 여유를 두되 §1.5-b의 확정선보다 느슨하게는
> 가지 않는다.** 선은 **조이기만** 한다. 조일 때는 0.05 눈금으로 내리고, **조인 뒤에도
> 두 분모 모두에서 여유가 10% 이상** 남아야 한다.
> 그 규칙이 낸 결과: **G4 0.70 → 0.60 · G5 0.30 → 0.25로 조였고**, G1(0.70)·G3(0.60)·
> G7(0.85)·G9(0.25)·G12(0.70)는 **그대로**다(조이면 여유가 규칙 밑으로 내려간다).
> **느슨해진 칸은 하나도 없다.**

> 이 절에도 그대로 실려 있다. 위 본문은 그 시점 기록으로 두고 여기서 바로잡는다:

> 자리라 그 사실이 승인문 옆에 있어야 한다.** 천장 표는 `parity-fix-gates-r2.md` §3.1의 ★정정.

> **② 귀속은 2×2이고 초록은 네 칸 중 하나뿐이다.** R2 보고서가 「초록을 만든 것은 LSPIDLE,

> 그대로 = WS 0.790 / Priv 0.692 — 둘 다 미달**)을 채우면 이렇게 된다:
> **LSPIDLE과 잣대 교체는 어느 쪽도 단독으로 초록을 못 만든다 — 둘 다 필요조건이다.**

> 0이 되므로). 즉 **잣대 교체는 조명이 아니라 필요조건**이었다.

> 손대지 않았다** — 크리틱이 재계산으로 봉인했고, 고칠 것은 문장뿐이었다.
>
> 대조표·재현·남은 흠은 `docs/parity-fix-gates-r2.md`.

### 1.6 미결로 남는 것

- **A. 주 게이트의 LSP 비대칭.** 위 §1.4 · §1.4-b. **초판의 세 갈래는 근본 원인을
  비껴갔다**(확인 크리틱 S2-1 — 옳다). 문제는 픽스처가 아니라 **재는 exe의 위치**이고,
  초판의 (a)를 고르면 두 팔 다 **배포본에 없는 것**을 재게 된다. 갈래를 다시 쓴다:
  - **(a′) 배포 위치에서 잰다** ← 수정 R1이 고른 길. exe를 레포 밖에 두고 `--cwd`도 거기로
    (§1.4-b의 재현 블록). **오늘 두 팔이 다 「배포본에 있는 것」만 재게 된다.**
    비용은 주행마다 exe 복사 한 번. `bench/fixture.mjs`는 안 건드린다.
  - **(b′) 패키징 뒤에는 두 팔 다 LSP가 있게 맞춘다.** `resources/node.exe` +

  - **(c″) ★「LSP 제외」는 근사다**(확인 크리틱 R2 F2). 피감수는 정착 직후의

    뺄셈**이다. 크기도 무시할 수준이 아니다 — 벤치 팔의 두 총계가 **691.3 대 594.6**으로

    초판은 이 주석을 G4 한 줄에만 달아 유휴 두 줄이 같은 순간의 뺄셈처럼 읽혔다 —

    역할별 표본)은 하네스 숙제다.

    회귀 추적선으로 이걸 쓴다. (초판 (c)와 같은 결론이지만 **주 게이트로 승격**한다.)

    쓸 수 있는 레버는 **exe 위치 + cwd뿐**이다.

### 3.4 찾은 구멍 — **이번 라운드는 보고만 한다**

**A. 호스트(Rust) 쪽 문자열이 렌더러만큼 번역돼 있지 않다.**

| | `t(ko,en)` 콜사이트 | 고유 ko |
|---|---:|---:|
| 2.6.2 호스트 (`src/main`, 39파일) | **238** | **194** |
| 3.0 호스트 (`src-tauri/src`+`crates`, 145파일) | **54** | **37** |

두 호스트 모두 같은 문법을 쓴다(2.6.2 `src/main/lang.ts` · 3.0 `ccg_fs::t` +
`ipc/parity/aimsg.rs::t`). 차이의 상당 부분은 **문자열이 렌더러로 옮겨간 것**으로 보이지만
(3.0 렌더러가 ko를 198개 더 가졌다) 그 대응을 한 줄씩 맞춰 보진 않았다 — **미검증**이다.

**B. 확인된 실물 회귀 1건 — 첨부 파일 대화상자가 한국어 고정.**

```
3.0   src-tauri/src/ipc/parity/dialog.rs:45-49          2.6.2  src/main/index.ts:1355-1360
  .set_title("첨부할 파일 선택")          ← t() 없음      title:  t('첨부할 파일 선택', 'Choose files to attach')

  .add_filter("이미지", &IMAGE)          ← t() 없음      name:   t('이미지', 'Images')
  .add_filter("텍스트·문서", &TEXT)       ← t() 없음      name:   t('텍스트·문서', 'Text & documents')
```

**네 문자열 전부 2.6.2는 번역하고 3.0은 안 한다.** UI 언어를 `en`으로 둬도 네이티브 파일
선택 창의 제목과 필터 이름만 한국어로 남는다. M8 크리틱 S4(「UI 언어가 en인데 트레이
메뉴만 한국어」)와 **같은 계열**의 자리이고, 그때와 같은 처방(`ccg_fs::t` 감싸기)으로 닫힌다.

**C. 파리티라서 회귀는 아닌 것**(참고):
탐색기 우클릭 라벨은 3.0 `AgentCodeGUI3으로 열기`(`src-tauri/nsis/hooks.nsh`),
2.6.2 `AgentCodeGUI로 열기`(`build/installer.nsh:16,21`) — **둘 다 한국어 고정**이다.

**D. 하드코딩 후보 수(같은 자로 잰 비교값).**
따옴표 문자열 리터럴만 세고 패치노트(ko 원문이 그대로 있는 게 정상)를 뺀 값:
**3.0 = 58 · 2.6.2 = 49.** 같은 오차가 양쪽에 걸리므로 **차(+9)만 의미가 있고**,
그 대부분은 `app/src/api/shim.ts`의 개발자용 진단 문구(`백엔드 미구현 채널` 등 9건 —
2.6.2에 대응 파일이 없다)다. 절대값을 「번역 누락 58건」으로 읽으면 안 된다.
