## AgentCodeGUI 3.0.9

한도가 초기화됐는데 설정 · 계정 picker가 「0% 남음 · 곧」을 붙들던 것과 한 계정의 한도가 19시간째 옛 값이던 것, /clear 뒤 첫 전송이 「작업 중」에 굳던 것을 실측으로 고쳤습니다. 설정에 Updates 페이지(확인 · 설치 · 패치노트)가 생겼고, OpenAI 모델 목록에 GPT-6-Astra를 올리고 GPT-5.3 같은 구세대를 빼고 속도(Fast · Ultrafast)를 고를 수 있게 했습니다.
3.0.x를 쓰고 있다면 앱 안에서 자동으로 이 업데이트를 받습니다.

**바뀐 것**

- **한도가 초기화됐는데 설정·계정 picker는 「0% 남음 · 곧」을 붙들고 있던 것 — 리셋 시각을 지난 값을 아무도 지난 값으로 안 봤다.** 한도 게이지는 마지막 조회값을 그리고, 캐시(셸 디스크 2분 · 메모리 5분 · 렌더러 1분)는 값의 나이만 봤습니다. 창의 초기화 시각이 지났다는 사실은 「곧」이라는 글자로만 남고, 그 퍼센트가 지난 창의 값이라는 판정은 어디에도 없었습니다. 그래서 Anthropic이 한도를 초기화해 준 뒤에도(결제 직후 · 지원 처리 등) 캐시가 살아 있는 동안은 옛 「Fable 0% 남음 · 곧」이 그대로였고, 설정 탭은 주기 갱신이 없어 닫고 다시 열기 전엔 바뀌지 않았습니다(제보 스크린샷 — 그 사이 디스크 캐시는 정상값으로 갱신돼 있었습니다). 이제 리셋 시각을 지난 창은 지난 창의 값으로 읽습니다: 앱은 그 행을 캐시 적중으로 치지 않고 다시 묻고(디스크·메모리 둘 다), 화면은 값이 들어올 때마다 가장 이른 리셋 시각에 시계를 걸어 그 순간 다시 묻습니다(이미 지난 창이 있으면 곧바로 · 계정당 1분에 한 번). 그 사이 게이지(설정 · 계정 picker · 작업 바 팝오버)는 「초기화됨 · 새 값 확인 중」으로 그리고, 소진 숨김 필터 · 「주간 소진」 줄 · 정렬(임박순 · 적게 남은순)도 지난 창을 소진으로 세지 않습니다 — 엔진의 자동 전환이 이미 쓰던 판정과 같은 규칙입니다.
- **한 계정의 한도가 19시간째 옛 값이던 것 — usage API의 「1시간 뒤 다시」를 30초로 잘라 되두드렸다.** 한도 조회 API는 계정 단위로 세게 제한돼 429에 `Retry-After: 3600`(1시간)을 돌려주기도 합니다(실측). 앱은 그 값을 30초 상한으로 잘라 자고 곧바로 한 번 더 물었고(그동안 직렬 조회 큐가 통째로 멈춤), 실패하면 3분 뒤 또 2건, 자동 전환 워커도 따로 20초→5분 곡선으로 또 — 차단 중인 계정에 시간당 수십 건이 나가 차단이 풀리지 않았고, 화면엔 19시간 전 값이 실측처럼 남았습니다. 이제 서버가 부른 대기가 30초보다 길면 자지도 되묻지도 않고 그 길이(최대 1시간)만큼 그 계정의 조회를 건너뜁니다 — 설정 조회와 자동 전환 워커 둘 다. 「다시 시도」를 직접 누르면 그때는 묻습니다. 낡은 값은 그대로 보이되, 지난 창이면 위의 「초기화됨」으로 읽힙니다.
- **OpenAI 모델 목록 — GPT-6-Astra 추가 · GPT-5.3 같은 구세대 제거 · 한국어 설명 · 속도(Fast) 선택.** Codex CLI 0.153의 모델 목록(`model/list`)을 실측해 맞췄습니다. GPT-6-Astra(가장 뛰어난 모델 · 복잡하고 까다로운 작업)가 맨 위에 오르고, 설명은 서버 영어 원문 대신 GPT-5.6-Sol처럼 한국어로 적힙니다(Sol은 「믿음직한 에이전트 일꾼 · 일상 작업」으로 서버 설명에 맞춰 고쳤습니다). 서버가 목록에 아직 남겨 둔 구세대(GPT-5.3-Codex-Spark · 5.4-Mini · 5.5)는 이름표가 아니라 세대 규칙(5.6 미만)으로 걸러 앞으로 나올 옛 모델도 같이 빠집니다 — 6.x·모르는 새 모델은 그대로 뜹니다. 그리고 서버가 모델마다 광고하는 속도 티어(Astra 「Fast · 2배」 · 5.6 「Fast · 1.5배」 · Sol은 「Ultrafast」도 · 5.4-Mini 없음)를 선택한 모델의 추론 슬라이더 아래 「속도」 줄에서 표준 / Fast / Ultrafast로 고를 수 있습니다. 고른 값은 채팅 정체성의 축(`engine.codexTier`)이 되어 `thread/start`·`thread/resume`·`turn/start`의 `serviceTier`로 실리고, 칩에는 「GPT-6-Astra · Fast」로 붙고, 티어가 없는 모델로 바꾸면 내려놓습니다. 티어를 고르지 않은 채팅의 저장 파일과 정체성 해시는 한 글자도 바뀌지 않습니다. 그리고 Codex 스레드마다 채팅에 앉던 「Under-development features enabled … suppress_unstable_features_warning」 경고 카드는 스레드 설정에 그 억제 키를 실어 더 뜨지 않습니다(app-server에 직접 확인).
- **/clear 뒤 첫 전송이 「작업 중」에 몇 분씩 굳고, 중단 후 다시 보내면 몇 초 만에 답하던 것 — 실행 채택이 이벤트 하나에만 걸려 있었다.** 3.0.5(유휴 중지) · 3.0.7(한도 대기) · 3.0.8(CLI의 API 재시도 대기)에서 매번 다른 원인으로 짚었던 제보입니다. 이번엔 세션 파일로 실측했습니다: CLI는 **3초 만에 답을 다 썼는데**(사고 · 본문 · 파일 읽기 2회) 화면은 아무것도 받지 못했습니다 — 앱 쪽 유실입니다. 렌더러는 새 실행의 id를 `status:analyzing` 이벤트 **하나**에서만 채택하고, 그 전까지 오는 이벤트는 전부 「지난 실행의 잔재」로 버립니다. 그 한 이벤트가 전송 중 유실되면 실행 id가 영영 「대기」에 묶여 뒤따르는 working · result · done이 모두 버려지고, 전송이 세운 「작업 중」만 남습니다 — 중단+재전송이 유일한 복구였던 이유입니다. 이제 대기 상태에서 실 실행의 `working`(살아 있는 턴의 첫 도구 신호 — 잔재는 done/error라 혼동될 수 없다)을 만나면 그 실행을 채택해 매듭을 풉니다. `scripts/poc-pending-adopt.mjs`가 유실을 재현하고 채택을 단언합니다. 한계: 이벤트 스트림 자체가 전송 계층에서 끊기면 working도 오지 않아 이 처방이 닿지 않습니다 — 재발하면 `CCG_ENGINE_LOG`로 전송과 리듀서를 가릅니다.
- **설정 › Updates — 업데이트 확인 · 설치 · 재시작과 패치노트를 한 자리에서.** 설정 왼쪽 「앱」 그룹에 **Updates** 페이지가 생겼습니다. 설치된 버전 카드의 「업데이트 확인하기」를 누르면 확인 → 받기 → 「지금 설치 · 재시작」까지 이 자리에서 끝납니다(「이미 최신 버전이에요」 · 실패 안내 포함). 자동 안내를 기다리거나 앱을 껐다 켤 필요가 없습니다. 「패치노트 보기」는 이미 본 버전이라도 이번 · 지난 버전들의 변경 사항 창을 다시 엽니다. 받아 둔 새 버전은 다음 실행에 쓰이고, 설치는 이 버튼으로만 일어납니다 — 종료할 때 몰래 설치하지 않습니다.

> **처음 설치할 때 파란 경고 창이 뜨면 — 정상입니다.** AgentCodeGUI3은 코드 서명 인증서를 쓰지 않습니다.
> 「**추가 정보**」 → 「**실행**」을 누르면 설치가 시작됩니다. 설치 위치는 `%LOCALAPPDATA%\AgentCodeGUI3`, 기존 2.6.2는 그대로 남습니다.

## AgentCodeGUI 3.0.9 (English)

Fixes Settings and the account picker holding on to "0% left · soon" after your limits were reset, one account showing a 19-hour-old limit value, and the first send after /clear freezing on "working" — all measured, not guessed. Adds a Settings › Updates page (check · install · patch notes), puts GPT-6-Astra on the OpenAI model list, drops GPT-5.3-era models, and lets you pick the speed tier (Fast · Ultrafast).
If you are on 3.0.x, the app picks this update up on its own.

**Changed**

- **Limits were reset, but Settings and the account picker kept showing "0% left · soon" — nobody treated a value past its reset time as old.** The limit gauges draw the last fetched value, and the caches (shell disk 2 min · memory 5 min · renderer 1 min) only looked at the value's age. That a window's reset time had passed showed up only as the word "soon"; nothing decided that the percentage was from the previous window. So after Anthropic reset your limits (right after a payment, a support reset), the old "Fable 0% left · soon" stayed as long as the cache lived, and the Settings tab has no periodic refresh, so it did not change until you closed and reopened it (reported screenshot — the disk cache had already been refreshed with the correct value by then). A window past its reset time is now read as the previous window's value: the app no longer counts that row as a cache hit and asks again (disk and memory), and the UI arms a timer at the earliest reset time whenever a value arrives, so it asks again at that moment (immediately if a window has already passed · once a minute per account). Until the new value lands the gauges (Settings · account picker · workbar popover) read "Reset · Checking…", and the exhausted-hide filters, the "Weekly exhausted" line and the sort orders (resets soonest · least left) no longer count a passed window as exhausted — the same rule the engine's auto-switch already used.
- **One account showed a 19-hour-old value — the usage API's "retry in an hour" was cut to 30 seconds and hammered.** The usage API is tightly limited per account and sometimes answers 429 with `Retry-After: 3600` (one hour; measured). The app capped that at 30 seconds, slept, and asked once more right away (stalling the serial query queue for the whole wait), then failed, then asked twice more three minutes later, while the auto-switch worker retried on its own 20s→5min curve — dozens of requests an hour into a blocked account, so the block never lifted and a 19-hour-old value sat on screen as if current. When the server asks for more than 30 seconds the app now neither sleeps nor retries; it skips that account for that long (up to an hour) — in the Settings query and in the auto-switch worker alike. Pressing "Retry" yourself still asks. The old value stays visible, and if its window has passed it reads as "Reset" per the note above.
- **OpenAI model list — GPT-6-Astra added · GPT-5.3-era models removed · Korean descriptions · speed (Fast) selection.** The list now matches what Codex CLI 0.153 actually advertises (`model/list`). GPT-6-Astra (most capable · complex, demanding work) sits on top, and descriptions are written in the app's language instead of the server's English (Sol now reads "reliable agentic workhorse · everyday tasks", matching the server). Previous-generation models the server still lists (GPT-5.3-Codex-Spark · 5.4-Mini · 5.5) are hidden by a generation rule (below 5.6) rather than by name, so future old models drop out too — 6.x and unknown new models still show. And the speed tier each model advertises (Astra "Fast · 2x" · 5.6 "Fast · 1.5x" · Sol also "Ultrafast" · 5.4-Mini none) can be chosen on a "Speed" row under the selected model, below the reasoning slider: Standard / Fast / Ultrafast. The choice becomes an identity axis of the chat (`engine.codexTier`), rides on `thread/start` · `thread/resume` · `turn/start` as `serviceTier`, shows on the chip as "GPT-6-Astra · Fast", and is dropped when you switch to a model without that tier. Saved files and identity hashes of chats that never picked a tier do not change by a single byte. The "Under-development features enabled … suppress_unstable_features_warning" warning card that landed in the chat on every Codex thread no longer appears — the thread config now carries that suppression key (verified directly against the app-server).
- **The first send after /clear froze on "working" for minutes, then answered in seconds after stop + resend — run adoption hung on a single event.** The same report was pinned on a different cause in 3.0.5 (idle stop), 3.0.7 (limit wait) and 3.0.8 (the CLI's API retry wait). This time the session file settled it: the CLI had **finished the whole answer in about 3 seconds** (thinking · text · two file reads) while the panel showed nothing — the drop was on the app side. The renderer adopts a new run's id only from the single `status:analyzing` event and treats everything before that as leftovers of the previous run. If that one event is lost in transit, the run id stays pending forever, every following working · result · done is discarded, and only the "working" set by the send remains — which is exactly why stop + resend was the only way out. Now, while pending, a real run's `working` (the first tool signal of a live turn — leftovers are done/error, so it cannot be confused) adopts that run and unties the knot. `scripts/poc-pending-adopt.mjs` reproduces the loss and asserts the adoption. Limit: if the whole event stream is cut at the transport layer, no working arrives either — if it recurs, capture `CCG_ENGINE_LOG` to tell transport from reducer.
- **Settings › Updates — check · install · restart and the patch notes in one place.** A new **Updates** page lives under the "App" group in Settings. "Check for updates" on the installed-version card runs check → download → "Install now · restart" right there (including "already up to date" and failure notes), so there is no waiting for the automatic prompt or restarting the app. "View patch notes" reopens the changes of this and previous versions even if you have already seen them. A downloaded version is used on the next launch, and installing happens only through this button — never silently on exit.
