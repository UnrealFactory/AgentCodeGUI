# FPS144 R1 — 프레임 타임 눈금 신설 + 144Hz 핫패스

**한 줄**: 기존 「60fps·드랍 0%」 게이트는 **모니터를 재고 있었다**(vsync 간격). 프레임
**작업 시간**을 재는 눈금을 새로 만들어 6.9ms 예산으로 다시 보니, 스크롤은 두 앱 다
예산 안이고, 문제는 **일이 표시율을 따라 늘어나는 구조**(rAF 루프 두 개)였다. 그 구조를
표시율에서 떼어내 60Hz 무후퇴 · 상한 해제 시 **프레임 처리량 +47%**를 얻었다.

덤으로 **기존 스트리밍 팔의 결함 하나**를 찾았다: `--live` 스트리밍의 3.0 칸은
스트리밍이 아니라 **「Not logged in」 오류 말풍선 한 장**을 재고 있었다(§3.3).

---

## 1. 왜 새 눈금이 필요했나

기존 하네스(`bench/multi.mjs`·`scroll.mjs`·`stream.mjs`·`fpsab.mjs`)의 `p95Ms`는
**rAF 콜백이 불린 시각의 간격**이다. 그 간격을 정하는 것은 앱이 아니라 **vsync**다.
60Hz 모니터에서는 앱이 1ms를 쓰든 15ms를 쓰든 간격이 똑같이 16.6~16.8ms로 찍힌다.

그래서 R3 크리틱이 「두 앱 다 p95 16.8ms로 붙어 실패 경계 근처에 가지 않는다 = 정보가
없다」고 적은 것은 **부하가 모자라서가 아니라 눈금이 앱을 안 보고 있었기 때문**이다.
같은 주행에서 두 눈금을 나란히 뽑으면 그 차이가 그대로 보인다(3.0·4패널 동시 스크롤):

| 눈금 | 값 | 무엇을 말하나 |
|---|---|---|
| rAF 간격 p95 (옛 게이트) | **16.8 ms** | 이 기계의 모니터가 60Hz다 |
| 프레임 작업 시간 p95 (새 눈금) | **5.4 ms** | 앱이 프레임당 실제로 쓴 메인 스레드 시간 |

144Hz의 프레임 예산은 **6.9ms**다. 간격 눈금으로는 6.9ms 초과를 셀 수 없다.

## 2. 눈금 — 무엇을 어떻게 재나

### 2.1 원리

Chromium/WebView2의 한 프레임은 `BeginMainFrame` **한 개의 태스크**다:

```
rAF 콜백들 → 스타일 → 레이아웃 → 페인트 → 커밋
```

태스크는 서로를 선점하지 못한다. 그래서 rAF 콜백 **안에서** `MessageChannel`로 시각을
쏘면, 그 메시지 태스크는 **커밋이 끝난 뒤**에야 실행된다. 두 시각의 차이가 그 프레임의
**메인 스레드 작업 시간**이고, 여기엔 **vsync 대기가 들어가지 않는다.**

```
raf(ts) ── t0 = now() ──┐
                        │ (남은 rAF 콜백 + 스타일 + 레이아웃 + 페인트 + 커밋)
port1.onmessage ── t1 = now()
work = t1 - t0
```

구현: `bench/ftgauge.mjs` (공용 계측부) · `bench/fps.mjs` (하네스).
`t0`은 **메시지에 실어** 보낸다 — 전역에 두면 메시지가 다음 프레임 뒤로 밀렸을 때 값이
덮여 `work`가 0/음수로 찍힌다.

rAF **재요청은 콜백 안에서 즉시** 한다. 처음엔 페인트 뒤 메시지 태스크에서 재요청했는데,
그러면 다음 vsync를 놓쳐 **fps가 인위적으로 58.8로 떨어졌다**(실측). 즉시 재요청으로
바꾸자 60.0으로 돌아왔고, 그래야 `avgFps`/`droppedPct` 열이 기존 결과와 그대로 비교된다.
분위 규약도 기존 하네스와 같은 nearest-rank(`floor(n*p)`)를 쓴다.

### 2.2 이 눈금이 맞다는 확인 (독립 대조)

인페이지 값과 **CDP Tracing의 렌더러 메인 스레드 `RunTask` 실측**을 같은 주행에서 비교했다:

| 팔 | 인페이지 workMax | 트레이스 taskMax | 차이 |
|---|---|---|---|
| 1패널 스크롤 | 6.1 ms | 6.26 ms | 2.6% |
| 4패널 스크롤 | 6.4 ms | 6.50 ms | 1.6% |

최대값이 3% 안에서 일치한다 — 인페이지 눈금이 실제 `BeginMainFrame` 태스크를 재고 있다.

### 2.3 한계 (그대로 옮긴다)

1. 우리 rAF 콜백이 그 프레임의 **몇 번째**로 불리는지는 정할 수 없다. 앱이 나중에 등록한
   rAF는 창 안에 들어오고 먼저 등록된 것은 빠진다 → `work`는 프레임 작업의 **하한**이다
   (과소평가 쪽으로 틀린다).
2. 커밋 직후 메시지 태스크 앞에 다른 태스크(입력·IPC·타이머)가 끼면 그만큼 얹힌다. 그
   시간도 같은 예산을 먹는 메인 스레드 작업이라 해석은 같다.
3. **컴포지터 스레드/GPU 프로세스는 안 보인다.** 메인 스레드 눈금이다.
4. `long-animation-frame`(LoAF)은 이 WebView2에서 **안 나왔다**(`loaf: null`). 게다가
   임계 하한이 16ms라 6.9ms 프레임은 원리상 못 본다 — 꼬리 귀속 보조로도 못 썼다.
5. `--novsync`는 **측정 전용 팔**이다. §5 참조.

### 2.4 오염 증인 (`sysCpuPct`)

이 기계에는 **사용자의 실앱이 떠 있다**(실측: `clangd` 하나가 CPU 232초를 먹고 있었다).
그 부하가 밴드째 움직이면 「고치기 전/후」가 코드가 아니라 **기계 상태**를 잰다 — 실제로
같은 코드·같은 팔이 회차마다 p95 **5.2 ↔ 8.4ms**로 흔들렸다.

그래서 모든 측정 창에 `os.cpus()` 누적 시간 차(**프로세스 스폰 0**)를 붙여 `sysCpuPct`로
남긴다. 이 칸이 팔끼리 크게 다른 행은 코드가 아니라 기계를 잰 행이다.
그리고 **판정은 절대값이 아니라 짝지은 A/B**로 한다(§5).

### 3.2 그럼 4패널 스크롤의 6.9ms는 어디로 가나 (트레이스 귀속)

`--trace`로 렌더러 메인 스레드 이벤트의 **자기 시간**을 뽑았다(8초 · 4패널 동시 스크롤):

| 자기 시간 | 횟수 | 이벤트 |
|---:|---:|---|
| **856 ms** | 358 | **Layerize** (합성 레이어 재배치) |
| 113 ms | 4168 | RunTask |
| 110 ms | 1491 | Paint |
| 81 ms | 744 | PrePaint |
| 75 ms | 332 | HitTest |
| 47 ms | 784 | IntersectionObserver::computeIntersections |
| 46 ms | 360 | Commit |
| 40 ms | 134 | Layout |
| 33 ms | 2695 | FunctionCall |

**JS가 아니라 합성**이다 — `Layerize`가 프레임당 1.4ms(1패널)~2.5ms(4패널)로 단연 1위.

그래서 「`backdrop-filter`가 범인」이라는 그럴듯한 가설을 세웠고, **틀렸다는 것을 측정으로
확인했다**(§4).

### 3.3 ★ 기존 스트리밍 팔의 결함 — 3.0 칸은 스트리밍이 아니었다

`bench/multi.mjs --live` 계열의 4패널 동시 스트리밍 팔을 새 눈금으로 돌리다가, 3.0의
표본이 **프레임 15장 / busy 314ms**뿐인 것을 봤다. 2.6.2는 같은 프롬프트로 239장 /
4046ms였다. 진단(`bench/scratch/fps144-diag-live.mjs`) 결과:

```
3.0(배포 모사): 전송 → 1초 안에  "Not logged in · Please run /login"  → busy 314ms
2.6.2         : 같은 프롬프트로 실제 스트리밍                          → busy 4046ms
```

즉 그 팔의 **3.0 칸은 스트리밍이 아니라 오류 말풍선 한 장을 재고 있었다.** 두 앱이 서로
다른 사건을 재는 눈금은 비교가 성립하지 않는다.

- 재현: `node scripts/poc-fps144-live-diag.mjs` (`DIAG_NOACCT=1`이면 계정 제거 대조 팔).
- 대조로 `accounts.json`을 지운 팔도 돌려봤다 → 턴이 **아예 안 열린다**(스케줄링조차 안 뜸).
  격리 홈에서 실계정 턴은 3.0에서 못 쓴다는 뜻이고, 가설(계정 오버라이드 탓)은 기각됐다.
- **파장**: 이전 라운드들이 `--live`로 3.0 스트리밍을 인용했다면 그 칸은 재검토 대상이다.
  이 라운드는 그 팔을 **쓰지 않았다.**
- 증거 파일: `bench/results/fps-tauri-3.0.0-multi-fps144-before.json`(3.0 = 프레임 15~16장 ·
  busy 314/317ms) vs `fps-electron-2.6.2-multi-fps144-before.json`(2.6.2 = 222~239장 ·
  3745/4046ms). 이 두 파일은 **최초 은행**이라 `sysCpuPct` 증인이 없다(그 칸은 §2.4 뒤에
  추가했다) — 절대값은 §3.1의 witnessed 표를 쓰고, 이 두 파일은 위 결함의 증거로만 읽는다.

## 4. 60 캡 훑기 — 무엇을 찾았고 무엇을 안 고쳤나

### 4.1 `app/src`에 **문자 그대로의 60Hz 상수는 없다**

타이머 기반 재도색 루프(16/33/50ms 계열)도 없다. 시각 갱신은 전부 rAF다. 타이머는
600ms(오프스크린 스냅샷 플러시) · 1000ms(경과 초) · 1200ms(백그라운드 셸 로그) ·
5~20s(작업 문구) · 30s · 60s 뿐으로, **프레임과 결합돼 있지 않다.**

`Typewriter`의 `setInterval(30ms)`(`Chat.tsx`)은 유일한 타이머 애니메이션인데 — **그대로
두는 게 맞다.** 30ms 타이머는 표시율과 **무관**해서 144Hz에서도 일이 안 늘어난다. 이걸
rAF로 "현대화"하면 오히려 144Hz에서 일이 2.4배로 늘어난다. 이 라운드의 취지와 정반대다.

### 4.2 진짜 캡은 상수가 아니라 **캡의 부재**였다

`Chat.tsx`의 공개 루프는 커밋 간격을 `Math.min(50, cur / 400)`로 벌린다. 이 식은
`cur ≈ 6656자`에서야 16.6ms를 넘는다. **그 아래에서는 간격 제한이 아예 없다** = rAF마다
커밋 = 커밋마다 `text.slice(0, shown)` 전체를 remark가 **처음부터 재파싱**한다.

- 60Hz: 초당 60회 재파싱
- 144Hz: 초당 **144회** 재파싱 — 같은 코드가 **모니터만 바꿔도 일을 2.4배** 한다

바닥 고정 루프(`useThreadFollow`)도 같은 모양이다: `busy` 동안 **매 프레임 무조건**
`scrollHeight` 읽기(강제 레이아웃) + `scrollTop` 쓰기(scroll 이벤트 → 핸들러가 또 3개 읽기).
표면 4개면 프레임당 4벌.

### 4.3 스트리밍 트레이스 귀속 — 여기서는 **JS가 61%**

합성 스트리밍(4패널 · 8.1초 · §5.1) `--trace` 자기 시간:

| 자기 시간 | 횟수 | 이벤트 |
|---:|---:|---|
| **2734.6 ms** | 14576 | **FunctionCall** (= 리듀서 + React 렌더 + remark 재파싱) |
| 289 ms | 716 | PrePaint |
| 263 ms | 487 | Layerize |
| 224 ms | 13412 | RunTask |
| 223 ms | 285 | Layout |
| 222 ms | 6967 | Paint |
| 200 ms | 567 | UpdateLayoutTree |
| — | **4372** | FireAnimationFrame (≈ **프레임당 9개** = 패널 4 × 루프 2 + 눈금 1) |

메인 스레드 busy 4487ms 중 **JS가 2734.6ms(61%)**, 프레임당 **약 5.6ms**.
6.9ms 예산의 대부분이 여기서 나간다. 스크롤(§3.2)과 정반대 그림이라, **한 처방으로 둘 다
고치려 들면 안 된다**는 것도 이 표가 말해 준다.

### 4.4 안 고친 것들 — 측정이 「범인 아님」이라 말했다

CSS 후보는 **한 부팅 안에서 CSS만 갈아 끼우며 교대로** 쟀다(`scripts/poc-fps144-css.mjs`,
4라운드 · 4패널 동시 스크롤). 코드·프로세스·기계 상태가 전부 같고 바뀌는 건 CSS 한 줄뿐이라
짝지은 차이가 그 CSS의 몫이다.

| 팔 | p95 델타 (vs base) | >6.9ms 델타 | 판정 |
|---|---:|---:|---|
| `.jump-bottom`의 `backdrop-filter` 끔 | **+0.15 ms** | +0.4%p | 이득 없음 → **안 고침** |
| `.jump-bottom-wrap` 통째 제거 | **+0.10 ms** | +0.2%p | 이득 없음 → **안 고침** |
| `content-visibility:auto` 끔 | **+6.65 ms** | **+44.5%p** | 훨씬 나쁨 → **지금이 맞다** |
| `contain-intrinsic-size` 고정 | +0.10 ms | +0.2%p | 이득 없음 → **안 고침** |

- 스크롤 중 살아 있는 블러 표면(sticky `.jump-bottom`)은 **범인이 아니다.** 가설이 틀렸다.
- `content-visibility:auto`는 **끄면 p95가 12.2ms로 뛰고 초과율 44.5%**가 된다 — 네이티브
  가상화가 이미 예산을 지켜 주고 있다. 건드리지 않는다.
- 모달·오버레이의 `backdrop-filter`는 스크롤 중 DOM에 없어 후보가 아니다.
- `.codeblock{animation:rise .4s}` 등 CSS 애니메이션도 **안 건드렸다** — 스트리밍 트레이스에서
  `Paint` 자기 시간이 전체의 **4.9%**뿐이라(§4.3) 여기서 뺄 게 없다.

## 5. 핫패스 수정 — 「일」을 표시율에서 떼어낸다

### 5.1 무엇을 고쳤나 (`app/src/components/Chat.tsx` 한 파일)

두 rAF 루프에 **시간 바닥 `MIN_COMMIT_MS = 10`**을 둔다. 상한을 표시율이 아니라
**사람이 보는 속도**에 거는 것이다.

1. **공개 커밋**(`SmoothMarkdown`) — `Math.min(50, cur/400)` → `Math.max(10, Math.min(50, cur/400))`
2. **바닥 고정**(`useThreadFollow`) — 매 프레임 `scrollHeight` 읽기 + `scrollTop` 쓰기를
   10ms 바닥으로 접는다. 내용은 커밋보다 자주 바뀌지 않으므로 **그보다 자주 고정할 이유가 없다.**

공개 커서의 속도는 시간 기반이라 **총 공개 시간은 그대로**다. 바뀌는 것은 한 커밋에
드러나는 글자 수뿐이다.

**바닥값 10의 근거 — 15에서 실측으로 되돌렸다.** 처음 15ms로 두었더니 60Hz 프레임 주기
(16.67ms)에 너무 가까워, rAF 타임스탬프가 조금만 흔들리면(14.8ms 간격) 커밋이 한 번
걸러지고 다음 커밋이 **두 배 길이**를 한 프레임에 파싱해 꼬리가 두꺼워졌다:

| 바닥 | 60Hz 짝지은 델타 (B−A) | 판정 |
|---|---|---|
| 15 ms | dP50 **+0.5** · dP95 **+0.7** · >6.9ms **+1.2%p** | 60Hz 후퇴 → 기각 |
| **10 ms** | dP50 **0** · dP95 **−0.1** · >6.9ms **+0.1%p** | 무후퇴 → 채택 |

10ms는 60Hz에서 **구조적으로 못 걸린다**(16.67 > 10이라 건너뛸 프레임이 없다).

### 5.2 어떻게 검증했나 — 부팅 교대 A/B + 합성 스트리밍

밴드 이동(§2.4) 때문에 「고치기 전 파일 ↔ 고친 뒤 파일」 절대값 비교는 못 믿는다.
`scripts/poc-fps144-stream.mjs`는 **A-B-A-B로 부팅을 교대**하고 라운드 안에서 짝지어 뺀다
(`fpsab.mjs`와 같은 규약). 두 팔은 exe만 다르다:

- A = HEAD(`493b1db`) 격리 트리 빌드 · B = 거기에 Chat.tsx 변경만 얹은 빌드

**스트리밍 무대는 합성이다.** 실엔진 팔이 3.0에서 성립하지 않으므로(§3.3), 엔진 이벤트가
렌더러로 들어오는 **바로 그 경계**(`window.api.multi.onEvent`의 콜백)에 고정 일정으로
델타를 넣는다(48자 × 40ms × 4패널 = 9730자 / 8.1초). 그 아래로는 제품 코드가 그대로 돈다:

```
리듀서(assistant-stream) → React 팬아웃 → SmoothMarkdown rAF 공개 → remark 재파싱
→ useThreadFollow 바닥 고정 → 레이아웃/페인트/합성
```

즉 **렌더러 핫패스 전체**를 재고 엔진·IPC·모델 지연만 뺀다. 이 라운드가 고치는 자리가
정확히 그 안이라 신호가 오히려 깨끗하고, 일정이 고정이라 **결정적**이다.

**한계**: 2.6.2에는 못 쓴다 — Electron contextBridge의 `window.api`는 frozen·non-writable
이라 경계를 감쌀 수 없다(실측 `node scripts/poc-fps144-api-probe.mjs electron|tauri`:
2.6.2 `apiFrozen: true` · `writable: false`, 3.0 `configurable: true` · `writable: true`).
그래서 이 팔은
**3.0의 고치기 전/후 비교 전용**이고, 앱 간 비교로 인용하면 안 된다. 절대값도 엔진 비용이
빠졌으므로 "실사용 스트리밍 프레임 시간"으로 읽으면 안 된다.

### 5.3 결과 — 60Hz 무후퇴, 상한 해제 시 처리량 +47%

144Hz에서만 갈리는 수정을 60Hz 기계에서 그대로 재면 **두 팔이 같게 나온다**(바닥이 매
프레임 만족되니까). 그래서 프레임 상한을 푼 팔(`--novsync` =
`--disable-gpu-vsync --disable-frame-rate-limit`, 3.0은 제품이 이미 가진 env 옵트인
`CCG_WEBVIEW_ARGS_EXTRA`로만 — **제품 기본값·tauri.conf 불변**)을 같이 돌렸다.

**① 60Hz (무후퇴 확인) — 4라운드 짝지은 중앙값**

| 무대 | A(전) | B(후) | 짝지은 델타 (B−A) |
|---|---|---|---|
| 4패널 동시 스크롤 | p50 3.6 · p95 5.35 · >6.9ms 0% | p50 3.6 · p95 5.35 · >6.9ms 0% | dP95 **−0.15** · dOver69 **0** |
| 4패널 동시 스트리밍 | p50 2.8 · p95 6.05 · p99 16.35 · >6.9ms 3.5% | p50 2.6 · p95 5.95 · p99 15.8 · >6.9ms 3.8% | dP50 **0** · dP95 **−0.1** · dP99 **−0.9** · dOver69 **+0.1%p** |

옛 눈금도 무후퇴: 두 팔 다 **60.0 fps**. 드랍은 **A가 최악 7.6%**(부하가 겹친 r2),
**B는 4라운드 전부 0%**.

**② 프레임 상한 해제 (>60Hz 거동) — 4라운드**

| 무대 | A(전) | B(후) | 판정 |
|---|---|---|---|
| 4패널 스트리밍 **도달 fps** | **688.6** | **1013.65** | **+47%** (4라운드 전부: 664→1010, 670→1022, 710→1016, 706→995) |
| 4패널 스트리밍 p99 | 1.45 ms | 0.95 ms | **−34%** (4라운드 전부 개선) |
| 4패널 동시 스크롤 | p95 4.8 | p95 4.7 | 중립 (스크롤은 이 수정의 대상이 아니다) |

같은 8.1초 일정을 같은 총 공개 시간에 보여 주면서 **프레임을 1.47배 더 낸다** = 프레임당
일이 그만큼 줄었다는 뜻이다. 이것이 144Hz에서 돌아올 몫이다.

**③ 부하가 겹쳤을 때** — r2에서 A가 `sysCpuPct 99.6%`를 맞았다. 같은 라운드에서
A는 p95 29.9ms · 드랍 7.6%, B는 p95 7.1ms · 드랍 0%였다(dP95 **−22.8ms**).
한 라운드짜리 관찰이라 표제로 쓰지 않지만, 방향은 위와 같다.

## 6. 남은 것 / 안 한 것

- **`Layerize`**(4패널 스크롤 프레임당 최대 2.5ms)는 **원인을 못 좁혔다.** CSS 후보 4개가
  전부 무효였고(§4.4), 남은 후보는 합성 레이어 구조 자체다. 다만 현재 p95가 예산 안이라
  (5.4ms) 이 라운드에서 손대는 것은 **추측 최적화**가 된다 — 다음 라운드 숙제로 남긴다.
- **앱 간 스트리밍 비교**는 이 라운드에서 **못 했다**(§3.3 · §5.2 한계). 하려면 격리 홈에서
  3.0의 실계정 턴이 돌게 만드는 별도 작업이 필요하다.
- **실제 144Hz 패널 검증**은 못 했다(이 기계는 60Hz). `--novsync`는 상한 해제 대리 측정이다.
- `content-visibility`·`backdrop-filter`·CSS 애니메이션은 **측정 결과 근거가 없어 안 건드렸다.**
