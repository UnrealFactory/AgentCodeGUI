## 1. §2-1 대량 커밋 — 살아났다 (체크리스트 1·2 통과)

### 재현 조건이 진짜인가

파일 2,000개(추적 중 + 수정), 경로는 한글·공백·40단계 서브폴더 섞어 평균 89자.

```
argv 합계            178,000자      (Windows CreateProcess 한계 32,767자의 5.4배)
status 행 수         2,001행        ← UI가 실제로 그만큼 고를 수 있다(폴더 접기 안 일어남)
옛 방식 git add -A -- …files   스폰 실패: "파일 이름이나 확장명이 너무 깁니다. (os error 206)"
```

`os error 206`(`ERROR_FILENAME_EXCED_RANGE`)은 **프로세스가 뜨지도 못한** 것이다.
"고치기 전이면 같은 판에서 실패했음이 자명한가"에 대한 답 — 자명하다. 재현 성립.

### 새 길

```
결과        ok=true
소요        852ms
git 스폰    3회(계수기)  ·  4회(GIT_TRACE)
```

계수기 3 = `repo_root` + `add`(stdin) + `commit -F -`. GIT_TRACE가 하나 더 세는 것은
`git commit`이 스스로 돌리는 자동 정비(auto gc) 자식이다 — 앱이 띄운 게 아니다.
빌더 보고(831ms·3회)와 오차 범위 안에서 일치한다.

부작용 검사:
- 고르지 않은 `고르지 않은 파일.txt`는 그대로 남았다(커밋에 안 섞였다).
- 커밋에 담긴 파일 수 **정확히 2,000**, 커밋 수 3(init·base·이번 것), 제목 그대로.

### 유니코드·공백·이모지 경로

`한글 폴더/띄어쓰기 파일 이름.txt` · `이모지 🚀 폴더/파일 (괄호).txt` 커밋 성공,
고르지 않은 파일 생존. 제목 `유니코드 제목 — 한글 · 🚀`, 본문(개행 2줄 + `# 샾 줄`)이
`commit -F -` 왕복 뒤에도 **한 글자도 안 잘렸다**(`commit_detail`로 되읽어 확인).
`#`로 시작하는 줄이 살아 있다 = `-m`과 같은 정리 규칙을 탄다는 주장도 실측으로 참.

고약한 이름 한 판(`위험 #샾 [대괄호].txt`, 경로에 `" b/"`가 든 `공백 있는 이름 b/속 파일.txt`,
CRLF 파일, 삭제된 파일, 미추적 폴더)도 8행 전부 커밋됐다.

### 훅 거부 롤백

600경로(argv 30,600자) + `pre-commit`이 `exit 1`:

```
ok=false · error="훅이 막았다"(훅 자신의 stderr가 그대로 사용자에게 온다)
git diff --cached --name-only  →  0행     ← 스테이징이 통째로 걷혔다
HEAD 제목                      →  "init"  ← 거부됐는데 커밋이 생기지 않았다
```

### stdin 전환이 새로 만든 폭탄 — 실제로 막혀 있다

빈 목록 3변형(`[]`, `[""]`, `["",""]`) 전부 `커밋할 파일이 없어요`로 되돌아오고
인덱스는 0행 그대로다. (막기 전이면 `add -A --pathspec-from-file=-`에 빈 입력은
"경로 제한 없음"이 되어 **저장소 전체가 스테이징**된다 — 빌더가 스스로 찾아 막은 자리고,
그 방어가 실제로 서 있는 것을 확인했다.)

## 2. §2-2 AI 메시지 diff — 200배가 사실이다. 다만 「무조건」이 아니다 (체크리스트 3)

### 정상 경로 (실측)

| 규모 | 갈래 | 새길 | 옛길(파일당) |
|---|---|---|---|
| 900파일(argv 51,300자) | 전 트리 | **2스폰 · 283ms** | 120파일 표본 **240스폰 · 5,702ms** → 900 환산 **1,800스폰 · 42.8초** |
| 120파일(argv 6,840자) | argv | **2스폰 · 70ms** | 240스폰 · 5,616ms |

계수기와 GIT_TRACE가 **같은 수**를 냈다(2/2, 240/240). 빌더의 «43,808ms/1,800 → 195ms/2»와
같은 크기다(내 쪽이 릴리스 빌드라 절대값만 다르다).

### 답이 갈리지 않는가 — 옛길과 1:1 대조

120파일 표본에서 `(add, del, tag, 변경 줄 전체)` **불일치 0**.
고약한 판(8행)도 옛길과 전부 동일:

- CRLF 파일 → `\r`이 양쪽 다 안 남는다(갈릴 줄 알았던 자리인데 안 갈렸다).
- 경로에 `" b/"`가 든 파일 → `diff --git a/… b/…` 좌우 가르기 성공.
- **내용 안에** `diff --git a/가짜 b/가짜` / `--- a/가짜` / `+++ b/가짜` / `@@ …`를 심은 파일
  → 파서가 안 속는다(+4 −0, 줄 내용까지 동일).
- 삭제된 파일 · 미추적 새 파일 · 안 바뀐 파일 전부 동일.

캡(파일별 24k·총량 120k)은 `aimsg.rs`에서 **한 줄도 안 바뀌었고**, `serialize_diff`는
`add`/`del` 줄만 먹는다 — 즉 ctx가 빠진 bulk 결과가 캡 로직에 들어가는 입력은 옛것과
같은 문자열이다(위의 줄 단위 대조가 그 증명이다).

### ★ 구멍 ① — 커밋이 하나도 없는 저장소(첫 커밋)에서 옛길로 통째 되돌아간다

`git diff HEAD`가 unborn HEAD에서 죽으면 **그 파일만이 아니라 배치 전부**가 `file_diff`로
내려앉는다(`git.rs` `if !r.ok { return files.iter().map(file_diff) }`).

```
300파일 · 커밋 없는 저장소 →  902 스폰(파일당 3.0) · 31,272ms
```

2,000파일이면 6,000스폰·3분대다. 사용자가 말한 "AI 메시지가 느리다"가 **첫 커밋에서는
그대로 남아 있다**. 답은 맞는다(전 행 `tag:new`) — 느릴 뿐이다.

### ★ 구멍 ② — 전 트리 diff가 32MB(`MAX_OUTPUT`)를 넘으면 같은 자리로 떨어진다

```
600파일 · 파일당 ~75KB 변경 · 전 트리 diff 45,181,800바이트
→  1,202 스폰(파일당 2.0) · 32,355ms
```

(대조: 같은 모양 400파일·30.1MB는 캡 안이라 **2스폰·394ms**. 경계가 진짜다.)

### 그래서 무엇이 틀렸나

`aimsg.rs:227` 주석은 «diff 수집 — 파일이 몇 개든 **git 스폰 1~2회**다»,
`docs/renderer-divergence.md` §6.4 표는 «스폰 수 … 전체 **1~2회**»라고 **무조건문**으로 적었다.
같은 §6.4는 폴백 단위도 틀렸다 — «unborn HEAD·32MB 초과·인용 경로(제어문자)는 **그 파일만**
옛길로 내려앉아»라고 썼는데, 앞의 둘은 **배치 전체**다(`git.rs`의 함수 rustdoc은 «git 실패(전부)»로
바르게 적어 놨다. 장부만 틀렸다). 장부는 다음 파리티 감사가 읽는 문서다.

### ★ 새로 생긴 거짓말 하나 — 미추적 **폴더** 행이 「+0 −0」으로 온다

`status --porcelain=v2`는 미추적 폴더를 **한 줄로 접는다**(`새 폴더/`). 그 행은 UI 목록에
그대로 뜨고 사용자가 고를 수 있다. 같은 목록을 두 길에 넣어 봤다:

| 길 | `새 폴더/` 행의 답 | 프롬프트에 들어가는 문장 |
|---|---|---|
| 옛길 `file_diff` | `error: "내용을 읽을 수 없어요"` | `### 새 폴더/ (diff 본문 없음: 내용을 읽을 수 없어요)` |
| 새길 `bulk_file_diffs` | `tag:"edit", add:0, del:0` | `### 새 폴더/ (+0 −0)` |

둘 다 내용은 못 준다. 그런데 새길은 **"안 바뀌었다"고 단언한다** — 폴더째 새로 만든 커밋이
모델에게는 "변경 0"으로 보인다. `bulk_file_diffs`가 `unparsed` 신호까지 만들어 가며 피하려던
바로 그 「조용한 거짓말」이 폴더 행에서 그대로 난다(`ls-files --others`는 파일만 주므로
미추적 판정에 안 걸리고, 디스크에 있으니 "안 바뀐 추적 파일"로 분류된다).
커밋 자체는 정상이다(폴더 안 파일이 다 담긴다) — 망가지는 것은 AI 메시지의 재료다.

## 4. 체크리스트 5 — A/B 증거: 형식은 복구됐고, **결론이 데이터와 반대다** (실패)

### 복구된 것 (사실)

```
tauri-m12r2     19행 · summary {attempted 19, ok 18, failed 1, 94.7%}  ← 행 재계산과 일치
electron-m12r2  19행 · summary 동일                                     ← 행 재계산과 일치
viewport:null   0행 (38행 전부 채움)
PNG             각 폴더 19장, 18장은 21:43~21:45 재촬영분
PNG 실제 픽셀   38행 중 37행이 그 행의 viewport와 정확히 일치
```

유일한 실패 행 `settings-engine-confirm`이 두 앱 **같은 문구**(`clickText: no .set-inner
button containing 정리`)로 떨어지는 것도 확인했다 — 파리티 차이가 아니라 환경(엔진 버전
1개뿐)이라는 설명은 데이터와 모순되지 않는다.

경고 가드는 **실주행으로 유발**했다. 19행 리포트를 심은 스크래치 태그에 단건 재주행:

```
$ node bench/ab.mjs tauri --tag=critr28bgit --only=settings-language,zzz-nonexistent --no-boot
[ab] 경고 — --only 2개인데 리포트는 1행(시도 1·skip 0)
[ab] 경고 — 이전 리포트 19행을 1행으로 덮어쓴다. 단건 재주행이면 --merge를 붙여라
→ 남은 리포트 1행, 그 행에 viewport [1440,900] 기록됨
```

두 줄 다 실제로 뜬다. G2·G3의 **기능**은 산다.

### ★ 실패 — 보고서가 자기가 커밋한 숫자의 반대를 적었다

`docs/parity-fix-git-r1.md:179`(같은 커밋 e47a3ee의 짝):

> `본 패스 18행    두 앱 모두 [1320, 880]   (M12 R2가 밝힌 "같은 기본 창 크기"가 값으로 남는다)`

같은 커밋의 `report.json`이 말하는 것:

| | 본 패스 창 안 17행 | `limit-hold-bar`(별도 창) | `boot-splash-native` |
|---|---|---|---|
| 3.0 (tauri) | **[1440, 900]** | [1320, 880] | [1440,900] in-window-overlay |
| 2.6.2 (electron) | **[1320, 880]** | [1320, 880] | [300,240] separate-window |

PNG 픽셀도 같다(tauri 17장 1440×900, electron 17장 1320×880). **"두 앱 모두 1320×880"은
17행에서 거짓이다.**

원인은 앱이 아니라 하네스이고, 리포트가 스스로 적어 뒀다: 본 패스는 `fixWindowSize`
(`Browser.setWindowBounds` 1440×900)를 부르는데 그 레버는 Electron에 **안 먹는다** —
`report.windowSized`가 tauri `true` / electron `false`다. 3.0의 진짜 기본 창은 1320×880이고
(하네스가 크기를 강제하지 **않는** 별도 창 화면 `limit-hold-bar`만 [1320,880]로 찍혔다),
`ab.mjs:505`의 M12 R2 주석이 이미 못을 박아 뒀다:

> 캡처 전에 크기를 **다시 강제하면 안 된다**. 강제하면 3.0만 1440×900으로 끌려가
> electron 1320×880과 어긋난다(실측: limit-hold-bar가 그렇게 어긋나 있었다).

**G3가 만든 값이 바로 그 사고를 잡아냈는데, 보고서는 "두 앱이 같다"고 적어 사고를 덮었다.**
결과는 두 겹이다.

1. 증거 장부에 거짓 문장이 커밋됐다(체크리스트 5가 묻는 «summary가 PNG·수치와 자기모순
   없는지» — 모순이다).
2. 그 문장이 가리고 있는 실제 문제: **본 패스 17행의 A/B 스크린샷 쌍은 캔버스가 서로 다르다.**
   19화면 파리티 판정의 근거 사진 대부분이 같은 자를 안 대고 찍혔다는 뜻이다.
   (부팅 패스는 M12 R2가 `settleSize`로 이미 고쳐 뒀다. 본 패스만 안 고쳐졌다.)

### 곁다리 — 실패 행의 PNG가 옛 실행분이다

`settings-engine-confirm.png`는 두 폴더 다 **17:14/17:16**(그날 낮 실행) 것이 남아 있다.
그 행은 이번에 FAIL이라 안 찍혔기 때문인데, 폴더만 열어 보면 «정리 확인 화면이 잘 찍혔다»로

## 6. 다음 라운드로 넘기는 것 (심각도 순)

1. **[치명] `docs/parity-fix-git-r1.md:179`의 viewport 문장을 데이터대로 고치고, 본 패스의
   캔버스 어긋남을 사고로 다룰 것.** 문장만 고치면 절반이다 — `ab.mjs:289`의 `fixWindowSize`가
   3.0에만 먹어 17행이 1440×900 대 1320×880으로 찍혔다는 사실을, 부팅 패스에 이미 쓴 처방
   (`settleSize`: 강제하지 말고 앱이 자기 크기를 적용할 때까지 기다렸다 찍기)으로 본 패스에도
   옮기거나, 최소한 「이 19화면 A/B는 캔버스가 달라 픽셀 비교로 못 쓴다」를 장부에 남길 것.
2. **[높음] 「스폰 1~2회」의 두 구멍.** unborn HEAD는 `git diff HEAD` 대신
   `git diff --no-index`/`ls-files -z --others` 한 번 + 디스크 읽기로 같은 답을 낼 수 있고,
   32MB 초과는 지금 조용히 43초로 떨어진다. 최소한 주석·§6.4의 무조건문을 조건문으로 고치고
   폴백 단위(**배치 전체**)를 바로잡을 것.
3. **[중간] 미추적 폴더 행(`새 폴더/`)이 `+0 −0`으로 온다.** `on_disk`가 디렉터리면
   "안 바뀐 파일"로 분류하지 말고 폴더로 다룰 것(하위 파일을 펼치거나, 최소한 옛길처럼
   "본문 없음"으로 정직하게).
4. **[낮음] 실패 행의 옛 PNG.** FAIL 행의 PNG는 지우거나 `.stale.png`로 밀어 둘 것 —
   리포트가 FAIL인데 폴더에는 성공 사진이 남는다.
5. **[낮음] 실앱 확인 숙제 유지.** 다음 정식 빌드 뒤 2,000파일 커밋을 실제 UI에서 한 번.
   지금 exe(18:09)에는 이 라운드의 Rust가 없다.
