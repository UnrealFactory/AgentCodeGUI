## 1. 재현 방법 — 무엇을 어떻게 돌렸나

```bash
cargo build -p ccg-store --features cli        # ccg-migrate.exe (HEAD와 동일 확인)
cargo test  -p ccg-store --features cli        # 13 passed
node docs/critic/tools/critic-m2-migrate.mjs   # 실홈 복사본 독립 재현
node docs/critic/tools/critic-m2-damage.mjs    # 손상 홈 15종
node docs/critic/tools/critic-m2-kill.mjs      # SIGKILL 5타이밍 + 찢어진 커밋
node docs/critic/tools/critic-m2-semantics.mjs # 왕복 의미론(별칭) 공격
node docs/critic/tools/critic-m2-tauri.mjs     # 실제 Tauri 창(플래그 on/off) + 키 포맷
node docs/critic/tools/critic-m2-api.mjs       # api-config 양방향 · api-usage
```

안전 규약 준수: 사용자 실홈(`~/.agentcodegui`)은 **읽기/복사만** 했다(`cloneReal()`).
모든 대상은 `%TEMP%/ccg-critic-m2-*`. 앱은 격리 `CCG_HOME`으로만 띄웠고
(`.instance-lock`이 홈별이라 사용자 실앱과 충돌하지 않는다 — `main.rs:16-34`),
종료는 **내가 스폰한 PID만** `killTree(pid)`.

Tauri 스모크는 `target/release/agentcodegui.exe`(01:18 빌드, `CCG_UNIFIED_STORE`·`chats-v3`
문자열 포함 확인)를 `%TEMP%`로 복사해 썼다 — 다른 크리틱이 중간에 재빌드해도 흔들리지 않게.

| 빌더 주장 | 크리틱 독립 재현 |

| prune 정밀도 | 재현. 본채팅 하나만 지운 페이로드 → 정확히 그 하나만 사라짐 |

### 2.2 반박

| 빌더 주장 | 실측 |
|---|---|
| §4 *"쓰기는 DPAPI 직접 … **2.6.2도 그대로 읽는다**(되돌려도 키가 안 죽는다)"* | **거짓.** Electron 42.3.2 `safeStorage.decryptString`이 던진다: *"Ciphertext does not appear to be encrypted."* Chromium `DecryptString`의 DPAPI 폴백에 **닿기 전에** Electron이 `v10` 접두사를 검사해 거부한다 → **D6** |
| §6-4 *"플래그를 켜면 추가 채팅 창은 여전히 옛 `session-chats/`를 읽는다 = 두 살림"* | **거짓.** `src-tauri` 전체에 `session-chats` 참조가 **0건**이다. `session-wins:hydrate/persist/rename`는 `ch::` 상수조차 없어 `__unimplemented`로 떨어진다. 두 살림이 아니라 **살림이 없다** — 실제 결과는 §3.4-6의 도달 불가 → **D7** |
| §3.2-5 *"멱등성 5→5 / 311→311"* | 개수는 맞지만 **내용은 덮인다.** 재실행이 3.0에서 바뀐 제목·추가된 메시지를 2.6.2 시점 값으로 되돌린다 → **D3** |

### 2.3 미검증으로 남긴 것

- `chat:status` 브로드캐스트·`chat:*` 실행 채널: 구현이 없어 검증 대상이 아니다(보고서와 동일).
- 2차 정체성의 **부하 픽스처** 전건 미수행: 재현했고 사유(합성 홈에 계정·키 없음)도 같다.
  실물 엔진으로 돌려도 같은 결론이라 별도 결함으로 세지 않았다.

## 3. 공격 결과

### 3.1 손상 홈 15종 (`critic-m2-damage.mjs` → `m2-r1-damage.json`)

판정: `preserved`(보존) / `reported-drop`(사라졌지만 warnings에 남음) / `silent-*`(조용) / `crash`.

| # | 손상 | 판정 | 실측 |
|---|---|---|---|
| 1 | 채팅 파일 60%에서 잘림 | **silent-skip** | 그 대화만 사라지고 `warnings: []` |
| 2 | `chats/index.json` 잘림 | **silent-drop** | **본채팅 3개 전부** 미이관, warnings 0, exit 0 |
| 3 | UTF-8 아닌 바이트 삽입 | **silent-skip** | 동상 |
| 4 | 순환 `btwOf`(A↔B·자기 자신) | preserved | 무한루프 없음, 간선 그대로 |
| 5 | 32 MB 첨부 | preserved | 645 ms, 크래시 없음 |
| 6 | 중복 chatId(본채팅↔추가 채팅) | preserved **+ 그래프 오배선** | `id_collision` 경고는 뜨지만 `hold`가 `c-aaa`가 아니라 **`sc-c-aaa`** 로, `btwOf`도 `sc-c-aaa`로 간다 → **D10** |
| 7 | 존재하지 않는 세션 참조 | preserved | `btw_orphan` 경고로 정직하게 drop |
| 8 | 인덱스에 없는 채팅 파일 | **silent-drop** | 파일은 디스크에 있는데 이관 0, 경고 0 |
| 9 | 경로 탈출 id | preserved | 홈 밖 파일 생성 없음 |
| 10 | 1000단 중첩 JSON | **silent-drop** | serde 재귀 한도(128) → 파싱 실패 → 조용히 스킵. **2.6.2(JS)는 읽을 수 있는 파일** |
| 11 | 본채팅 id = `ma-<sid>-<i>` | **silent-drop** | 패널이 같은 파일을 덮어써 본채팅 대화 소멸 + `index.order`에 **중복 id** → **D11** |
| 12 | ui-prefs/mcp/skills 파싱 실패 | preserved | 크래시 없음(기본값) |
| 13 | `api.mode=true` + 채팅별 계정 | **silent-leaf-drop** | `me@example.com`·`sub@example.com`이 레코드 어디에도 없다 → **D5** |
| 14 | ui-prefs 꼬리 잘림(api.mode=true였음) | **silent-value-flip** | 전 채팅이 `subscription`·`outputStyle:null`로 **굳는다**. 경고 0 → **D14** |
| 15 | chat-talk id 중복 | preserved + 오배선 | `btwOf` → `talk-c-aaa`(D10과 같은 뿌리) |

`crash` 0건은 좋다. 문제는 **8/15가 조용하다**는 것이다. §5.2가 *"조용한 값 보정이 가장
위험한 마이그레이션 버그"*라고 못 박았는데, 지금 마이그레이터는 **값**은 안 고치면서
**레코드는 조용히 버린다.**

### 3.2 SIGKILL — 5개 타이밍 (`critic-m2-kill.mjs` → `m2-r1-kill.json`)

부하 홈(200채팅 / 20세션×6패널 / 추가 30 = 350채팅·17400메시지), 완주 1475 ms.

| 타이밍 | killed | 옛 3디렉터리 | chats-v3 | 잔여물 | 재실행 |
|---|---|---|---|---|---|
| 221 ms (15%) | ✔ | 바이트 동일 | absent | 0 | ok 350/350 |
| 811 ms (55%) | ✔ | 바이트 동일 | absent | 0 | ok 350/350 |
| 1357 ms (92%) | ✔ | 바이트 동일 | absent | 1(스테이징) | ok 350/350 |
| 스테이징 관측 kill(파일 22개 시점) | ✔ | 바이트 동일 | 없음 | 2 | ok 350/350 |
| 스테이징 관측 kill(파일 233개 시점) | ✔ | 바이트 동일 | 없음 | 2 | ok 350/350 |

비율 기반 kill로는 스테이징 창을 못 맞춘다(읽기·빌드가 ~1.3 s, 스테이징 쓰기+커밋이
마지막 ~100 ms)는 것도 실측했다 — 그래서 **스테이징 디렉터리를 관측해서** 죽이는 경로를
따로 만들었다. 그 창에서도 결과는 같다. **크래시 내성은 진짜다.**

찢어진 커밋만 예외다(**D8**): 커밋이 rename **둘**(`chats-v3`, `boards`)이라 그 사이/또는
`boards` 커밋 실패 시 `chats-v3`만 제자리에 앉는다. 그 상태를 만들어 재현한 결과 —

```
is_migrated() = true (다시는 마이그레이션 안 한다)
board:get = null · ma:get = null
light 조회: 350개 중 349개가 마커(보드가 없어 visible_chat_ids()가 빈 목록)
손으로 다시 돌리면 복구됨
```

저장 경로 중간 kill도 봤다: 350파일 저장(465 ms)을 256 ms에 죽였을 때 **150개만 적용**,
손상·소실 **0**, `chat-0150.json.tmp` 1개가 남는다(누구도 안 지운다 — prune은 `*.json`만 본다).

### D1 (치명) — 별칭 계층이 런타임 정체성을 **매 저장마다** 되돌린다 (P3 재발)

`legacy_bridge.rs:46-59 absorb_legacy()`는 페이로드에 옛 필드가 있으면 **무조건**
`set_owned_mem(id, "identity", raw)`로 런타임 진실을 갈아엎는다. 보고서 §5.1은 이걸
"과도기 예외(별칭이 유일한 저자)"로 선언했지만, 예외에 **가드가 없다**:

- 옛 렌더러는 초안 한 글자에도 디바운스 저장을 날린다 → 그 페이로드의 `picker`는
  **읽어간 시점의 사본**이다. 게다가 그 이펙트의 의존성에 `state`가 있어
  (`App.tsx:607-637`, deps `[…, state, manualCwd, refDirs, picker, …]`) **스트리밍 토큰마다
  재무장**한다 — 즉 저장은 턴 **중에** 600 ms 간격으로 계속 도착하고, 활성 채팅의 `picker`는
  렌더러의 라이브 상태에서 온다. 폴백이 일어나는 바로 그 구간이다.
- M3의 폴백이 턴 중에 `set_owned("identity")`를 하면, 뒤이어 도착하는 그 저장이
  폴백 이전 값으로 되돌린다(실측 §3.3 B2·B3).
- 다음 send는 `IdentityChanged` 재스폰 — m-logic §1 P3가 "죽었다"고 선언한 병리 그대로다.

지금은 `chat:identity-set`도 폴백도 없어 **무해**하다. M3가 붙는 순간 켜진다.

```rust
// legacy_bridge.rs — 제안: "렌더러가 실제로 바꾼 것"만 저자로 인정한다
static PROJECTED: Mutex<HashMap<String, Value>> = Mutex::new(HashMap::new());

fn legacy_subset(o: &Map<String, Value>) -> Value { /* picker·manualCwd·cwd·refDirs·api만 */ }

fn with_legacy(chat: Value, source: Source) -> Value {
    // …되그린 뒤…
    PROJECTED.lock().insert(id, legacy_subset(&o));   // 우리가 내보낸 모양을 기억한다
}

fn absorb_legacy(chat: &Value, source: Source, g: &Globals) -> Value {
    if has_legacy {
        let incoming = legacy_subset(&o);
        let echo = PROJECTED.lock().get(id) == Some(&incoming);   // 우리가 준 걸 그대로 돌려준 것
        if !echo { crate::chats_v3::set_owned_mem(id, "identity", raw.clone()); }
        // echo면 identity는 손대지 않는다 → §4.1의 "Rust 값이 이긴다"가 그대로 산다
    }
}
```

이건 새 발명이 아니다 — 스냅샷 마커가 "렌더러가 안 들고 있는 것"과 "지운 것"을 가르는 규약과
**같은 종류의 판별**이다.

### D2 (치명) — `chats-v3/index.json` 한 바이트가 깨지면 다음 저장 한 번이 **전 대화 파일을 지운다**

```rust
if index_ok && !items.is_empty() {

// read_all도 index가 깨졌을 때 디렉터리 전수 스캔으로 폴백하면(순서는 파일명) 조회 전멸도 사라진다
```

### D3 (치명) — 재마이그레이션이 3.0에서 쌓은 대화를 2.6.2 시점으로 덮는다

`migrate()`는 소스 레코드로 `<id>.json`을 **덮어쓴다**. id를 유지하는 일반 채팅과 결정론
id를 쓰는 패널은 전부 여기 걸린다(`carried`는 *새로 생긴* id만 살린다).

실측: 마이그레이션 후 그 채팅에 메시지 1개 추가 + 제목 변경 → 재실행 →
`title:""`·`messages:0`으로 **되돌아감**(`m2-r1-migrate.json.remigrationClobber`).

스펙 §4.1은 이 경로를 **사용자에게 권하는 카드**로 설계해 뒀다:
*"2.6.2에서 만든 대화가 있어요 — 다시 가져올까요? → 재마이그레이션(멱등)"*.
그 카드는 아직 구현되지 않았고(코드에 `migratedAt` mtime 비교 없음 — 보고서 "남은 것"에도

(그리고 §5.3-5 멱등 검사는 **id 집합**이 아니라 **내용 해시**로 판정해야 한다.)

### D5 (높음) — "무손실"이 아니다: `api.mode=true`면 **채팅별 계정이 전부 사라진다**

### D6 (높음) — 3.0이 쓴 API 키를 2.6.2가 못 읽는다 (보고서 §4 주장 반증)

원인: Electron `safeStorage.decryptString`이 OSCrypt에 넘기기 **전에** `v10`/`v11` 접두사를
검사한다. 3.0의 `encrypt()`는 DPAPI 직접이라 접두사가 없다(`safe_storage.rs:150-153`).

```rust
// safe_storage.rs — Local State 키가 있으면 v10으로 쓴다(2.6.2가 읽는 유일한 모양)
pub fn encrypt(plain: &str) -> Option<String> {
    if let Some(key) = os_crypt_key() {
        let nonce: [u8; 12] = random_nonce();
        let ct = Aes256Gcm::new_from_slice(&key).ok()?.encrypt(Nonce::from_slice(&nonce), plain.as_bytes()).ok()?;
        let mut blob = V10.to_vec(); blob.extend_from_slice(&nonce); blob.extend_from_slice(&ct);
        return Some(b64_encode(&blob));
    }
    Some(b64_encode(&dpapi_protect(plain.as_bytes())?))   // 폴백(2.6.2 미설치 환경)
}
```
`aes-gcm`은 이미 의존성에 있고 키 읽기도 이미 있다. 폴백 갈래는 남기되
**"2.6.2가 없던 환경에서 쓴 키는 되돌리면 다시 넣어야 한다"**를 문서에 적으면 정직해진다.

### D12 (중간) — 얼려둔 `status`의 유일 진실이 "캐시"인 파일이다

§4.3 규약 3·5는 `status.json`을 **파생 캐시**라 부르고 깨지면 얕은 스캔으로 재구성한다고

그리고 `build_chat()`은 추가 채팅의 `status`를 **레코드에 안 넣는다**(status.json에만).

2.6.2는 그 값을 `session-chats/<id>.json`에 들고 있었다 = **회귀**.
→ `build_chat`이 `status`를 레코드에도 남기고 `ChatLite`에 필드 하나 추가(비용 0에 가깝다).

### D13 (중간) — 낡은 `chats:save`가 `chats:set-active`를 덮는다

`write_chats`는 페이로드의 `activeChatId`를 무조건 인덱스에 쓴다(`chats_v3.rs:153-156`).
§6.2 U3이 `chats:set-active`를 만든 이유가 **바로 이 덮어쓰기**인데, 반대 방향 가드가 없다.

보고서는 "2.6.2와 같은 동작"이라고 적었지만, 2.6.2엔 `set-active`가 없었고 라우팅도 없었다.
→ 단조 카운터 하나로: `set_active`가 올린 세대보다 낡은 저장은 `activeChatId`를 무시.

### D15 (낮음) — 종료 flush가 배선되지 않았다

`ccg_store::status::flush()`를 부르는 곳은 `ccg_migrate.rs`뿐이다(`src-tauri` 0건).

무해하지만, §4.3 규약 2의 "500 ms 디바운스 **+ 앱 종료 flush**"는 절반만 있다.
보고서 "남은 것"에 없다 → 목록에 추가돼야 한다.

### D16 (낮음) — 대화가 증발하는 코드에 `cargo test`가 하나도 없다

13개 테스트는 매핑표(5)·base64/DPAPI(2)·얕은 뷰(2)·마이그레이션 술어(3)·지문(1)이다.
`chats_v3.rs` · `legacy_bridge.rs` · `fanout.rs` · `boards.rs` = **0**.
마커 병합·소유 되끼움·prune 칸막이는 전부 손으로 돌리는 JS 하네스에만 있다.
M3는 재생 하네스를 `cargo test`로 만들었다(`1d8df4d`) — 같은 기준을 여기에도.
(내 공격 중 A·B1·B2·C1~C5는 그대로 `#[test]`가 된다 — 홈은 `tempdir` + `CCG_HOME`.)

### D17 (낮음) — 두 크레이트가 같은 값의 바이트 모양을 다르게 쓴다

`api_key` 변형: ccg-store는 `{"kind":"api_key"}`, `ccg-engine`의 serde는
`{"kind":"api_key","account":null,"dropEnvKey":null}`. 1차 비교 키가 "정준 직렬화 **바이트**"인
이상 생산자는 하나여야 한다. M-LOGIC이 `to_raw()`로 저장을 시작하는 순간 전 채팅 파일이
한 번 다시 쓰이고(내용 비교가 다르다고 판정), 그 시점의 1차 비교는 거짓 불일치가 된다.
→ `RawBilling`에 `skip_serializing_if = "Option::is_none"` 또는 ccg-store가 항상 채우기.

## 5. `origin` 필드 판정 (스펙 §4.1 목록 밖 추가 필드)

**판정: 필요악 — 이번 라운드 유지, 단 3줄 수정 + 스펙 갱신 요청. 대안은 있고, 그 대안이 더 낫다.**

### 필요는 진짜다
얼려 둔 2.6.2 렌더러가 목록을 셋으로 나눠 들고 있는 한, "페이로드에 없다 = 지운 것"이라는
2.6.2 prune 규약을 그대로 쓰면 본채팅 저장 한 번이 패널·추가 채팅을 지운다. 무언가로
**칸을 막아야 한다**. C1·C2 실측은 지금 구현이 그 일을 해내고 있음을 보여준다.

### 그런데 지금 모양은 두 구멍을 만든다
- 기본값이 `chat`이다 → `origin` 없는 레코드는 **본채팅 목록으로 새고**(C3b), **낡은 저장에
  삭제된다**(C3c). 코어 `write_chats`가 `origin`을 안 찍으므로 M-LOGIC이 만드는 채팅이 곧
  그 상태다. 즉 이 필드는 **모든 미래 저자가 지켜야 하는 암묵 규약**을 하나 늘렸다.
- 스펙 §4.1 필드 목록 밖이라, 다른 라운드 작업자가 이 규약을 모른 채 레코드를 쓴다.

### 더 나은 대안(다음 라운드 권고)
**칸을 레코드에 새기지 말고, 별칭 계층이 "내가 넘겨준 id 집합"을 들고 있는다.**

```
prune 허용 범위 = (이 채널이 마지막 get에서 넘겨준 id) ∩ (그 뒤 이 채널이 만든 id)
```
- 파일에 새 필드가 없다 → 마이그레이션·역호환·미래 저자 문제가 통째로 사라진다.
- **C3c도 같이 닫힌다**: Rust가 만든 채팅은 그 렌더러에게 넘어간 적이 없으므로 삭제 후보가
  아니다. `origin`으로는 못 닫는 구멍이다.
- 패널 칸은 이미 `boards/*.slots`에서 파생할 수 있다(`ma_save`의 `live_panels`가 그 절반).
- 비용: 별칭 계층에 `HashMap<채널, HashSet<id>>` 하나. D1의 `PROJECTED` 맵과 같은 자리다.

### 이번 라운드에 지금 해야 할 최소치
```rust
// 1) 기본값을 "모른다"로 — 모르는 칸은 **아무도 못 지우고** 옛 목록에도 안 낀다
fn origin_of(chat: &Value) -> &str { chat.get("origin").and_then(Value::as_str).unwrap_or(ORIGIN_UNKNOWN) }
//    chats_get: origin == ORIGIN_CHAT 만 노출(변화 없음)
//    chats_save/ma_save: origin != 내 칸 → 무조건 보존(unknown 포함)
// 2) 코어 write_chats가 새 레코드에 origin을 찍는다(없으면 'chat'이 아니라 실제 생성 주체)
// 3) ux-chat-unify §4.1 필드 목록에 origin을 **수명(별칭 계층과 함께 소멸) 명시**로 추가
```
→ **스펙 갱신 요청감이 맞다.** 스토어 파일 포맷은 여러 라운드가 공유하는 계약면이고,
"보고서에만 적힌 필드"는 다음 사람이 밟는다(D9가 그 증거다).

## 6. 남은 것 7건 재평가 — 다음 라운드 계획으로 충분한가

| # | 보고서 항목 | 크리틱 판정 |
|---|---|---|
| 1 | `chat:*` 13채널 이름만 | 타당. M-LOGIC 소관 |
| 2 | `win:chat-*` 4개 이름만 | 타당 |
| 3 | `chat:status` 브로드캐스트 없음 | 타당. **추가**: 그래서 `status::set`도 안 불리고 종료 flush도 없다(D15) |
| 4 | `session-wins:*` 별칭 미구현 = "두 살림" | **서술 오류(D7).** 실제는 *hydrate/persist/rename에 핸들러가 아예 없다* → 3.0에서 추가 채팅은 **영속되지 않고**, 마이그레이션된 사본은 **UI에서 도달 불가**. 위험도는 "두 살림"보다 **낮지만(이중 쓰기 없음) 더 눈에 띈다**(대화가 사라진 것처럼 보인다) |
| 5 | 2차 키가 진짜 `RunIdentity::hash()`가 아니다 | **실홈에 한해 해소.** 실물 엔진으로 돌려 5/5 정규화 성공·해시 산출·역직렬화 무손실 확인(`m2-r1-identity.json`). 하네스에 붙이는 일만 남았다 |
| 6 | 실제 Tauri 창 미검증 | **해소.** §3.4 — 플래그 on/off 둘 다 실측 |
| 7 | `origin` + 리포트 경로가 스펙과 다름 | §5 판정. 리포트 경로(`docs/poc-out/`)는 스펙(`docs/design/poc-out/`)과 다르지만 무해 — **스펙을 실제 경로로 고치면 끝** |

### "session-wins 별칭 부재 때문에 기본값을 못 켠다"는 진단은 **부정확하고 불충분하다**

플래그를 오늘 기본으로 켜면 실제로 터지는 것은 다섯이고, session-wins는 그중 하나일 뿐이다:

1. **추가 채팅이 화면에서 사라진다**(D7) — 사용자 눈에는 대화 증발과 구분되지 않는다.
2. **API 키를 3.0에서 한 번이라도 넣으면 2.6.2로 못 돌아간다**(D6) — 롤백 경로가 부분적으로 끊긴다.
3. **index.json 손상 = 전멸**(D2) — 유일 사본이 된 뒤라 옛 디렉터리가 못 구한다.
4. **재마이그레이션 카드를 붙이는 순간 데이터 파괴**(D3).
5. **M3 폴백이 붙는 순간 P3 재발**(D1).

즉 다음 라운드 계획은 "session-wins 별칭 + 상태기계"로는 부족하다. **기본값 승격 게이트**를
따로 세워야 한다:

```
기본값 ON 게이트 (전부 통과해야):
  □ D1 가드(별칭 저자 에코 판별)        □ D2 prune 안전판
  □ D3 재마이그레이션 보존 규칙          □ D6 v10 쓰기
  □ session-wins 별칭 + 추가 채팅 도달성  □ D12 status 회귀 복구
  □ 위 전부를 잠그는 cargo test(D16)
```

## 7. 가장 큰 격차 하나

**검증 게이트가 마이그레이터와 같은 눈을 쓴다.**

`poc-chat-unify-migrate.mjs`는

- before 인벤토리를 **`index.order`를 통해** 만든다(`fanout()` — `migrate_v3::read_fanout`과 같은 규칙),
- 정체성을 **자기 매핑 미러**로 만들어 디스크의 매핑 결과와 비교하고,
- 멱등을 **id 집합**으로 판정한다.

그래서 "무손실 전 항목 통과"는 사실 **"마이그레이터가 본 것에 한해 무손실"**이다.
이 맹점이 실제로 가린 것:

| 가린 결함 | 하네스가 못 본 이유 |
|---|---|
| D4 조용한 드랍(인덱스 밖 파일·손상 파일) | before가 인덱스를 통해 세므로 **양쪽에서 동시에 사라진다** |
| D5 계정 소실 | before/after 둘 다 같은 매핑을 통과한 값이라 **바이트가 같다** |
| D3 재마이그레이션 덮어쓰기 | 멱등을 **개수·id**로만 판정 |

내 하네스는 같은 홈에서 같은 마이그레이터를 돌리고도 이 셋을 전부 잡았다. 차이는 60줄이다:
**(a) 인벤토리를 디스크 파일에서 만들고, (b) 원본 레코드의 리프가 목적지에서 되찾아지는지
전수 감사하고, (c) 멱등을 내용 해시로 본다.**

게이트가 스스로를 검사하면 통과는 신호가 아니다. 다음 라운드에서 §5.2 인벤토리 규칙에
**"before는 인덱스가 아니라 디렉터리에서 만든다"** 한 줄을 넣는 것이 이 라운드에서 얻을
가장 큰 이득이다.
