## 2. 커버리지 게이트 공격 — 가장 큰 격차

### 2.1 과대선언은 정말 못 한다 (주장 성립)

`S1.covers`에 밟지 않는 `T3`·`F5`를 심었다.

```
s01_account_change_midturn_coldstart ... FAILED
[#1 …] covers 선언은 했는데 안 밟은 전이: ["T3", "F5"]
```

`harness/mod.rs:664 check_covers`가 `Sim::finish()`에서 런타임 `fired` 집합과 대조한다. **여기까지는 정직하다.**

### 2.2 그러나 게이트의 만점은 선언만 센다

`s25_spawn_timeout`의 `#[test]`만 떼고 레지스트리의 `S25`는 그대로 뒀다. T3를 밟는 테스트는 이제 **0개**다.

```
─ 프레임 커버리지 ............ 전이 60/60 밟음
─ 안 밟은 전이 ............... []
frame_coverage: 3 passed · replay_standing: 31 passed · 전체 초록
```

**원인**: `frame_coverage.rs:52`의 `covered`는 `declared()`(정적 레지스트리)에서 나온다. 그리고
`frame_coverage.rs`는 시나리오를 실행하는 `replay.rs`·`replay_standing.rs`와 **다른 테스트
바이너리**라 런타임 `fired`를 원리적으로 볼 수 없다.

설계 §3.7은 *"시나리오 최소 1개가 그 전이를 밟는지 검사한다. 안 밟는 전이가 있으면 빌드 실패"*를
요구한다. 게이트가 막겠다고 선언한 **"표에는 있는데 테스트가 없는 줄"이 구조적으로 만들어진다.**

> 곁가지: `frame_coverage.rs:7-9`의 *"지금은 그 조건을 아직 못 채운다 → 베이스라인만 박는다"*는
> 주석은 **stale**이다. `covered >= 60` ∧ `all.len() == 60`이므로 현재는 사실상 엄격 게이트다.
> 약한 건 베이스라인이 아니라 **입력이 선언이라는 점**이다.

### 2.3 `kills`·`synth`는 아예 무검증

`check_covers`는 `covers`만 본다. `kills`(병리 15/15)와 `synth`(합성 33 / assumed 1)는 **집계만**
되고 대조되지 않는다. 실제로 귀속이 뒤집혀 있다:

| | 선언 | 실제 |
|---|---|---|
| `S4` | `synth: ["rate-limit-blocked(assumed)"]` | `f_result_err(문구 분류)` — **assumed 픽스처를 안 쓴다** |
| `S4C` | `synth: []` | `synth("rate-limit-blocked")` — **쓴다** (`replay.rs:477`) |

합계(assumed 의존 1건)는 우연히 맞고 귀속은 반대다. 보고서 §2.4의 *"#4c가 의존"*은 행동상
맞지만, §2.3의 기계 집계는 그 사실이 아니라 S4의 잘못된 선언에서 나온 숫자다.

### 3.2 leaf_paths 14 vs 15 — 빌더 주장 CONFIRMED

## 4. 재생 spot-check — 어려운 8개

`#2c`·`#2d-i/ii`·`#4`·`#5a`·`#5b`·`#6c-i/ii/iii`·`#8b`는 **서술과 단언이 일치**한다. 특히
`#2c`는 `model=="opus" ∧ effort==High` 두 줄로 N2를 실제로 잠그고, `#4`는 `spawns==3` ∧
`T16 정확히 1회` ∧ `texts == ["1","이어서 진행해 주세요","2","3"]`로 §3.4-a를 진짜로 잠근다.
`#8b`는 `stream_closed:appquit` 사유를 문자열로 확인한다. 이름만 있는 테스트는 없었다.

### 4.1 ❌ `#4c` — 단언이 약하고, 약한 자리에 실제로 반증이 숨어 있다

```rust
assert!(sent_after <= 3, "★ R1 설계였다면 중지 뒤에도 큐가 혼자 나갔다(L1의 최악 형태)");
```

경계를 조여 실제 값을 뽑았다: **`sent_after == 2`**, `texts == ["1", "2"]`.

즉 **되돌리기로 큐를 복원한 뒤 사용자가 대기표를 끄면(`HoldCancel`) 큐 head "2"가 그 자리에서
자동 전송된다.** 그런데

- 테스트 주석(`replay.rs:514`)은 *"hold가 꺼졌으니 큐는 사용자가 다시 보낼 때까지 **가만히 있는다**"*
- 보고서 §2.1 #4c는 *"**몇 시간 뒤 자동 전송 0건**"*
- Scen 이름은 *"#4c hold 중 interrupt — 몇 시간 뒤 혼자 보내지 않는다"*

셋 다 SUT와 반대다. `<= 3`이 정확히 이 2건을 통과시킨다. 그리고 `advance_to(60분)` 뒤 추가
전송이 0인 진짜 이유는 hold 의미론이 아니라 **바로 앞의 `StopAll`이 큐를 비웠기 때문**이다 —
시나리오가 잠근다고 말하는 성질을 실제로는 잠그지 않는다.

이건 테스트 강도 문제만이 아니라 **제품 의미론 질문**이다. 사용자 동선은
`Esc → 되돌리기 → "자동 이어서 끄기"`인데 마지막 클릭이 곧바로 전송을 유발한다.

**제안**: 먼저 의미론을 확정하라. `hold.cancel`이 "자동 이어서 포기"라면 드레인을 유발하면 안 된다.

```rust
// runtime.rs — HoldCancel 은 게이트만 내리고 드레인을 깨우지 않는다
Cmd::HoldCancel => { self.hold = None; self.emit(…); /* drain_if_possible() 호출 안 함 */ }
```
```rust
// replay.rs — 어느 쪽으로 확정하든 값을 **정확히** 박는다
assert_eq!(sent_after, 1, "hold를 꺼도 큐는 사용자가 다시 보낼 때까지 가만히 있는다");
```

### 5.3 job object 실증 ✅ (빌더 미실시)

```
홀더 28972 → claude.exe 3828 → conhost.exe 15332 · bash.exe 21448
taskkill /F /PID 28972      ← 홀더만. /T 없음 = Rust Drop 이 안 돈다
4초 후: 28972 dead · 3828 dead · 15332 dead · 21448 dead
사용자 실앱 2976·26940 : 무사   |   잔존 ping.exe : 0
```

`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`가 **손자까지 실제로 거둔다.** 보고서가 단언만 하고
검증하지 않았던 안전 주장이 이제 실증됐다.

### 5.4 O17 능동 프로브 ✅ **닫혔다 — 긍정** (빌더가 미확인으로 남긴 항목)

먼저 내 오판을 적는다: 프로브 응답(`control_response{probe-1}`) 페이로드에는 **살아 있는 셸이
원장에 있어도** `background_tasks`가 없다. 나는 이걸 O17 실패로 읽었다. 틀렸다 — 코드는 응답
페이로드를 읽지 않는다(`runtime.rs:1458` *"응답 자체는 신호가 아니다 — 뒤따르는 REPLACE가
판정한다"*). 판정은 `f13_replace`(`:1846-1872`)에서 일어난다.

그래서 **REPLACE가 정말 따라오는지**를 양방향으로 쟀다(bypass 모드 + 실제 백그라운드 `ping`):

| 프로브 | 원장 셸 | 응답 REPLACE | 지연 | 의미 |
|---|---|---|---|---|
| probe-1 | **살아 있음** | `["bmu7qit88"]` | **33ms** | 항목 존재 → `rearm(ActiveProbe)` → Alive |
| probe-2 | **끝난 뒤** | `[]` | **35ms** | 항목 부재 → **T21b** `watchdog:active` 정착 |

REPLACE 이력 `[[bmu7qit88], [bmu7qit88], [], []]` — 프로브마다 정확히 하나가 따라온다(3s
타임아웃 대비 100배 여유).

**결론**: ⑥·T21b·`#6c-ii`·`#6c-iii`·`#7b′`·*"30분이 아니라 ~93초"*가 전부 **실물 근거를 얻었다.**
`FakeCli.probe_reply`는 실제 동작을 올바르게 모형화한다. 보고서 §4가 *"⑥이 실패하면 되돌릴
대상"*으로 특정해 둔 4건은 **되돌릴 필요 없다.**

> 곁가지 관측: 재전송 `initialize` 응답은 최초 응답에 없던
> `pending_permission_requests` · `pending_user_dialog_requests`를 추가로 싣는다.
> 부팅/재접속 시 열린 카드 재동기화에 쓸 수 있는 자리다(설계에 없는 공짜 재료).

## 7. M-WF `effort` — 독립 추출로 확인 ✅

`docs/critic/tools/critic-m3-wfkeys.mjs`. `type:"workflow_agent"`를 품은 객체 리터럴을
**중괄호 균형으로 잘라 최상위 키만** 집계했다(빌더와 독립적인 방법).

```
type:"workflow_agent" 사이트 = 6        (보고서: emitter 6개 — 일치)
최상위 키 합집합 = 24
  effort 계열 = []           → hasEffort = false
  fallbackModel = true · model = true
emitter 본문에 'effort' 문자열 = 0건
```

키: `agentId · agentType · attempt · blocked · cached · error · fallbackModel · index · isolation ·
label · lastAttemptReason · lastProgressAt · lastToolName · lastToolSummary · model · phaseIndex ·
phaseTitle · promptPreview · queuedAt · remoteSessionId · resultPreview · startedAt · state · type`

**방법론 주의(중요)**: 넓은 창(±수천 바이트)으로 1차 추출했을 때는 `effort = true`가 나왔다.
전부 이웃한 **에이전트 정의** 코드였다 — `Rne(we?.effort)` · `bashCommandClamp` ·
`String(ot.effort??xA(W)??"")`(캐시 키). 즉 **effort는 입력 쪽에만 있고 emitter에는 없다.**
빌더의 부정 주장은 더 엄격한 방법에서도 살아남는다.

보강 확인(원문 대조):

- `"Active effort level for the current turn (e.g., \"low\", \"medium\", \"high\", \"xhigh\", \"max\"),
  after any silent downgrade for the selected model. Also exposed to hook commands and Bash as the
  CLAUDE_EFFORT env var."` — 존재
- `"Reasoning effort applied to the current turn."` — **턴 단위** 값임을 명시.
  빌더의 *"세션 effort를 에이전트 칩에 붙이면 화면이 거짓을 말한다"* 경고를 뒷받침한다.
- `CLAUDE_EFFORT` 3회 · `StatusLineCommandInput` 2회.

**사용자 보고용 결론**: 워크플로 에이전트별 effort는 **와이어에 실려 오지 않는다.** 정직한
선택지는 `model`(+재시도 시 `fallbackModel`) 칩뿐이다. 보고서 §5는 그대로 채택할 만하다.

> 사소한 차이: 보고서 키 목록은 `type`을 빼고 `message`를 넣었다(24 vs 24). effort 판정과 무관.

## 8. mtime 프로브 — 위험도는 빌더 자평보다 **낮다**

`ClaudeDriver`가 `mtime_fresh`를 오버라이드하지 않아 트레이트 기본값 `false`를 쓴다 —
사실 확인. 빌더는 *"지금 상태로 출하하면 조용한 dev 서버는 ⑥에만 의존한다"*고 경고했다.

**§5.4에서 ⑥이 실물에서 동작함이 증명됐으므로 "⑥에만 의존"은 안전한 의존이다.** 실제 비용은:

1. 30s마다 프로브 왕복 1회 추가 — 실측 33~35ms. 무시할 만하다.
2. CLI가 **무응답**이면 ④도 ⑥도 못 답해 30분 하드리밋까지 간다. 그런데 그 방향은
   **보수적**이다(살아 있는 셸을 안 죽인다).

즉 **오탐 사망 위험이 아니라 지연 비용**이다. 출하 차단 사유가 아니다. 다만
`s07e`는 `FakeCli.mtime_fresh_ids`를 직접 심어 `probe_count == 0`을 단언한다 — 출하 경로에서는
`probe_count == 1`이 된다. **존재하지 않는 성질을 잠그고 있는 테스트**이므로, ④를 구현하기
전까지는 그 단언을 `probe_count <= 1`로 낮추거나 테스트에 `#[ignore = "④ 미구현"]`을 달아
정직하게 두는 편이 낫다.

## 10. 가장 큰 격차 1개

> **커버리지 게이트의 "선언은 거짓말을 못 한다"가 절반만 참이고, 보고서의 모든 헤드라인
> 수치(전이 60/60 · 병리 15/15 · 합성 33/assumed 1)가 그 절반 위에 서 있다.**

과대선언은 못 한다 — 그건 진짜다. 그러나 게이트가 만점을 계산하는 입력은 **정적 레지스트리**이고,
게이트는 시나리오를 실행하는 바이너리와 **분리돼 있어** 실적을 볼 수 없다. `#[test]` 한 줄만
지우면 그 전이의 테스트가 0개가 되어도 게이트는 60/60을 외치고 CI는 초록이다. 설계 §3.7이
*"안 밟는 전이가 있으면 빌드 실패"*로 막으려던 바로 그 실패 모드가 구조적으로 가능하다.
그리고 `kills`·`synth`는 그 절반의 보호조차 없다 — 실제로 `S4`↔`S4C`의 귀속이 뒤집힌 채
초록이었고, 아무도 몰랐다.

C2(함정 A 미잠금)와 C3(#4c의 거짓 주장)는 **이 격차의 증상**이다. 둘 다 "선언·이름·주석은
그렇게 말하는데 기계는 확인하지 않는" 같은 형태다. 게이트가 실적을 세도록 바꾸면 이 계열
결함은 다음 라운드부터 스스로 드러난다.

**공정하게 덧붙이면**: 이 엔진은 크리틱이 실물로 때린 항목 — 소프트 중단·job object·능동
프로브 O17·M-WF effort — 에서 **전부 통과했다.** 특히 빌더가 최대 미확인 위험으로 남긴 O17이
양방향으로 닫혔다는 것이 이번 라운드의 가장 큰 좋은 소식이다. 문제는 코드가 아니라
**코드가 옳다는 것을 증명한다고 주장하는 장치**에 있다.
