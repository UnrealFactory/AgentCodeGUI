## 4. 질의 채널 공격 — `critic-m9r2-query.mjs`(신규) · 지적 0건

폴더가 다른 3패널(`wA`·`wB`·`wC`)에 서로 다른 목록을 물려 칩이 `1 · 1` / `1 · 2` / `1 · 3`으로
갈리게 해 두고(자리 오배정이 눈으로 보이게) 밀었다.

### 4.1 조회는 정말 런타임을 안 만드나 (Q1) — **참**

프로세스 계수와 허브 계수 두 갈래로 잰다.

```
기준(턴 0회)      : app 트리의 claude.exe 0 · 허브 슬롯 0 · spawns 0
냉조회 31발       : panelId×15(3패널×5) · 없는 chatId×5 · 없는 보드×5 · 이상한 주소 6종
  → 전부 null · claude.exe 0 → 0 · 슬롯 0 → 0 · spawns 0 → 0
턴 1회 뒤         : 슬롯 1 · spawns 1 · claude.exe 0 (턴 끝에 죽는다)
그 뒤 조회 20발   : 20/20 값 반환 · claude.exe 0 → 0 · spawns 1 → 1 · 슬롯 1 → 1
```

이상한 주소 6종(`{}` · `panelId:''` · `'nosep'` · 슬롯 `99999999999999999999` · `-1` · 범위 밖 `5`)도
전부 `null`이고 슬롯을 안 만든다. **"마운트만으로 CLI를 띄우지 않는다"는 물증으로 참이다.**
죽은 CLI를 되살리지도 않는다(`spawns` 불변) — 스냅샷은 프로세스와 분리돼 있다.

### 4.2 보드 자리 번역 — 껍데기 셋 전부 정확 (Q2)

```
그리드 칩          : ["1 · 1", "1 · 2", "1 · 3"]                     ← 자리별 제 값
panelId 직접 조회  : m9q::0→srv-a/wA/스킬1 · m9q::1→srv-b/wB/2 · m9q::2→srv-c/wC/3
chatId 직접 조회   : ma-m9q-0→srv-a · ma-m9q-1→srv-b · ma-m9q-2→srv-c   ← 두 주소가 같은 답
크게 보기(자리1)   : 카드 안 칩 "1 · 2"          ← 남의 자리 값이 아니다
원래 크기로        : ["1 · 1", "1 · 2", "1 · 3"]
팝아웃(자리2·턴 0) : "1 · 3"
다이얼 3 → 1       : 남은 자리 1 · 칩 "1 · 2"     (order 순열이 [1,…]로 바뀐 뒤)
다이얼 1 → 3       : ["1 · 1", "1 · 2", "1 · 3"] · 화면 순서 ["1","0","2"]
```

번역이 튼튼한 **구조적 이유**도 확인했다: `panelId = ${boardId}::${slot}`의 `slot`은 **보드
`slots[]`의 자리 키**이고, 다이얼이 바꾸는 것은 `count`·`order`(보이는 순열)뿐이라
`panel_id_to_chat`이 읽는 배열은 안 흔들린다. 「크게 보기」도 같은 `panelId`를 넘긴다
(앵커 키만 `::exp`로 가른다). 그래서 자리 수를 접었다 펴도 주소가 안 미끄러진다.

### 4.3 조회 폭주 (Q3) — 셸이 버틴다

| 판 | 값 |
|---|---|
| 직렬 100발 | **70ms** · null 0 (한 발 ≈ 0.7ms 왕복) |
| 병렬 100발 | **17ms** · null 0 · 그동안 렌더러 16ms 타이머 최대 공백 **16ms** |
| **턴이 도는 중** 병렬 100발 | **19ms** · null 0 · 한 발 최대 **15ms** |
| 실제 재마운트 20왕복(크게 보기⟷복귀 = 40마운트) | 칩 결손 **0회** |
| 폭주 뒤 | 패널 3 살아 있음 · `window.api` 정상 · CLI 프로세스 증가 0 · spawns 증가 0 |

**경계 하나는 기록해 둔다**(결함 아님): 이 조회는 `ipc_call`(tokio 워커) → `hub::call`의
**블로킹 `recv_timeout(3s)`**를 탄다. 지금 허브가 `ensure` 앞에서 즉답하므로 워커 점유가
마이크로초라 무해하지만, **마운트 수명주기가 블로킹 허브 왕복을 타는 첫 사례**다. 허브가
막히는 판(스폰 폭주·스토어 지연)이 오면 마운트 하나당 최대 3초씩 tokio 워커를 물고, 그
시간에 다른 창의 IPC가 굶는다 — `ipc/mod.rs`가 파일·Git·LSP를 `spawn_blocking`으로 뺀
바로 그 이유다. 실측 상한(턴 중 15ms)이 여유롭다는 것이 지금의 답이고, 값싼 보험은
셸 메모리 캐시 한 장이다.

### 4.4 푸시와 조회의 경합 — 낡은 값이 안 이긴다 (Q4)

턴 한복판에 목록을 갈아치우고(`srv-old`/스킬1 → `srv-new`/스킬4) 전이 구간 3초 동안
재마운트를 난사했다(크게 보기⟷복귀 반복 → 매 마운트가 조회를 한 발씩 쏜다).

```
라운드 0·1·2 : 정착 칩 "1 · 4" · 셸 스냅샷 srv-new · 전이 중 표본에도 되돌아간 값 없음
```

코드 근거도 같은 말을 한다: `setSnap((cur) => cur ?? tl)` — 조회 답은 **빈 칸만 채운다.**
그리고 조회 발사와 구독 등록이 **같은 틱**이라 그 사이에 놓치는 푸시가 없다(팝아웃 창에서
`ma:event`의 네이티브 `listen()`이 비동기 등록이라 이론적 공백이 있지만, 그 구간에 오는
푸시의 값은 이미 셸 `env`에 반영돼 있어 왕복이 같은 값을 돌려준다).

### 4.5 덤 — 재시작 뒤에는 아무것도 안 돌아온다 (`critic-m9r2-restart.mjs`)

R2가 창구를 열면서 「지난주 목록을 되살리지 않는다」는 원칙을 깨지 않았는지, 같은
`CCG_HOME`으로 두 번 띄워 확인했다.

```
1회차(턴 1회) : 칩 "1 · 1" · 조회 → srv-restart
앱 종료 → 재기동
2회차(턴 0회) : 칩 null · 조회 null · 허브 슬롯 0
```

디스크 절임 없음. 원칙 유지.

## 5. 크리틱 도구 한 줄(norm 거울) — 정당하다

**판정: 정당. 다만 그 한 줄은 원래부터 「독립 근거」가 아니었고, 독립 근거는 다른 데 있다.**

`critic-m9-norm.mjs`가 재는 것은 두 조각이다.
① **실 CLI가 실제로 뱉은 접두사**(`prefixes` 배열 — 원문 그대로 저장된다),
② 그 접두사와 **제품 규칙의 일치 여부**. ②의 규칙은 처음부터 `wire.rs::mcp_norm`을 **손으로
옮긴 거울**이고(그 파일이 스스로 "그대로 옮긴 것"이라 적었다), R1판 역시 R1 제품 코드의
거울이었다. 제품이 움직였으면 거울도 움직여야 한다 — 안 그러면 도구는 **없어진 코드**를 잰다.
실제로 R1 거울을 지금 데이터에 대면 `emoji🚀srv`가 **0매치**로 떨어져, 고쳐진 제품을 「깨졌다」고
잘못 신고한다(내가 확인했다).

거울을 고치면 남는 위험은 하나뿐이다: **오전사**(거울이 Rust와 안 같아지는 것). 그건
빌더 말로 못 닫으므로 **거울을 안 쓰는 근거 두 자리**로 닫았다 — 둘 다 내가 직접 확인했다.

1. **실 CLI 원문 vs 제품 단위 테스트 표.** 내 무인증 주행이 CLI 0.3.241에서 읽은 접두사:
   ```
   mcp__my_co_tools__ · mcp__srv__dbl__ · mcp________ · mcp__UPPER-Case__ · mcp__emoji__srv__
   ```
   `wire.rs`의 새 테스트 `mcp_prefix_counts_utf16_units_like_the_cli_does`가 못 박은 표와
   **다섯 줄 다 같다**(BMP 4자 = `_` 4개 · 서로게이트 쌍 = `_` 2개). 이 대조에는 JS 거울이
   한 글자도 안 들어간다.
2. **화면까지의 왕복.** 빌더 하네스 B 픽스처가 실 CLI에 `ccg-emoji🚀b`를 물려 받은 접두사가
   실물 2패널에서 `연결됨 · echo, ping · 도구 2` 행으로 그려지는 것을 `--app`에서 확인했다.
   여기도 거울이 없다.
3. 덤으로 **거울이 아예 못 보는 자리**도 지금은 초록이다: 정규화를 **안 거친** 접두사
   (`mcp__Ω_유니코드_🚀__hello`)가 정규화된 행에 붙는다(A2 — R1은 여기서 도구를 잃었다).
   이건 R2가 `mcp_norm(server)`를 되맞춤 키에도 한 번 더 태워서 생긴 이득이다.

빌더의 경계 신고도 사실이다: `critic-m9-attack.mjs`는 `ac7694b..b102e57` 사이 **커밋 0건**
(한 글자도 안 고침) · `m9-r1-*.json` **덮어쓴 것 0건**(git log로 확인).

작은 유보 하나: 이 편집으로 `critic-m9-norm.mjs`는 이제 **제품과 함께 움직이는 파일**이 됐다.
다음 라운드가 `mcp_norm`을 또 고치면 이 도구는 또 따라가야 하고, 그때마다 §5의 ①②를
같이 돌리지 않으면 「자기 거울에 자기를 비추는」 초록이 된다. 이 문서가 그 절차다.

## 6. A4-push를 엔진 라운드로 미룬 판단 — 타당

**판정: 타당. 근거 셋은 확인됐고, 넷째(예측)는 아직 아무도 안 쟀다.**

| 빌더 주장 | 내 확인 |
|---|---|
| "프레임이 셸에 안 온다"(와이어 계수 0) | **재확인.** 내 재실행에서 A4b 구간 `commandsChanged` 기여 **0** · A4c(턴 중) 기여 **1**. arm이 아니라 **시점**이 죽은 것이 맞다 |
| "원인은 `on_result → land_turn → OnIdle → close_and_finish → driver.kill()`" | **코드로 확인.** `runtime.rs:1867` `(empty=true, drainable=false) → OnIdle → Terminating → close_and_finish(AllClear)` |
| "레버는 `Linger(ms)` 한 줄이지만 턴 종료 의미에 매달려 있다" | **확인.** `Linger`는 `T20b`·`Resident{Linger}` 브로드캐스트·`linger_deadline`·드레인 보류(§3.4-a)와 한 덩어리다. `close_policy`가 **런타임 단위 옵션**(`with_close_policy`)이라 이론적으론 국소 적용이 가능하지만, 셸은 그 세터를 **한 군데도 안 부른다**(`grep` 0건) — 지금 켜려면 기본값 축을 새로 내야 하고 그건 M9의 몫이 아니다. **미룸이 값이 맞다** |
| "그때 arm은 **코드 변경 0**으로 저절로 초록이 된다 — 이미 배선돼 있다" | **미검증.** 제품 수정 없이 그 상태를 만들려고 `land_turn`의 `(empty=true, drainable=true)` 갈래(=result 순간 큐에 다음 발화가 있으면 안 닫고 드레인)를 사용자 경로로 노렸다. **두 번 다 전제부터 안 섰다**(턴1을 250ms·3,000ms로 두고 각각 +150ms·+1,000ms에 두 번째 발화 — 둘 다 `spawns 2`, 즉 같은 프로세스로 안 이어졌다). 그래서 result 뒤 프레임이 셸에 오는 판 자체를 못 만들었다(`commandsChanged: 0`) |

미검증이라고 미룸이 틀렸다는 뜻은 아니다 — 오히려 반대다: **사용자 경로로는 result 뒤에
CLI가 살아 있는 판을 못 만든다**는 것이 이번에 두 번 확인됐고, 그러면 이 arm이 실사용에서
울릴 일 자체가 지금은 없다(실 CLI 2턴 주행의 `commandsChanged`도 **0장**이었다). 다만
엔진 라운드가 `Linger`를 켤 때 **"코드 변경 0"은 검증된 사실이 아니라 예측**이라는 것은
그 라운드가 알고 시작해야 한다. 그때의 판정 도구는 이미 있다(`critic-m9-attack --only=A4`).

## 7. 새 발견

### 7.1 ★`npm run typecheck`가 빨갛다 — 3.0만 고치고 2.6.2 쌍둥이를 안 고쳤다

R1 크리틱은 레포 `node_modules`가 비어 있어 tsc를 못 돌렸고, 그 칸이 비어 있는 사이
**같은 계열의 실수가 두 번** 들어갔다. 지금은 `node_modules`가 살아 있어 잰다.

```
$ npm run typecheck        # HEAD(b9aed34) · 워크트리(b102e57) 동일
exit 2

typecheck:node  src/preload/index.ts(250,3): TS2741
  Property 'toolingGet' is missing in type '{ run; cancel; interrupt; … }'
  but required in type WindowApi['multi']
typecheck:web   src/renderer/src/store/session.ts(1047,51): TS2345
  Argument of type '{ type: "tooling"; runId: string; tooling: ChatTooling }'
  is not assignable to parameter of type 'never'      ← 소진 가드
```

귀속을 대조군으로 못 박았다(부모 워크트리 `894e489`):

| 게이트 | 894e489 (부모) | b102e57 (판정 대상) |
|---|---|---|
| `typecheck:node` | **초록**(출력 0줄) | **빨강** — `toolingGet` |
| `typecheck:web` | **빨강** — `tooling` 소진 가드 | 빨강(그대로) |

* **node 쪽은 이 커밋이 깨뜨렸다.** `src/shared/api.ts`의 `WindowApi.multi`에 `toolingGet`을
  **필수**로 더했는데, 같은 인터페이스를 구현하는 **다른 쪽**(Electron `src/preload/index.ts`)에
  안 넣었다. 3.0 셸의 `app/src/api/shim.ts`에만 넣었다.
* **web 쪽은 M9 R1(`582872f`)부터다.** 그 커밋이 `protocol.ts`에 `EngineEvent{type:'tooling'}`을
  더하면서 소진 가드를 **`app/src/store/session.ts`에만** 고쳤다(커밋 메시지 ③이 그렇게 적고
  있다). 쌍둥이 `src/renderer/src/store/session.ts`에는 `tooling`이란 낱말이 **한 번도 안 나온다.**

**사용자 피해는 지금 없다**(두 렌더러는 분리돼 있고 `electron-vite build`는 tsc를 안 탄다 ·
`McpSkillView`는 Tauri 쪽에만 있다 · shim의 `?.()` 옵셔널 체이닝이 런타임을 지킨다). 피해는
**규율** 쪽이다: 레포의 공식 타입 게이트가 두 라운드째 빨간 채로 굴러가고 있고, R2의 게이트
줄은 `tsc 0`이라고만 적어 **더 좁은 판(`-p app/tsconfig.json`)만 신고**했다. 다음 사람이
`npm run typecheck`를 치면 자기가 깬 줄 안다. 고침은 각각 한 줄이다(preload에 스텁 하나 /
2.6.2 렌더러에 `case 'tooling': return state`).

### 7.2 같은 서버를 40px 안에서 두 낱말로 부른다 (`unknown` vs `상태 미상`)

R2가 상태 여섯 갈래를 세면서 **툴팁에는** `상태 미상`이라는 낱말을 새로 만들었는데,
**행의 낱말은 안 맞췄다.** `wire.rs:569`가 status 없는 서버에 `"unknown"`을 채우고,
`McpSkillView.statusLabel`은 모르는 값을 "지어내지 않는다"는 규칙으로 **원문 그대로** 낸다.

```
칩 툴팁 : "MCP 4개 연결 · 1개 상태 미상 · 스킬 5개 · 클릭해 자세히"
같은 카드의 행 : "no-status-here · unknown"          ← 한국어 UI에 영문 토큰
```

`unknown`은 CLI가 준 값이 아니라 **셸이 붙인 기본값**이므로 "모르는 값은 그대로 보여준다"는
규칙의 대상이 아니다(그 규칙이 지키려는 것은 *CLI가 새 status를 도입했을 때*다). 한 줄이면
맞는다(`if (s === 'unknown') return t('상태 미상', 'Unknown')`). 영어 UI에서는 안 보이는
결함이라 더 늦게 잡힌다.

### 7.3 관찰(결함 아님 · 기록)

1. **밀도는 그대로다** — §3 끝. R2가 섹션 머리(`MCP 서버 10 · 꺼짐 1`)를 손댔지만 sticky도
   접기도 필터도 없어, 서버 10 + 스킬 50이면 여전히 60행 중 6행만 보이고 스킬 목록은
   처음부터 화면 밖이다.
2. **조회가 블로킹 허브 왕복을 탄다** — §4.3의 경계.
3. **정규화 키 충돌**은 R2의 양쪽 정규화로 성질이 바뀌었다: 이름이 다른 두 서버가 같은
   키로 접히면(`my.co tools` vs `my_co_tools`) R1은 도구를 **잃었고** R2는 **양쪽 행에 붙인다.**
   CLI 접두사 자체가 그 둘을 구분하지 못하므로 앱이 더 잘할 수 있는 자리가 아니다 —
   R1 §3.2가 적은 "뒤에서 가르기"의 대가와 같은 계열이고, 대가의 얼굴만 바뀌었다.
4. **`m9-r1-b-midturn.json`의 A5 무효 표시**(R1 §7 각주)는 R2 문서 §R2.5-다가 그대로
   물려받아 적었다 — 정정 전달이 됐다.
