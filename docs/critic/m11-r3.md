# M11 R3 확인 크리틱 — 계정 파일 레이스 (`2a61755`)

**임무**: R3가 닫았다고 적은 자리(F1 잠금·3-way 병합·좁히기 / F2 격리·백오프·복구 / F3~F9 / F5)를
독립 재실행으로 판정하고, **새로 만든 방어의 가장자리**를 다시 친다. 빌더의 산출 JSON은
증거로 쓰지 않았다 — 내가 다시 돌린 게이트, 내가 새로 짠 공격, 내가 심은 뮤테이션,
그리고 **진짜 2.6.2 코드**로 한 동시 실행 1판만 적는다.

### 왜 설치본 exe가 아니라 "실코드 + 실 런타임"인가

esbuild로 번들해 **같은 Electron 런타임**(`node_modules/electron` 42.x)에서 돌렸다.

| 막힌 길 | 이유 |
|---|---|
| 설치본 `AgentCodeGUI.exe` | `auth.ts:76 APP_HOME = os.homedir()/.agentcodegui` — **CCG_HOME 오버라이드가 없다.** 격리가 불가능 = 실홈·실토큰을 건드린다 |

## 4. ★ 재공격 — 잠금을 **모르는** 이웃 (G1)

도구: `docs/critic/tools/critic-m11r3-attack.rs`(C1) · `docs/critic/tools/critic-m11r3-262race.mjs`(실 2.6.2).

R3의 실증(`m11r3_store_race`)과 R2의 T4는 **자식도 `ccg-auth`를 쓴다** = 자식도 `flock`을 잡는다.
그건 "3.0 두 벌"의 판이다. F1이 막겠다고 적은 상대는 **2.6.2 실앱**이고, 그쪽의 쓰기는
`fs.writeFileSync(STORE_PATH, JSON.stringify(...))` 한 줄이다(`auth.ts:124`) — 잠금도 병합도 없다.

### 4.1 실 2.6.2 코드 (1판)

```text
[SEED] ["mine@x"]
[BGW]  rounds=450 ok=450 clobbered=2  store=Some("bg-449") folder=Some("bg-449")
[262]  {"rounds":150,"removed":150,"resurrected":2,
        "homedir":"…\\ccg-m11r3c-262-26960","store":["mine@x"]}
```

- **로그아웃 취소 2/150.** 2.6.2가 `removeAccount('ghost@x')`로 지운 계정이, 3.0의 배경 쓰기가
  **자기 레코드만 고치는데도** 되살아난다 — `update_account_record`가 잠금 안에서 읽은
  스냅샷과 쓰기 사이(§6, 실측 **11~14.5ms**)에 이웃의 통짜 쓰기가 떨어지기 때문이다.
  되살아난 항목은 `credEnc`를 그대로 문다 = **살아 있는 토큰째** 돌아온다(R2 §5와 같은 피해).
- **역방향 클로버 2/450.** 이웃의 낡은 통짜 쓰기가 우리 회전을 백업에서 지운다. 폴더 사본이
  살아 있어(`folder=bg-449`) 토큰 자체는 무사하다 — R2가 적은 "유일한 완충"이 그대로 유일하다.

### 4.2 내 Rust 이웃 (200판 × 3주행)

`auth.ts`의 모양을 그대로 옮긴 잠금 없는 자식(`peer` 모듈)으로:

| 주행 | 로그아웃 취소 | 내 회전 클로버 |
|---|---|---|
| 1 | 0 / 200 | 180 / 200 |
| 2 | **15 / 200** | 36 / 200 |
| 3 | 0 / 200 | 55 / 200 |

되살아남은 **잠깐**일 수 있어(다음 쓰기가 다시 지운다) 15ms를 1ms 간격으로 훑어 센다.
그 순간의 파일이 곧 사용자가 보는 계정 목록이다.

**해석**: R3가 만든 것은 *"잠금을 아는 프로세스끼리의 안전"*이다. 그건 실재하고 값지다
(3.0 두 벌 · 워커 vs 허브 · 앞으로 이식될 3.0 로그아웃). 하지만 커밋 제목이 든 숫자
("로그아웃 취소 11/120 → 0")는 **상대를 바꾸면 0이 아니다.** 하네스 비율이 실제보다
훨씬 촘촘하다는 것은 사실이지만(사용자는 로그아웃을 하루 몇 번 한다), *조건부 확률*
— 이웃의 쓰기가 우리 창에 떨어졌을 때 무슨 일이 나는가 — 는 R2에서 **한 톨도 안 줄었다**.

## 5. 3-way 병합의 실패 모드

### 5.1 기준점이 **스레드**에 묶여 있다 (C2, 경)

`record_base`는 `thread_local!`이고 `take_base()`는 한 번 쓰면 소비한다. 읽은 스레드와
쓰는 스레드가 다르면 base가 없고, base가 없으면 `merge3`은 **첫 줄에서 `mine`을 그대로
돌려준다** = R2의 통짜 덮어쓰기다.

```text
[C2] 같은 스레드 읽기→쓰기: 로그아웃한 b@x가 되살아났나 = false   ← 설계가 상정한 모양
[C2] 다른 스레드 읽기→쓰기: 로그아웃한 b@x가 되살아났나 = true    ← ★
```

허브가 목록을 읽고 워커가 쓰는 모양(= 이 앱이 실제로 스레드를 쓰는 방식)에서 층 ②가
**말없이 사라진다.** 오늘 제품에서 이 조합이 안 나는 이유는 §7의 도달성 감사 때문이지
설계가 막아서가 아니다.

### 5.2 손상 안전문이 **정상적인 빈 목록**도 되살린다 (C3, 경)

안전문은 *"디스크가 비었는데 base는 안 비었으면 병합을 건너뛴다"*이다. 그런데
`read_store_file`은 **손상**과 **마지막 계정 로그아웃**을 구별하지 않는다. 후자에서 문이 열리면
그건 복구가 아니라 **로그아웃 전체 취소**다.

```text
[C3] 이웃이 남긴 파일 = { "version": 3, "accounts": [] }        ← 멀쩡한 v3 · 정상 상태
[auth] accounts.json이 비어 보인다(손상 의심) — 병합을 건너뛰고 우리 목록으로 복구한다
[C3] 우리 쓰기 뒤 계정 = ["a@x", "b@x"]                          ★ 둘 다 credEnc째 부활
```

구별할 재료는 있다(파일 존재 여부 · 파싱 성공 여부 · `version` 유효성). `read_store_file`이
그 셋을 뭉개 `StoreFile::default()`로 주는 것이 원인이라, 고치는 자리도 거기다.

### 5.3 같은 위험이 **제품 경로**에는 문 없이 열려 있다 (C7, 정보)

안전문은 `merge3`(=`write_store_file`) 안에만 있다. 목록을 바꾸는 다른 문 `update_store`는
잠금 안에서 읽은 값을 그대로 믿는다:

```text
[C7] 깨진 파일 위 로그인 뒤 계정 = ["c@x"]   (원본은 a@x·b@x)
```

**2.6.2와 같은 동작이다**(`auth.ts:108 readStoreFile`의 `catch → accounts: []`) — 회귀가 아니라
선행 결함이고, 3.0은 아직 로그인/로그아웃을 이식하지 않아 도달 불가다. 다만 *"손상 위에서
계정을 잃지 않는다"*를 이번 라운드가 새로 약속했으므로, **문 하나에만 단 자물쇠**로 적어 둔다.

## 6. 잠금 — 잔재 · 크래시 · 오래 쥠 (C4·C8)

```text
[C4-①] 잠금을 쥔 채 죽은 프로세스 뒤 획득: 207~372µs  cross=true    ← 커널이 거둔다
[C4-②] 살아 있는 주인이 10초 쥔 동안 배경 쓰기: 4.013s 성공=true    ← 규약 3(4초 뒤 없이 진행)
[C4-③] 잔재 .lock 존재=true · 재획득 121~143µs cross=true           ← 잔재는 무해
[C8-①] persist_refreshed_report 1회 = 11.2~14.5ms (읽기+DPAPI 2회+쓰기, 잠금 안)
[C8-②] 잠금 안 클로저가 60ms일 때 이웃 로그아웃 → 되살아남 = true
```

- **잔재·크래시는 안전하다.** `.lock` 파일은 남지만 다음 획득을 0.1ms에 통과시킨다.
  `std::mem::forget` + `process::exit`로 죽여도 커널이 핸들과 함께 잠금을 거둔다.
- **오래 쥔 주인**: 4초를 기다린 뒤 *잠금 없이* 쓴다. 저장이 사라지지 않는 쪽을 고른 것은
  옳지만, 그 4초는 **프로세스 안 뮤텍스를 쥔 채** 흐른다 — 계정 6개면 워커 한 바퀴가
  최대 24초 밀린다(`SNAP_TTL` 120초 안이라 기능은 안 죽는다). 정보로 남긴다.
- **C8이 §4의 원리다**: 임계 구역이 짧아서 안전한 게 아니라 **11~14.5ms**나 된다(DPAPI 2회).
  클로저를 60ms로 늘리면 이웃의 로그아웃이 **결정적으로** 취소된다.

```text
src-tauri 전체에서 accounts.json을 쓰는 경로:
  ccg_auth::net::fetch_account_usage → access_token → rotate → store_rotation
    → claude::persist_refreshed_report → update_account_record   ← ★ 이 하나뿐
  (claude::write_store_file 호출은 acct_switch.rs:538 = **테스트 시드**가 유일)
  update_store / import_account_from_dir 호출 = **0건**(3.0의 계정 IPC는 여전히 읽기 전용)
```

그래서 R3의 세 겹 중 **층 ②(3-way 병합 + 안전문)는 제품 경로에 없다.** 오늘 사용자를
지키는 것은 층 ③(자기 레코드만) + 층 ①(잠금) + 폴더 사본이고, 층 ①은 2.6.2 상대로는
효과가 없다(§4). 커밋의 *"잠금을 모르는 2.6.2 실앱을 막는 것이 이 겹이다"*는 **아직 아무도
지나지 않는 문**에 달린 자물쇠를 가리킨다 — 3.0이 로그아웃을 이식하는 날 비로소 발효한다
(그리고 그때 §5.1·§5.2가 같이 발효한다).

## 8. 건강 장부(F2)의 복구 경로 — 두 군데가 틀렸다

### 8.1 지문이 없으면 **영원히** 안 풀린다 (C6, 중대)

```text
[C6] 표식 파일 = { "gone@x": { "needsLogin": true, "reason": "http 401", "at": … } }   ← tokenFp 없음
[C6] 재로그인(완전히 새 크리덴셜) 뒤 needs_login = true                                 ★
```

- `mark_needs_login`은 `fingerprint()`가 `None`이면 `tokenFp`를 **안 적는다**.
- 해제 규칙은 `if r.token_fp.is_some() && r.token_fp != fingerprint(email)`이라, 그 표식은
  **어떤 재로그인으로도** 무효가 되지 않는다.
- 남은 해제 경로는 "조회 성공"뿐인데, `collect()`는 표식이 선 계정을 **조회 전에 `continue`**
  한다(`acct_switch.rs:411`). 그래서 성공할 기회 자체가 없다.
- 지우는 UI도 없다(설정은 배지만 그린다 · IPC는 읽기 전용 · 로그아웃/로그인 어느 쪽도
  `health::clear`를 안 부른다).

도달 경로는 좁지만 자연스럽다: **워커가 401을 받은 그 순간 그 계정이 스토어에 없으면**
지문이 `None`이다. 로그아웃은 곧 토큰 해지라 401은 오히려 그때 나오고, 워커 한 바퀴는
최대 20초라 목록 스냅샷이 그만큼 낡는다. 그리고 그 401의 **자연스러운 처방이 로그아웃 →
재로그인**이다 — 사용자가 처방을 따르면 새 계정이 **태어날 때부터 격리**된다.

화면 문구까지 틀린다: *"삭제하고 다시 로그인하면 풀립니다"* — 이 판에서는 안 풀린다.

### 8.2 재로그인이 아닌 **평범한 갱신**에도 풀린다 (C5, 경)

```text
[C5] 액세스 토큰만 갱신(refresh는 그대로) 뒤 표식 = false / 장부=[]
```

지문은 크리덴셜 **원문 전체**의 sha256이라(`token_fingerprint`), CLI가 턴 중에 액세스 토큰
하나만 리프레시해도 달라진다. 그러면 표식이 스스로 지워지고 그 계정은 다시 후보가 된다.
방향이 항상 나쁜 것은 아니지만(리프레시가 됐다 = 그 계정은 살아 있다), **401/403으로 표식이
선 계정**은 리프레시가 계속 성공하므로 *격리 → 해제 → 401 → 격리*를 돈다. 문구가 약속한
"재로그인하면 풀린다"의 실체는 "**뭐든 바뀌면 풀린다**"이다.

## 9. Probe 한정의 대가 — 네트워크가 멀쩡한 429에서 후보가 사라진다 (경)

`plan`의 통과를 `Probe` 하나로 좁힌 근거는 *"`collect()`가 조회 뒤 preflight를 다시 잰다"*인데,
그 문장은 **조회가 성공했을 때만** 참이다(`acct_switch.rs`의 재측정은 `Ok(u)` 가지 안에 있다).
조회가 429/5xx로 실패하면 세 가지가 겹친다:

| # | 무엇 | 값 |
|---|---|---|
| ① | 판정은 조회 **전** 값 그대로 | 만료 토큰이면 `NeedsRefresh` → `SkipWhy::Unverified` |
| ② | 새 usage가 없으니 캐시가 낡는다 | `ACCT_USAGE_TTL_MS` = **2분** |
| ③ | 셸 격리 백오프가 재조회를 막는다 | 60초 → ×2 → 상한 **30분** |

②가 지나면 살아 있는 계정도 `usage_unknown`이라 후보가 아니다:

```text
[C9] pick=None skipped=[cur@x:Current, ok@x:UsageUnknown]   ← ok@x의 토큰은 Probe(살아 있다)
```

즉 usage API가 잠깐 흔들리면(그 API는 같은 IP의 병렬 2건 중 1건이 429라고 이 저장소가
직접 적어 뒀다 — `usage.rs` 헤더) 자동 전환이 **최대 30분** "갈아탈 계정이 없어요"가 된다.
게다가 백오프가 **두 층에서 따로 올라간다**: `net`의 `RotateBackoff`(교환 안 나감)로 착지한
호출도 셸의 `note_sick`에 실패로 세어져(`Err(_)` 한 가지), **POST 한 건 없이** 셸 백오프가
60초→2분→4분으로 배가된다. 429는 계정의 죄가 아닌데 계정이 벌을 받는다
(`CCG_NO_NET`만 예외 처리돼 있다).

### 다음 라운드 순서 (내 권고)

1. **G2** — 지문이 없으면 표식을 **안 쓰거나**(이유만 로그), 해제 규칙을 `token_fp.is_none() → 무효`로
   뒤집는다. 겸사겸사 `import_account_from_dir`/`remove_account`에서 `health::clear(email)`를 부른다
   (로그인·로그아웃은 그 계정에 대한 우리 기억을 버려야 하는 자리다).
2. **G1** — 2.6.2가 잠금을 모르는 한 남는 창이라, 닫는 길은 둘이다: ⑴ 2.6.2 쪽에 같은 `flock`을
   이식(동결 트리 수정이라 비용이 크다) ⑵ **쓰기 직전 mtime/크기 재확인 + 불일치면 재시도**
   (`update_account_record`가 클로저 뒤에 한 번 더 읽어 비교하면 창이 11ms → µs로 줄어든다).
   무엇을 택하든 **실증의 자식을 잠금 없는 쪽으로** 바꿔야 숫자가 뜻을 갖는다.
3. **G3·G4** — `read_store_file`이 "없음/깨짐/빈 목록"을 구별해 돌려주고(안전문의 재료),
   기준점은 스레드가 아니라 **읽은 스냅샷에 붙인다**(`StoreFile`이 base를 들고 다니면 된다).
4. **G6** — 429·5xx는 `note_sick` 대상에서 빼거나 별도(짧은) 곡선으로. `RotateBackoff`는
   실패로 세지 않는다.
