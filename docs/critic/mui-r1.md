## 1. 재현 — 유리 방어

### 1.1 복구 시간 (빌더 표 대조)

`scripts/poc-glass/glass.ps1 -Action knock -Backdrop 1 -Seconds 8 -IntervalMs 25`

| 경로 | 내 실측 | 빌더 주장 | 판정 |
|---|---|---|---|
| 조용한 드리프트(폴링만) | **8/8** · 296~529 · 평균 **346.6ms** | 8/8 · 309~637 · 359ms | 재현 |
| 메시지 경로(`WM_SETTINGCHANGE`) | **8/8** · 62~94 · 평균 **82.8ms** | 8/8 · 61~95 · 72ms | 재현 |

**다만 문서의 명령으로는 문서의 수치가 안 나온다.** `ui-glass.md` §5가 적어 둔 그대로
(`-Action knock -TargetPid <PID> -Backdrop 1 -Seconds 8`, `-IntervalMs` 없음) 돌리면
기본 폴링이 1000ms라 **1017 / 1003 / 1003ms**가 찍힌다. 사용자가 §5를 그대로 따라 하면
"복구가 1초"라고 결론 내린다. → §5 명령에 `-IntervalMs 25`를 박아야 한다(제안 diff D5).

### 1.2 픽셀 — swing만으로는 "생비침"을 증명할 수 없다 (내가 추가한 축)

빌더의 판정 지표 `swing`(원색 3띠 위 저주파 추적성)은 **블러 여부를 못 가른다.**
3.0의 핵심 주장("재질이 죽으면 벽지가 **블러 없이** 생으로 비쳐 글자를 못 읽는다")은
고주파 축이라, swing 21(아크릴) vs 23(NONE)만으로는 확인도 반박도 안 된다 —
오히려 "둘이 비슷하니 별 차이 없다"로도 읽힌다.

그래서 `docs/critic/tools/mui-glass-px.ps1`를 새로 썼다. 배경판을 **창 바로 아래
z-order에 끼우고**(창을 옮기지 않는다 = 포커스 절도 없음) 마젠타/시안/흰색 **+ 4px 체커**로
갈아 끼우며 사이드바 패치(120×150)를 잰다. `detailH` = 인접 픽셀 차 평균 = 선명도.

## 3. 결함 (제안 diff 포함 — 제품 코드는 안 고쳤다)

### 3.1 【최대 격차】 폴백은 **부팅 순간의 문서**에만 도달한다

`CCG_GLASS_FORCE_OFF=1`(= "이 OS에서는 아크릴 불가"와 같은 상태)로 띄운 뒤:

| 문서 | htmlClass | fallback style | `--panel` | `__ccgGlass.events` |
|---|---|---|---|---|
| 부팅 창 | `ccg-glass-off` | 있음 | `#1d1d1d` | 3 |
| **`location.reload()` 후** | **없음** | **없음** | `rgba(21,21,21,.7)` | **0** |
| **부팅 뒤 연 추가 채팅 창** | **없음** | **없음** | `rgba(21,21,21,.7)` | **0** |

원인은 구조다. `emit_state`는 **`ok`가 전이할 때만** 쏘고, 그 공백을 메우는 장치는
감시 스레드의 **부팅 3연발(250·1s·3s)뿐인데 그게 프로세스당 1회**다(`boot_i`).
`ok`는 계속 false이므로 이후 발화가 없고, **렌더러가 물어볼 경로도 없다** —
"단방향 브로드캐스트라 `ipc.rs`를 안 건드린다"는 경계 결정이 **풀(pull) 경로를 없앴다.**

영향: 추가 채팅(Ctrl+Shift+N)은 일급 기능이고, 크래시 복구는 M-CRASH의 존재 이유다.
투명 효과가 꺼진 사용자(설정·배터리 절약·원격)는 **그 두 경로 뒤로 영구히**
"재질 없는 투명 창" = 빌더가 폴백으로 막겠다던 최악(글자 뒤 벽지)에 남는다.

**제안 D1 — 부팅 페이로드에 실어 보낸다(경계 유지: ipc.rs 무수정).**
`initialization_script`는 **그 웹뷰의 모든 페이지 로드마다** 다시 돌므로 재로드·새 창이 공짜로 덮인다.

+        // 크래시 복구 재로드에는 오지 않는다(크리틱 R1 실증: events=0). 이 스크립트는
+        // 페이지 로드마다 다시 도므로 여기 실으면 그 두 구멍이 함께 닫힌다.

**제안 D2 — 벨트(선택).** `ok == false`인 동안에는 `PROBE_EVERY`마다 `force` 재발신
(초당 0.25회, 값이 안 바뀌면 렌더러는 멱등이라 무해). 페이로드가 없는 창도 4초 안에 수렴한다.

### 3.2 사각지대: "값은 3인데 안 그린다"를 **감지도 복구도 못 한다**

`glass.rs`는 스스로 이렇게 적었다 — *"값이 3인데 안 그리는 상태가 실재하고, 그때 되살리는
유일한 방법이 재기록이다"*(:234). **그 문장은 검증된 적이 없다.** knock/repro는 전부
**속성이 바뀌는**(attr-lost) 경로다. 그리고 그 상태가 오면:

- `read_backdrop` = 3 → 드리프트 아님, `advanced_effects_enabled()` = true, `remote_session()` = false,
  `DwmSetWindowAttribute` = Ok → **`ok=true` 유지 → 폴백도 안 켜진다.**
- 관측기(`glass.ps1 -Action observe`)에는 `render-lost` 플래그가 **있다**. 즉 빌더도 그 상태가
  실재한다고 믿는데, **제품에는 그 신호가 없다.**

나도 만들어 보려고 두 레버를 per-window로 걸었다(사용자 전역 설정 무관):
`WS_EX_LAYERED + LWA_ALPHA(255)`, `SetWindowCompositionAttribute(ACCENT_DISABLED)`.
**둘 다 아크릴을 못 죽였다**(swing 21 유지). 그러므로 이 라운드에서는
**"사각은 구조적으로 존재하나 도달 가능성은 양쪽 다 미증명"**이 정직한 결론이다.

> **내가 밟은 함정(자기 정정).** 처음엔 layered 상태에서 swing 0 · 평탄 20.5를 재고
> "render-lost 재현"이라고 적었다. 실제로는 **추가 채팅 창이 샘플 패치의 72%를 덮고 있었다.**
> 단일 창 인스턴스로 다시 재니 swing 21이 그대로였다. 오염 회차(C~F)는 원본 JSON에 남겨 둔다.
> 교훈: 픽셀 판정 도구는 **패치가 다른 창에 가려졌는지 먼저 단언해야 한다**(도구 결함, 내 몫).

**제안 D3 — 감지를 못 하면 실패를 안전하게 만든다.** D1을 넣으면 폴백은 언제나 도달하므로,
남은 선택은 "언제 켜느냐"다. 지금은 *꺼짐을 증명해야* 켜진다. 뒤집으면(**살아 있음을 증명해야
투명**) 사각이 와도 결과는 "의도된 불투명"이지 "글자 뒤 벽지"가 아니다. 비용은 부팅 순간의
스냅샷 하나(D1이 이미 제공)뿐이다. §5의 권고와 같은 결론이다.

### 3.3 진단이 부팅 값에 얼어 있다

적대 루프로 드리프트를 ~934회 만든 **직후** 렌더러가 보는 값:

```
__ccgGlass.state {ok:true, reason:"", reasserts:9, drifts:0} · events:3
```

`reasserts`/`drifts`는 **부팅 때 찍힌 숫자**다(`emit_state`가 전이에만 발화하므로).
`glass::health()`는 **호출자가 0**이다(`grep glass::health` → 0). 사용자가 증상을 다시 겪고
`window.__ccgGlass`를 보내오면 **"아무 일도 없었다"고 적힌 진단서**를 받게 된다.

**제안 D4 — 사건을 파일에 남긴다(IPC 없이, crash.rs의 로그 규약 그대로).**
`DRIFTS`가 증가한 회차에만 앱 홈 `glass.log`에 한 줄 JSON(ts·hwnd·이전 값·복구 ms).
재발 순간의 트리거를 특정하려는 §4·§5의 목적에 정확히 맞는다.

### 3.4 감시 스레드 종료 경합 (좁지만 실재)

```rust
if WINDOWS.lock().unwrap().is_empty() && APP.get().is_some() {
    std::thread::sleep(Duration::from_secs(2));
    if WINDOWS.lock().unwrap().is_empty() {      // ← 여기서 락이 풀린다
        STARTED.store(false, Ordering::SeqCst);  // ← 그 사이 arm()이 끼면
        return;                                  //   새 창은 등록됐는데 감시자가 없다
    }
}
```
`arm()`은 `push` 후 `spawn_watchdog()`을 부르고, 그 사이에 이 스레드가 `STARTED=false`를
쓰면 `swap(true)`가 **이미 true를 보고 스폰을 건너뛴다**. 크래시 복구 경로가
`destroy → 400ms → create_main`이라 2초 유예 안에 들어와 실측으로는 안 밟혔지만,
부하가 걸린 복구(2초 초과)에서 정확히 이 창이 열린다.

**제안 D5 — 목록 락으로 두 결정을 묶는다.**
```rust
// 감시 스레드
let list = WINDOWS.lock().unwrap();
if list.is_empty() && APP.get().is_some() {
    drop(list);
    std::thread::sleep(Duration::from_secs(2));
    let list = WINDOWS.lock().unwrap();     // ★ 락을 쥔 채로 STARTED를 내린다
    if list.is_empty() { STARTED.store(false, Ordering::SeqCst); return; }
}
// arm(): push와 spawn_watchdog을 같은 락 구간에서
let mut list = WINDOWS.lock().unwrap();
list.push(hwnd.0 as isize);
spawn_watchdog();          // ← 락을 쥔 채 호출 (STARTED 판정이 위와 직렬화된다)
drop(list);
```

### 3.5 문서 결함

- `ui-glass.md` §5 knock 명령에 `-IntervalMs 25`가 빠져 문서 수치(346ms)가 재현되지 않는다(§1.1).
- `glass.rs:47-48` 모듈 주석이 **"주기 검증(2초) … 늦어도 2초 안에 복구"**로 낡았다

## 4. `transparent(true)` 문제 제기 — 평가와 권고

**빌더의 발견은 옳다.** 3.0의 실패 모양은 2.6.2와 다르고, 내 detail 축이 그걸 증명했다
(체커 위 detail 0 → 5.36). "회색 판"과 "글자 뒤로 지나가는 사진"은 다른 사건이다.

**다만 사용자 증상과의 관계는 빌더의 서술보다 조심해야 한다.** 사용자가 말한 것은
**"진한 회색"**이다. 그건 2.6.2(Electron) 실패의 픽셀(15,15,15 평탄)과 일치하고,
3.0 백드롭 NONE의 픽셀(벽지 추적 + 선명)과는 **일치하지 않는다.** 즉
- 사용자가 겪은 사건이 3.0 셸에서 같은 모양으로 재현될지는 아직 모른다(3.0 실사용 제보 아님),
- 3.0에서 그 사건이 나면 **증상이 회색이 아니라 벽지**가 된다 — 즉 사용자는 "회색"이 아니라
  **"읽을 수 없음"**으로 다시 만난다.

### 권고 (M1 몫)

**투명은 유지하고, 폴백의 기본값을 뒤집는 쪽을 권한다.** 근거:

1. **불투명 전환은 한 줄이 아니다.** `CCG_CHROME=c`(투명+아크릴 제거)를 실제로 띄워 재 보면
   사이드바가 **38,38,38**에 착지한다 — 아크릴(15~38, 평균 24)도, 설계된 폴백(20)도 아닌
   제3의 밝기다. `transparent(false)`만 끄면 웹뷰 기본 바닥이 드러나 **토큰 위계가 어긋난다.**
   결국 폴백이 하는 CSS 작업(`--panel`/`--chat-bg` 불투명화)을 **똑같이** 해야 하고,
   그러면 남는 차이는 "아크릴을 포기하느냐"뿐이다. 아크릴은 2.6.2 파리티의 핵심 외형이다.
2. **투명을 유지해도 실패는 안전하게 만들 수 있다.** 지금 구조는 *꺼짐을 증명해야* 폴백이 켜진다
   → 증명 못 하는 실패(§3.2)와 통지 못 하는 창(§3.1)에서 최악이 남는다.
   D1(부팅 페이로드) + D3(기본값 뒤집기)이면 **모든 미지의 실패가 "의도된 불투명"으로 착지**한다.
   비용은 창 하나당 부팅 스냅샷 1회.
3. **방어 자체는 값을 한다.** 실제 트리거는 메시지를 동반하므로 현실 경로는 82.8ms이고,
   유휴 비용은 0.0044% 코어다. 방어를 빼고 불투명으로 가는 선택은 **얻는 게 성능이 아니다.**

> 반대 의견을 남겨 둔다: 만약 M1이 "아크릴을 3.0에서 포기한다"를 이미 고려 중이라면,
> 판단 근거는 유리 소실이 아니라 **파리티·정체성**이어야 한다. 소실 대응은 위 두 줄로 닫힌다.

### 5.6 7종 문법(형태 3 × 색조 4)의 일관성 — 통과, 흠 4개

- **형태 파생 규칙이 실제로 파생된다.** "앞뒤를 가르나 → rule / 개입이 필요한가 → band /
  무엇이 만들어졌나 → card"로 7종이 충돌 없이 떨어지고, 렌더에서도 세 층으로 읽힌다.
  `rule`의 선 방향(종결/경계)만으로 두 쓰임을 가른 것은 아이콘·색을 아끼는 좋은 수다.
- 흠 1 — **문법표가 자기 계측과 어긋난다.** `ui-notify-0-system.html:179`는 band를 **"39px+"**,
  `ui-notify.css:192` 주석은 **"1줄이면 39px(현행 41px)"**라고 적었는데 같은 시트의 실측은
  **47.0px(현행 46.8px)**다. 문서 §2.2만 47px로 고쳐졌다 — **읽는 사람이 보는 두 곳이 낡았다.**
- 흠 2 — **`card.bare`의 색조가 미지정.** `.card.bare .tile{color:var(--key)}`인데 문답 마크업에
  `t-positive`가 없어 `--key`가 정의되지 않는다(현재는 상속색으로 렌더). 배치표는 문답을
  `positive`로 규정했으므로 마크업이나 규칙 중 하나가 틀렸다.
- 흠 3 — **§4-1의 불변식이 패널 스코프에서 깨진다.** "행동 알약은 시각과 같은 줄에 산다 —
  줄이 늘지 않는다"인데, 420px에서는 트레이가 접혀 **86.4px**(같은 문장의 트레이 없는 띠는 65.6px)
  = **+22px**. §5-1은 "좁으면 접힌다"고 적어 두었으나 §4-1은 그대로다. 두 절을 화해시켜야 한다
  ("스레드 폭에서는 줄을 안 늘린다"로 한정하거나, 좁은 폭에서 알약을 아이콘 버튼으로 축약).
- 흠 4 — 지속성 경계(transient 제외)는 옳지만, **같은 사건이 토스트로도 뜨고 스레드에도 남는
  경우의 규약이 없다**(문서 §7-3이 스스로 인정). 이건 결함이라기보다 **다음 라운드 필수 항목**이다.

## 6. 경계 밖 수정 2건

### 6.1 `Cargo.toml` 피처 5개 — **문제 없음(의미), 마찰 있음(형식)**

`Win32_Graphics_Dwm` · `Win32_UI_Shell` · `Win32_System_RemoteDesktop` · `Win32_System_Registry` ·
`UI_ViewManagement`. 피처는 가산적이고 크레이트 전역에서 합쳐지므로 **다른 조각과 의미 충돌이 없다.**
남는 위험은 **같은 배열 끝에 셋이 동시에 줄을 붙일 때의 텍스트 충돌**뿐이고, 이건 규약으로 푼다
(피처 목록을 알파벳 정렬 + 한 줄 한 항목 — 이미 그 형태다).
`UI_ViewManagement`만 성격이 다르다(WinRT 투영) — 대안(`SystemParametersInfo(SPI_GETCLIENTAREAANIMATION)`
등)은 배터리 절약을 반영하지 못하므로 **채택 판단은 옳다.**

### 6.2 `#[path = "glass.rs"] pub mod glass;` (win.rs) — **되돌릴 것을 권고**

이유 셋:

1. **근거가 사실과 반대다.** "main.rs는 M2·M-CRASH가 함께 만지는 파일이라 한 줄도 충돌"이라 했는데,
   `git log`상 **main.rs 4커밋 / win.rs 6커밋**으로 **win.rs가 더 뜨겁다.** 그리고 이 커밋은
   win.rs를 **세 군데** 고쳤다(모듈 부착 + arm 2곳 + clear). 회피 목적이 달성되지 않았다.
   main.rs에서 바뀌는 것은 `mod` 4줄짜리 블록에 한 줄 추가 — git이 가장 잘 병합하는 모양이다.
2. **조용한 중복 모듈 위험.** 다음 사람이 자연스럽게 `mod glass;`를 main.rs에 넣으면
   같은 파일이 **두 모듈로 컴파일**된다. 스크래치 크레이트로 확인했다(rustc 1.96.1, **경고 0**):

   ```
   via w (win::glass): 1     ← #[path]로 붙인 쪽 카운터
   via w (win::glass): 2
   via crate::a       : 1     ← main.rs가 붙인 쪽은 **독립 카운터**
   ```
   glass.rs로 옮기면 `WINDOWS`·`STARTED`·`LAST_OK`·`REASSERTS`가 **두 벌**이 된다 —
   감시 스레드 2개, `arm()`한 창을 `clear()`가 못 지우고, `health()`가 다른 세계를 본다.
   `#![allow(dead_code)]`가 붙어 있어 "안 쓰는 쪽" 경고도 안 뜬다.
3. **경로가 소유를 오해하게 만든다.** 실제 경로는 `crate::win::glass`인데 문서·주석은 `glass.rs`로만
   부른다. D1(부팅 페이로드)처럼 win.rs 밖에서 부를 일이 생기면 바로 걸린다.

**제안 D7**: `main.rs`에 `mod glass;` 한 줄(알파벳 순 `crash` 다음), win.rs의 `#[path]` 블록 삭제,
호출부는 `crate::glass::arm/clear`. 충돌 위험은 한 줄이고, 위 셋이 사라진다.

- **render-lost 합성 실패.** 두 레버(WS_EX_LAYERED, ACCENT_DISABLED)로는 아크릴이 안 죽었다.

## 8. 가장 큰 격차 하나

> **"못 살리면 폴백"이라는 약속이 실제로는 "부팅 순간에만 폴백"이다.**
> 추가 채팅 창과 크래시 복구 재로드는 폴백을 영구히 못 받는다(events=0 실증).
> 방어의 값어치 전체가 이 한 구멍에 매달려 있다 — 재단언이 82ms에 되살리는 것은
> **되살릴 수 있는 경우**뿐이고, 되살릴 수 없는 경우를 받아 내라고 만든 장치가
> 정작 그 두 경로에서 없다. `ipc.rs`를 안 건드리려고 풀 경로를 없앤 결정이 원인이고,
> 고치는 데 필요한 것은 이미 있는 기계(`boot_payload_script`)에 **두 줄**이다(§3.1 D1).
