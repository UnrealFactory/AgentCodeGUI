## 3. 공격 — 깨진 것 (심각도순)

### S1 · **치명 · 3.0 전용 회귀** — 되돌리기/삭제가 조용히 **영구 삭제**한다

`file::delete_path` → `trash()`는 `SHFileOperationW` + `FOF_ALLOWUNDO | FOF_NOCONFIRMATION |
FOF_SILENT | FOF_NOERRORUI`다(`crates/ccg-fs/src/file.rs:273-295`).
`FOF_ALLOWUNDO`는 **"가능하면" 휴지통**이다. 휴지통이 없는 볼륨에서는 그냥 지운다.
그리고 `FOF_WANTNUKEWARNING`이 없으니 Windows가 평소 띄우는
"휴지통에 넣기엔 너무 큽니다 — 영구히 삭제할까요?" 경고도 **안 뜬다**.

같은 파일, 같은 경로, 두 앱(휴지통이 없는 `subst X:` 드라이브에서 실측, 2회 재현):

```
3.0   (SHFileOperationW)   ok=true   file_gone=true    휴지통 항목 수 162 → 162   ← 영구 삭제 + 성공 보고
2.6.2 (shell.trashItem)    ok=false  file_gone=FALSE   휴지통 항목 수 165 → 165   ← 거부, 파일 생존
                           err "Failed to perform delete operation"
대조군(보통 C: 볼륨)        두 앱 다 ok=true · 휴지통 +1                          ← 여기선 같다
```

Electron의 `shell.trashItem`은 `IFileOperation` + **`FOFX_RECYCLEONDELETE`**를 쓴다 —
"휴지통에 못 넣으면 지우지 말고 실패하라"가 그 플래그의 존재 이유다. 포팅이 그 보장을 잃었다.

**도달 경로 두 개** — 둘 다 클릭 한 번이다.
- 탐색기 우클릭 → 삭제 (`fs:delete`)
- Git 카드 → 미추적 파일/폴더 **되돌리기** (`git:discard(untracked=true)` → 같은 `delete_path`)

**같은 클래스의 다른 트리거**(문서화된 Windows 동작, 개별 실측은 안 함):
네트워크 드라이브·UNC · 이동식 매체 · 볼륨별 "휴지통을 사용하지 않고 즉시 삭제"(NukeOnDelete=1) ·
휴지통 할당량 초과 파일. 이 머신의 실제 정책은 `max=97433MB nuke=0`(C:)·`max=49703MB nuke=0` —
즉 **이 머신에선 크기 조건은 안 걸리지만 정책 한 칸만 바뀌면 걸린다.**

> 고치는 자리는 한 줄이다: `FOFX_RECYCLEONDELETE`를 못 쓰면(SHFileOperation에는 없다)
> `IFileOperation`으로 가거나, 최소한 `FOF_WANTNUKEWARNING`을 넣고 **삭제 후 실제로
> 휴지통에 들어갔는지 확인**해 아니면 실패로 돌려야 2.6.2와 같은 답이 된다.

### S2 · **치명 · 3.0 전용 회귀** — 이미지 한 장이 창을 **21초** 얼린다

`main.rs:59`는 **동기** `register_uri_scheme_protocol`을 쓴다. tauri 2.11.5가 비동기 변종을
따로 두는 이유가 문서에 그대로 적혀 있다 — *"process the request in a separate thread"*.
동기 핸들러 안에서 `serve::image_response`가 `std::fs::metadata` → `std::fs::read`를 그냥 돈다.

도달 불가 UNC 경로 하나로 실측:

```
크레이트 직접:  serve::image_response("…/%5C%5C10.255.255.1%5Cshare%5Ca.png")  →  21,048 ms
                (이름이 안 풀리는 호스트는 1,265 ms)

살아 있는 앱에서 <img src=…> 한 장을 걸고 창의 메시지 펌프를 두드림
  (SendMessageTimeout WM_NULL, 2s / IsHungAppWindow)

            요청 전            요청 중(1.2s)        요청 중(2.4s)
  3.0       True|6ms|False     FALSE|2016ms|False   FALSE|2013ms|TRUE   ← 창이 실제로 "응답 없음"
  2.6.2     True|7ms|False     True|6ms|False       True|6ms|False      ← 멀쩡
```

2.6.2의 핸들러는 `protocol.handle(async …)` + `fs.promises`라 메인 프로세스를 안 잡는다.

지금 당장 터지진 않는다 — 렌더러가 아직 리터럴 `ccg-img://`를 만들어 이 핸들러에 안 닿기
때문이다(리포트 §5-A). 하지만 **리포트가 남긴 그 한 줄**(`imageSrc()`를
`http://ccg-img.localhost/…`로)을 붙이는 순간, 에이전트가 만든 파일 목록에 UNC 경로가 하나만
섞여도 창이 통째로 멈춘다. `ccg-page`가 올라오면 표면이 더 넓어진다.

### S3 · **높음 · 3.0 전용 회귀** — `ccg-img`에 `ACAO: *`를 새로 붙였다 (JS가 바이트를 읽는다)

먼저 **"경로 탈출"은 오해다.** `serve.rs`는 애초에 루트를 두지 않는다(주석에 명시).
탈출할 담이 없으니 탈출도 없고, 그건 2.6.2도 같다. 확장자 화이트리스트도 같은 표다:

```
png                    served  image/png
secret.json            404                       ← 비이미지 확장자는 안 나간다
secret.json.png        served  image/png  본문 = {"token":"SUPERSECRET"}   ← 이름만 맞으면 나간다(2.6.2 동일)
디렉터리 / 없는 파일    404
../.. 조작             해당 없음(절대경로 스킴)
실홈 accounts.json      404
ADS(a.json:s.png)      served  ← 이미 쓴 스트림만. 새 권한 아님
63MB png               served (66,060,288B)      65MB png → 404       ← 64MB 캡 동작
```

**바뀐 건 헤더 한 줄이다.** `main.rs:66`이 `ACCESS_CONTROL_ALLOW_ORIGIN: *`를 붙였고
2.6.2의 `ccg-img` 응답에는 그 헤더가 없다. 결과(살아 있는 앱에서 `fetch`):

```
3.0   origin http://tauri.localhost → fetch("http://ccg-img.localhost/<abs>")  → 200, 16 bytes 읽힘
                                       fetch(secret.json.png)                   → 200, 본문 그대로 읽힘
2.6.2 origin file://                 → fetch("ccg-img://local/?p=<abs>")        → TypeError: Failed to fetch
                                       fetch(secret.json.png)                   → TypeError: Failed to fetch
```

`serve.rs` 주석의 정당화("같은 렌더러가 `fs:read-file`로 이미 임의 경로를 읽는다")는
**렌더러 오리진에만** 맞는 말이다. ACAO를 열면 청중이 바뀐다 — sandbox iframe·SVG 문서·
앞으로 올 `ccg-page` 미리보기처럼 **Tauri IPC가 없어 `fs:read-file`을 못 부르는 컨텍스트**가
디스크의 아무 `*.png`/`*.svg`를 바이트로 읽게 된다. 리포트 §5-D는 새 것으로 64MB 캡만 적었다.

### S4 · **높음 · 2.6.2와 공유** — 잠긴 파일에 되돌리기 = 인덱스만 지우고 멈춘다

`git::discard`는 `git checkout HEAD -- rel`이 실패하면 "HEAD에 없던 새 파일"로 보고
`git rm --cached` → 휴지통으로 간다. 그런데 checkout이 실패하는 이유는 그것만이 아니다.
다른 프로세스가 파일을 배타적으로 열고 있으면(빌드 락·엑셀·에디터):

```
git checkout HEAD -- locked.txt   →  error: unable to unlink old 'locked.txt': Invalid argument
git rm --cached -f -- locked.txt  →  성공  (인덱스만 만지니까)
trash(locked.txt)                 →  실패 (잠겨 있으니까)
결과:  discard_ok=false  "파일을 휴지통으로 보내지 못했어요"
       파일은 그대로 있는데  **인덱스에서 사라졌다**
       git status →  D:locked.txt  +  A:locked.txt(untracked)   ← 유령 두 행
```

사용자에게 뜬 문구는 휴지통 얘기뿐인데, 실제로 바뀐 건 **git 인덱스**다. 다음 커밋에
그대로 태우면 파일이 저장소에서 삭제된다. 코드가 2.6.2와 구조적으로 같으므로(같은 4줄)
회귀는 아니지만, **"되돌리기가 더 많이 파괴하는 자리"는 여기 하나뿐**이고 이번 라운드는
이 자리를 시험하지 않았다(§6 격차).

### S5 · **중간 · 2.6.2와 공유** — 32MB 캡이 "거짓말은 안 한다"는 리포트 문장이 틀렸다

리포트 §3: *"넘으면 자식을 죽이고 실패로 돌려준다(반쪽 출력을 파싱해 거짓말하지 않는다)."*
`exec`는 정말 거짓말을 안 한다. 그런데 **`file_diff`가 그 실패를 "HEAD에 없는 파일"로 읽는다.**

35MB짜리 blob이 HEAD에 있고 사용자가 그 파일을 한 줄로 줄인 상태 — 두 앱 모두:

```
{ error: null, tag: "new", add: 1, del: 0, lines: 2 }
```

즉 **70만 줄을 잃은 파일이 "새 파일 +1 −0"으로 그려진다.** 오류도, 빈 화면도 아니고
"멀쩡한 초록 한 줄"이다. 그 카드 옆에 되돌리기 버튼이 있다.
파일을 아예 지운 경우엔 `"내용을 읽을 수 없어요"`가 나오고 **`head_content`가 안 실린다** —
"되돌리기 전에 뭘 잃는지 보여준다"는 계약이 >32MB에서 조용히 꺼진다.

2.6.2(`execFile` maxBuffer 32MB)도 **글자 그대로 같은 답**을 낸다(실측). 회귀는 아니지만
리포트가 이 캡을 3.0의 개선으로 내세우며 붙인 괄호가 사실과 다르다.

### S6 · **중간 · 2.6.2와 공유** — 되돌리기 한 행이 서브트리 통째다 / 루트도 통과한다

`git status --porcelain=v2`는 미추적 폴더를 **한 행**(`newdir/`)으로 준다. 실측:

```
git status 행:   A:newdir/(u)        ← 카드에 한 줄
discard(newdir, untracked=true) →  ok  ·  newdir/ 이하 nested/b.txt까지 통째로 휴지통
```

두 앱 동일(2.6.2도 `shell.trashItem(dir)`). **정상 반경의 나머지는 전부 옳았다** —
이건 반드시 적어 둔다:

```
추적 파일 되돌리기:  워크트리 "orig" 복원 · 인덱스도 "orig" 복원(스테이징까지)
다른 파일의 스테이징: "other-staged" 그대로 — 안 건드림   ✅
새로 add된 파일:      인덱스에서 빠지고 파일은 휴지통       ✅
../ 탈출:            거부 "잘못된 경로" · 바깥 파일 생존    ✅
절대경로 주입:        거부 "잘못된 경로"                    ✅
index.lock 있을 때:   commit·discard 모두 실패, **파일 안 지움**(rm --cached도 같이 실패)  ✅
```

경계 하나: `discard(cwd, ".", untracked=true)`는 `abs_of`를 통과해 **저장소 폴더 전체를
휴지통으로 보낸다**(실측 `repo_still_there:false`). 2.6.2도 `absOf(root,'.') === root`로 같다.
렌더러는 `f.path`만 보내므로 제품에서 도달 불가지만, 가드가 없다는 사실은 남는다.

### S7 · **중간 · 리포트 정확도** — 정렬 잔여 클래스 2개가 빠졌다 (§4에서 상술)

### S8 · **낮음** — 오류 문구가 날것으로 새어 나온다 (두 앱 다, 문자열만 다름)

```
없는 드라이브 쓰기   3.0 "지정된 경로를 찾을 수 없습니다. (os error 3)"   2.6.2 "ENOENT: no such file or directory, open 'Z:\nope\nope.txt'"
권한 없는 파일 쓰기   3.0 "액세스가 거부되었습니다. (os error 5)"
index.lock           양쪽 "Unable to create 'C:/…/.git/index.lock': File exists."
바뀐 게 없는데 커밋   양쪽 **"On branch main"**   ← git stdout 첫 줄이 그대로 에러로 뜬다
```
`(os error N)`은 사용자 문구에 있을 물건이 아니다. "On branch main"은 두 앱 공통의
`errLine(stderr, stdout)` 폴백이 만든 것으로, 되돌리기·커밋 카드에 그대로 뜬다.

### S9 · **낮음** — `git:status`가 2.6.2보다 1.5~2배 느리다

2.6.2는 `status`와 `remote`를 `Promise.all`로 **동시에** 부르고(`git.ts:161-164`),
3.0은 순차다(`git.rs:334-341`). 마운트 직후 앱을 새로 띄워 3라운드 실측(40파일 클린 레포):
**3.0 61·80·132 ms** / **2.6.2 44·66 ms**(라운드 2·3 — 라운드 1은 tail에서 잘려 기록 못 함).
체감 임계는 아니지만 스트립이 매 턴 폴링하는 자리다. 이 수치는 evidence JSON에 없다(콘솔만).

## 4. 정렬(collate) — 43.5%는 실사용에서 체감되나

빌더 하네스는 커밋에 없어서 **내 교차검증기를 새로 썼다**
(`critic-m6-collate.mjs` + `critic-m6-collate.rs`: 같은 이름 집합을 Rust `name_cmp`와
Node `localeCompare(undefined,{sensitivity:'base'})`로 각각 정렬해 세트 단위 대조).

| 풀 | 세트 | 불일치 | 판정 |
|---|---|---|---|
| **이 머신의 진짜 폴더/파일 이름**(`C:\Code`·레포·홈·문서·다운로드·바탕화면에서 수집) | 600 | **1 (0.2%)** | 그 1건도 `App` vs `app` — **리포트가 이미 문서화한 대소문자 tie-break**(NTFS 한 폴더에 공존 불가) |
| 리포트가 말한 "실제 프로젝트 이름 꼴" 30개 | 600 | 23 (3.8%) | 전부 같은 대소문자 tie-break(`app/APP`·`bench/Bench`를 내가 일부러 같이 넣었다) |
| **한글·이모지·전각·부호가 섞인 "어렵지만 실제 있을 법한" 이름 32개** | 600 | **192 (32%)** | ↓ |
| 무작위 문자 수프 | 400 | 90 (22.5%) | 리포트의 43.5%보다 낮게 나왔다(내 풀 구성이 달라서) |

**판정 — 두 갈래로 갈린다.**
- **평범한 프로젝트 폴더에서는 체감 안 된다.** 실제 머신 이름 600세트에서 진짜 불일치 0.
  리포트의 "실파일명 꼴 불일치 0" 주장은 **성립한다.**
- **CJK가 섞인 이름에서는 눈에 보인다.** 그리고 원인 클래스가 **리포트가 적은 것과 다르다.**
  클래스별 쌍 대조(`critic-m6-collate2.mjs`):

```
MISMATCH  전각 라틴      2/3   full2.txt < ＦＵＬＬ.txt   (ICU: ＦＵＬＬ.txt < full2.txt)   ← 리포트에 없음
MISMATCH  가나 상호      1/2   ひらがな < カタカナ         (ICU: カタカナ < ひらがな)         ← 리포트에 없음
MISMATCH  한자↔한글      1/3   자.md < 字.md              (ICU: 字.md < 자.md)             ← 리포트가 적은 클래스
  match   2글자 확장(æ/ß) 0/3                                                              ← 리포트가 적었지만 내 쌍에선 안 나옴
  match   가나↔라틴 · 그리스·키릴 · 이모지↔부호 · 대소문자 · 숫자문자열 · 한글내부 · 문장부호 · Latin-1 접기
```

전각 라틴은 실제로 튄다: ICU는 `ＦＵＬＬ`을 `full`로 접어 f 자리에 두는데, `collate.rs`는
코드포인트 그대로 라틴 계층 **맨 뒤**(일본어 가나보다도 뒤)로 보낸다. 전체 목록 정렬에서
`ＦＵＬＬ幅.txt`가 `ÖNORM.pdf` 옆에서 목록 끝으로 **다섯 칸 이동**하는 걸 확인했다.

→ **§4의 "둘 다 실사용 파일명에서 0/600으로 안 나오는 조합"은 과소 서술이다.**
결론(근사로 남겨도 된다)은 유지할 만하지만, 잔여 목록에 **전각 라틴 · 가나 상호**를 넣어야 한다.

## 6. 가장 큰 격차 — 파괴 경로에 화면 증거가 **0**이다

이번 라운드에서 2.6.2와 **의미가 실제로 달라진 유일한 지점**은 휴지통 보장(S1)이고,
그 자리에 닿는 화면은 `git-discard-confirm`(변경 되돌리기 확인)과 탐색기 삭제 카드다.
그런데 이번 M6 증거는 그 자리를 **한 번도 안 밟았다**:

- `bench/screens.mjs`는 `git-discard-confirm`·`git-switch-confirm`을 **skip**한다
  (사유: *"지금 트리는 다른 에이전트가 동시 편집 중 — 오조작 한 번이 남의 작업을 파괴한다"*).
  타당한 사유지만, 결과적으로 **가장 위험한 카드가 A/B에서 통째로 빠졌다.**
- `bench/m6.mjs`의 `channel-audit`은 `git:discard`를 **존재하지 않는 파일**로만 두드린다
  (`rel: 'no-such-file-m6'`) — 채널이 살아 있다는 것 말고는 아무것도 말하지 않는다.
- `file-ops-write-path`는 `deletePath`를 부르지만 **삭제됐는지만** 보고
  **어디로 갔는지**(휴지통인지 영구인지)는 안 본다.

m6.mjs는 이미 `%TEMP%`에 **자기 클론**을 만든다 — 남의 트리를 건드릴 위험 없이
되돌리기·삭제를 진짜로 눌러 볼 수 있는 안전한 무대가 이미 서 있다. 그런데도 그 무대에서
파괴 동작을 안 눌렀다. 다음 라운드가 채워야 할 한 칸은 그거다:
**"삭제한 파일이 휴지통 항목 수를 +1 시키는가"**를 A/B로 세는 검사 하나.

| R-1 | `bench/m6.mjs`가 **살아 있는 실 레포**를 클론한다. 리포트의 `listFiles 773`·`커밋 상세 2343자`는 그 시점 HEAD의 값이라 다음 실행에서 재현되지 않는다(내 값 790·241). A/B 동수는 유지되지만 **회귀 기준선으로는 못 쓴다** — 고정 픽스처 레포가 필요하다 |
| R-2 | `ab.mjs`의 `viewer-loading` 뒤에 **두 앱 다** CDP 캐스케이드 실패가 붙는다(2.6.2는 재현성 있게 90s 굳음). 이 화면 뒤의 결과는 격리 재시도로 확인해야 신뢰할 수 있다 — 통과 실행만 보면 3.0에 없는 결함 4건이 초록/빨강으로 잘못 남는다 |
| R-3 | `exec()`의 stderr 스레드는 `take(256KB)`에서 읽기를 멈추고 파이프를 닫는다. 256KB 넘는 stderr를 쓰는 git(대량 warning)이 오면 EPIPE로 죽거나 예측 못 할 상태가 된다. 실측으로 못 만들었다(git이 그만큼 안 뱉는다) |
| R-4 | `log()`는 `%s`(subject)에 `\x1f`가 들어가면 필드가 밀린다. 2.6.2와 같은 구조라 회귀는 아니고, 재현하려면 악의적 커밋 메시지가 필요하다 |
| R-5 | 정션은 두 앱 모두 `dir:false`로 나와 **탐색기에서 못 펼치고 뷰어로도 못 여는 유령 행**이 된다(열면 "파일이 아니에요"). 멘션 목록에서도 그 아래가 통째로 빠진다. UE 프로젝트처럼 정션을 쓰는 트리에서 실사용 문제지만 **2.6.2부터의 동작**이라 이번 판정에서 뺐다 |
| R-6 | 내 `subst` 실험은 **휴지통 없는 볼륨**의 대표로 골랐다. 네트워크·이동식·NukeOnDelete=1·할당량 초과는 문서상 같은 클래스지만 개별 실측은 안 했다 |
