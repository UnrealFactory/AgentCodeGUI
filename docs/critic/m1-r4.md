### 1.3 ★ 신규 블로커 — 2.5~4.0초 사이의 두 번째 크래시는 아무도 안 받는다

`src-tauri/src/crash.rs`의 상태 기계에 **1.5초짜리 사각지대**가 있다.

```
crash.rs:58   const DEBOUNCE_MS: u64 = 4000;        // 이 안에 온 사건은 버린다
crash.rs:333  std::thread::sleep(Duration::from_millis(2500));  // 이때 RECOVERING 해제
```

- `t+0` 크래시 → 복구 시작, `LAST_AT = t`, `RECOVERING = true`
- `t+2500` → `RECOVERING = false` (감지 재개)
- `t+2500 ~ t+4000` → 새 크래시가 오면 `recover()`가 **디바운스 분기에서 조용히 반환**한다.
  `RECOVERING`도 아니고 재크래시로 세지도 않는다. **그냥 없던 일이 된다.**

실측 로그(A2a, `crash-attacks.json`의 `rekill-gap-3000`):

```
armed ×3
process-failed → recover-begin → reloaded ×3 → process-failed ×2 → recover-done   ← 1차: 정상 복구
process-failed × 3                                                                 ← 2차: recover-begin 없음
```
`recoverBeginCount: 1`, 창 3개 전부 화면에 남고 `mounted 0/3`. **R3 §7.3이 보고한 그 상태다.**

**A3이 더 나쁘다.** 렌더러가 죽고 3.3초 뒤 브라우저가 죽으면:

```
process-failed ×3 → recover-begin → reloaded ×3 → recover-done → process-failed ×3 → watchdog-browser-gone
```
`watchdog-browser-gone`까지 **찍혔는데 복구가 없다.** 원인이 코드에 그대로 있다:

```rust
// crash.rs:231-234
log("watchdog-browser-gone", …);
BROWSER_PID.store(0, Ordering::SeqCst);   // ← 먼저 지운다
recover(&app, Cause::BrowserGone);         // ← 디바운스로 버려질 수 있다
```
감시자는 **recover()가 받았는지 확인하지 않고 자기 감지 상태를 소거한다.** 그 뒤로는
`pid == 0 → continue`라 **감시 스레드가 영구 실명**한다. 브라우저가 죽었으니
`ProcessFailed` 경로도 못 온다 = 남은 감지 수단이 없다. 유령 3개 + 복구 불가 고착.

**현실성**: 높다. 복구가 하는 일이 `reload()`인데, 렌더러를 죽인 원인이 콘텐츠라면
(이 프로젝트의 알려진 크래시 계열 = 큰 diff/DP OOM, 메모리 `crash-hardening-pass`)
**다시 로드하면 몇 초 안에 같은 자리에서 또 죽는다.** 즉 사각지대는 예외 상황이 아니라
결정성 크래시의 **기본 경로**다. `MAX_RECOVERIES=5` 루프 가드는 6초 이상 간격일 때만
발동한다(A4에서 확인) — 빠른 재크래시는 세지도 않고 유령이 된다.

### 1.4 복구가 잃는 것 — M1 수준으로 허용 가능한가

| 항목 | 결과 |

| 스레드 내용(대화) | **복구됨** — 디스크에서 다시 읽는다(msgCount 4 · panels 4) |

| 창 위치·크기·개수 | 유지(렌더러 사망 팔은 창을 안 부순다) |
| 네이티브 다이얼로그 | **고아로 남는다**(A5) — 사용자가 폴더를 골라도 받을 사람이 없다 |

초안이 사라지는 건 설계상 그렇다 — `app/src/components/MultiAgent.tsx:112`

**복구 정책이 `reload()`인 이상 필연**이다.

**판정: M1 수준에서 허용 가능.** 근거 —
(a) 대안(창 재생성)은 더 많이 잃는다, (b) 2.6.2는 애초에 복구 자체가 없어 파리티 회귀가
아니다, (c) 잃는 것이 "몇 초 전에 타이핑하던 한 줄"이다.
**단 두 가지는 M1에 적어 둘 것**: ① 다이얼로그 고아는 유령 UI 계열이라(사용자가 실물
버그로 제보한 그 계열) M2 이전에 닫아야 한다 — 복구 시 열린 네이티브 다이얼로그를
같이 닫는 한 줄이면 된다. ② **진행 중인 엔진 턴이 복구를 넘어 살아남는지는 미검증이다**
(내 픽스처는 엔진을 안 띄운다). 스트리밍 중 렌더러가 죽었을 때 `reload()` 뒤 턴에
다시 붙는지는 M1 종료 전에 반드시 실측할 것 — 여기서 지면 "복구했다"는 말이 거짓이 된다.

## 2. NetSvc2 재판정 — 결론은 유지, 논거는 반박

### 2.1 ★ 지정된 재판정 명령이 무효다

§2.4와 §8은 재판정 절차를 이렇게 못박았다:

> `node bench/fpsab.mjs --rounds=4 --trials=3` … 지금 상태로는 명령 한 줄이 판정을 끝낸다.

**그 한 줄은 이제 레버를 자기 자신과 비교한다.** `bench/fpsab.mjs:40-43`의 팔은

```js
{ name: 'control', extraEnv: {} },                                              // 제품 기본값
{ name: 'lever',   extraEnv: { CCG_WEBVIEW_ENABLE_FEATURES: 'NetworkServiceInProcess2' } }
```

인데 리드가 `c673b15`에서 그 feature를 `FEATURES_ON_ADOPTED`에 넣었으므로
**control이 이미 레버를 켜고 있다.** `lever` 팔은 켠 위에 또 켜는 무동작이다.
(리드 본인의 재판정은 `307d94a` = 채택 **직전** 커밋에서 돌아 유효했다. 무효가 된 건
그 커밋 이후 — 즉 §8이 크리틱에게 지시한 그 명령이 지시받은 시점부터 무효였다.)

### 2.2 ★ §8이 인용한 짝지은 차는 인용한 파일에 없다

§8은 채택 근거로 이렇게 적었다:

> 짝지은 차 중앙: simple **+0.05** / load **−0.6**fps (라운드 간 노이즈 ±1 안).
> 드랍 프레임: 대조군 12시행 총 2, 레버 팔 **동등**.

같은 문단이 근거로 지목한 파일(`bench/results/fps-ab.json`, 리드 재실행분)의 실제 내용:

| | 파일의 값 | §8의 서술 |
|---|---|---|
| `pairedSimple` 델타 | **−2.1 · −2.4 · +0.9 · −0.8** → 중앙 **−1.45** / 평균 −1.1 | +0.05 |
| `pairedLoad` 델타 | −0.4 · −1.1 · +0.1 · −1.0 → 중앙 **−0.7** / 평균 −0.6 | −0.6 |
| 드랍 프레임(simple) | 대조군 **2** vs 레버 **4** | "동등" |
| 드랍 프레임(합) | 대조군 3 vs 레버 **5** | — |
| "노이즈 ±1 안" | simple 델타에 **−2.1 · −2.4** 가 있다 | ±1 |

load의 −0.6은 **평균**이라 맞다. 그러나 simple의 +0.05는 중앙값도 평균도 아니고
(−1.45 / −1.1) **파일의 어떤 통계와도 일치하지 않는다.** 실제 파일은 4라운드 중 3라운드에서
레버가 더 낮고, 가장 큰 두 편차가 둘 다 음수다. 즉 **리드가 채택 근거로 든 "짝지은 차 ≈ 0"은
리드 자신의 측정이 지지하지 않는다.**

(참고: §2.3 본문 표의 값(+0.1 / +0.15, 드랍 7 대 5)은 **빌더** 실행분이고 그것과도 다르다.
빌더 실행분은 지금 파일에 없다 — §3.1 참조.)

### 2.3 그럼 레버는 해로운가 — **아니다.** 그리고 그 판정에는 노이즈 바닥이 필요했다

§2.1의 사고 덕분에 뜻밖의 선물이 생겼다: **동일 구성 두 팔의 짝지은 차**,

### 2.5 §8 채택 논리의 구멍 (요약)

1. **인용한 수치가 파일에 없다**(§2.2) — 이게 제일 크다. 근거 문서와 근거 파일이 어긋나면
   다음 사람이 되돌릴 수 없다.
2. **노이즈 바닥을 재지 않고 "차 ≈ 0"을 결론으로 썼다**(§2.3). 널 실험(동일 구성 A/B) 없이

3. **재판정 절차를 채택과 함께 무효화해 놓고 그대로 지시했다**(§2.1).
4. 사소하지만: `drop0`·`fps60` 판정이 `bench/lib.mjs`의 `median()`을 쓰는데 그 함수는

   `fps60: true`가 될 수 있다 — 절대 게이트가 반올림으로 통과할 수 있는 구조다.

### 3.3 신규 결함 — `median()`이 짝수 길이에서 정수로 반올림한다

```js
// bench/lib.mjs
export function median(nums) {
  const a = nums.filter((n) => n != null).sort((x, y) => x - y)
  if (!a.length) return null

}
```

## 4. ★ `paintMs 0.45`는 대칭 지표가 아니다

- 2.6.2의 스플래시 창은 `ready-to-show`에서 뜬다 = **뜬 순간 이미 그려져 있다**
  (R3 크리틱 §4.3도 이 사실을 적어 놓고, 그 다음 줄에서 메인 창 `paintMs`를 "대칭 지표"라고
  불렀다 — R3 크리틱의 자기모순이다. R4는 그걸 그대로 물려받았다).
- 2.6.2 스플래시의 first-paint는 4회 중 1회만 잡혔다(스플래시가 빨리 닫혀 폴링이 놓친다).
  그래서 **371~423ms 구간**으로 읽는 게 정직하다. 어느 쪽이든 비는 **0.65~0.74**다.

### 4.3 판정

> **`paintMs 0.45`는 사용자 보고에서 빼라.** 대칭 짝은 **첫 픽셀 0.65~0.74** ·
> **본 UI 0.79**이고, **≤0.5를 넘긴 콜드 지표는 하나도 없다.**
> R4 §0의 "3.0의 최대 승점(paintMs 0.45)" · §4.3의 "같은 데이터 안에 3.0의 최대 승점이
> 있었다" · R3 크리틱 §11.1-5("paintMs를 대표 지표로 승격")는 전부 이 오류 위에 있다.

**남길 것은 있다**(과소평가도 하면 안 된다): 3.0은 **274ms에 풀사이즈 본 창이 스플래시를
띄우고 348ms에 UI가 선다.** 2.6.2는 371ms에 300×240 카드가 뜨고 443ms에 본 창으로
**튄다.** 3.0이 더 빠르고 전환도 없다 — 그건 진짜 승점이다. 다만 그건 **0.79배**지
0.45배가 아니고, "≤0.5 규칙을 넘긴 유일한 지표"라는 문장은 성립하지 않는다.

**제안 diff**
```js
// bench/coldstart.mjs — paintMs가 무슨 픽셀인지 파일에 남긴다(§9-5와 같은 처방).
+// 2.6.2의 스플래시는 별도 `data:` 창이라 connectMainPage가 **제외**하고,
+// 3.0의 스플래시는 메인 문서 안 오버레이라 **포함**된다. 두 앱의 paintMs는
+// 서로 다른 사건이다 — 대칭 비교는 rootMs이거나 '스플래시 대 스플래시'다.
+  paintNote: '3.0=스플래시 오버레이 첫 픽셀 / 2.6.2=스플래시가 걷힌 뒤 본 창 첫 픽셀 — 직접 비교 금지',
```
