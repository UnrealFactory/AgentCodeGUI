# R28e 「WFIRE」 확인 크리틱 R1 — 판정문

> 대상: `61d818a` *R28e WFIRE R1 — 상한의 단위를 바꾼다*
> 브랜치 `feature/3.0.0-beta` · 판정자는 코드를 고치지 않는다.
> **빌더 보고서·커밋 메시지를 근거로 쓰지 않았다.** 아래 숫자는 전부 내 손으로 빌드·주행한 값이다.

## 0. 결론

**합격.** 체크리스트 다섯 항목이 전부 내 계기에서 초록이고, 겨눈 격차(12시간 71발)는
**내가 만든 독립 계기 + 부모 커밋 대조군**으로 71 → 2가 재현된다. 지켜야 할 반대편
(창 이동 밤샘 7발·헛발질 2발)도 R28d와 **한 발도 다르지 않다**.

남은 최대 격차는 빌더가 「미완 1」로 신고한 그 자리인데, **신고 내용이 실앱에서는 더 나쁘다**:
에피소드 예산은 엔진뿐 아니라 **렌더러 축에서도** 재시작을 못 넘는다(§4.1). 다만 71발 축의
천장은 `attempts`라 재시작 1회의 손해는 +2발이고, 그 성질은 R28d에서도 같았다 — 회귀가 아니다.

## 2. 체크리스트 실측

### 2-1) 시각 미상 축 12시간 대본 셋 — 총량이 예산 이하인가 ✅

같은 probe · 같은 대본 · 다른 커밋:

| 12시간 대본(배너형 = 꼬리 없음) | **R28d**(`61d818a^`) | **R28e**(HEAD) |
|---|---|---|
| Q2 어시스턴트 텍스트 한 줄 + 즉사 | **71발** · attempts 0 · 안 접힘 · 공지 없음 | **2발** · attempts 2 · ready+paused · 공지 있음 |
| Q3 도구 하나 열고 결과 없이 즉사 | (동형) | **2발** · attempts 2 · ready+paused |

착지 공지도 실물로 잡았다 — `자동으로 이어서 보낸 턴이 계속 한도에 막혀서 자동 재개를 멈췄어요 …`.

**전조합 훑기**(수명 8종 × roll 4종 × 산출 2종 = 40판, 각 24시간):
HEAD **최악 12발**(전 조합 예산 이하) / R28d **최악 143발**(= 12시간 71발의 24시간 값).
「둘 중 하나도 안 무는 사각」은 안 나왔다.

### 2-2) 진짜 일한 밤샘 연속은 안 잘리는가 ✅ (단, 유효 범위는 60시간)

### 2-3) 헛발질은 2발에서 접히고 버튼이 뜨는가 ✅

## 3. 장치 자체에 대한 판정

두 장치가 **서로의 사각을 덮는다**는 주장은 내 계기에서도 성립한다:

* 수명만 있고 예산이 없으면 → 「산출 흘리며 천천히 죽는 턴」이 20시간 **39발**(대조군 실측).
* 예산만 있고 수명이 없으면 → 즉사 축이 예산 천장(12발)까지 가고 `attempts`는 영영 0.
* 둘 다 있으면 → 즉사 2발 / 천천히 죽음 12발 / 진짜 작업 무제한(≤60시간).

`MIN_WORK` 문턱의 방향도 안전한 쪽이다: **모르면 인정하지 않는다**(`auto_resume_fired_at`이
없으면 = 우리가 쏜 턴이 아니면 「일했다」가 아니다). 상한이 「모른다」로 지워지지 않는다.

## 4. 남은 격차

### 4.1 (최대) 에피소드 예산이 프로세스 재시작을 못 넘는다 — **두 축 다**

빌더는 이것을 「엔진만의 문제이고 렌더러는 `sanitizeHold`가 복원한다」로 신고했다.
**실앱에서는 그 절반이 성립하지 않는다.**

* 엔진: `ReloadHold`에 `attempts`도 `fires`도 없다. **실측** — 예산을 다 쓴 대본을 새 런타임에
  `reload_state`로 재장전하니 20시간 **12발 재충전**.
* 렌더러: `sanitizeHold`의 새 `fires` 복원은 **실앱에서 도달 불가**다.
  `limitResume.hold` pref를 쓰는 곳은 `App.tsx` 본채팅 하나뿐인데, 그 훅은 늘 `managed`다 —
  `ccg_store::status::empty_lite`와 `engine/lite.rs`가 **조건 없이** `resumeOwner:"engine"`을
  싣기 때문이다(실측: `engineOwnsResume(empty_lite행) = true`, `engineOwnsResume(live lite) = true`).
  `managed`면 장전 자체를 안 하므로(`useLimitResume`의 `if (o.managed) return`) 그 pref는 늘 비고,
  복원 분기는 영영 안 돈다. 렌더러가 실제로 표를 드는 표면(멀티 패널·추가 채팅 창·팝아웃)은
  애초에 영속을 안 한다(설계상 런타임 전용).

즉 **재시작 한 번 = 예산 통째로 재충전**이 두 축의 공통 착지다.
다만 71발 축(즉사)의 천장은 `attempts`이고 그 값도 R28d의 `ReloadHold`가 이미 0으로 놓고 있었으므로
재시작 1회의 실손해는 **+2발**이다(천천히 죽는 축에서만 +12발). **회귀는 아니고, 71발의 부활도 아니다.**
보고서 §미완 1의 문장은 고쳐 적어야 한다.

`ma:dispose`(패널 자리 접기)·채팅 삭제도 슬롯을 거두므로 같은 재충전 문이다.

### 4.2 「밤샘은 안 잘린다」의 유효 범위는 60시간

실측 120시간 대본(5시간 창 · 4.5시간 작업)이 **12발에서 접힌다**. 하룻밤은 안전하지만
이틀 반짜리 연속 주행은 잘리고, 그때 나가는 문장은 「이 한도 창에서 자동으로 12번 …」이다.
출구(버튼)가 있고 사람이 한마디만 해도 예산이 새로 열리므로 막다른 방은 아니다 —
다만 **불변식이 「안 잘린다」가 아니라 「60시간까지는 안 잘린다」**임을 문서가 그렇게 적어야 한다.

### 4.3 배너 문구가 예산 착지를 구분하지 않는다

엔진은 예산 착지에 정확한 공지를 스레드에 남기지만(실물로 확인), 화면 위 배너는
렌더러 소유 표면에서 `자동으로 이어서 보낸 턴이 계속 한도에 막혔어요`, 엔진 관장 본채팅에서
`한도가 풀렸어요 — 눌러서 이어가기`다. 예산 착지의 턴들은 **일도 했으므로** 전자는 부정확하고,
후자는 「풀렸다」가 조회의 말일 뿐이라 오해를 준다. 본채팅은 스레드 공지가 정확히 나가므로
침묵(D7)은 아니다. `Chat.tsx`는 이번 경계 밖이라 빌더가 안 건드린 것은 타당하다.

### 4.4 계기 잔류물

`cargo test -p ccg-engine`의 수가 228 → 236으로 보인다. 다른 갈래가 수를 셀 때 이 파일을 빼고 세면 된다.
산출 JSON 셋(`docs/critic/limit-engine-critwfirer1.json` · `-long.json` · `limit-codex-critwfirer1.json`)도
미추적으로 남겼다(기준 파일 덮어씀 0).
