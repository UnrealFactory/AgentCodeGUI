## 3. 뮤테이션 — "실측이 잡은 결함 셋"이 정말 잠겼나

보고서 §3·§4가 자랑하는 세 결함에 각각 되돌림을 넣고 테스트를 돌렸다.

| # | 결함 | 뮤테이션 | 결과 |
|---|---|---|---|
| 1 | 결과 카드 두 장 → `ended_turns` | `fail_result`의 `ended_turns.insert(t)` 제거 | **red 2건** — 잠김. 단 **관측 순서 한 갈래만**(§4.1) |
| 2 | `.cmd` shim 인용 → `raw_arg` | `raw_arg` → `arg` | **3/3 green — 뮤테이션 생존** ★ |
| 3 | 소문자 cwd → `to_rel` 재시도 | 재시도 블록 삭제 | **red 1건** — 잠김 |

### ★ ②는 테스트가 못 지킨다

`codex::driver::tests::a_cmd_shim_is_launched_through_cmd_exe`는 `Command::get_args()`를
단언한다. 그런데 **`arg()`와 `raw_arg()`는 논리 인자가 같다** — 차이는 `CreateProcess`에
넘길 커맨드라인을 만들 때만 난다. 그래서 이 단언은 동어반복이고, 회귀가 조용히 통과한다.

실제로 갈리는지는 **띄워 봐야** 알 수 있다(`docs/critic/tools/critic-m4-rawarg.rs`):

```
[raw_arg] status=Some(0) out=SHIM-OK app-server
[arg    ] status=Some(1) out=네트워크 경로를 찾지 못했습니다.
```

즉 결함 자체는 **실재**하고 고침도 **옳은데**, 그 자리를 지키는 것이 없다.
제안: 위 파일처럼 공백 있는 임시 폴더에 `codex.cmd`를 만들어 **실제로 스폰**하는 테스트 한 개.

### 4.1 ★치명 — 엔진 전환이 실패한다 (`switch`)

Claude로 1턴 돌린 채팅에서 picker를 Codex로 바꿔 보냈다(`claude:run{engine:'codex'}` — 렌더러가 보내는 그 모양).

```
afterClaude : engine=claude  spawns=1  session=CL-1
afterCodex  : engine=codex   spawns=2  session=CL-1   state=Idle
codex stdin : {"jsonrpc":"2.0","id":1,"method":"initialize",…}
              {"jsonrpc":"2.0","id":2,"method":"thread/resume",
               "params":{…,"threadId":"CL-1"}}      ← ★ Claude 세션 id
events      : … notice:"엔진이 20초 안에 응답하지 않았어요" · error · result
```

드라이버는 제대로 갈아탔다(`engine=codex`, T17 재스폰 확인). 그런데 `t1_spawn`이
`self.thread.session_id`(엔진 축과 무관한 **한 칸**)를 그대로 `resume`으로 넘긴다
(`runtime.rs:1270-1290`). `build_codex_spawn_spec`은 그 값을 그대로 `CodexPlan.resume`에
싣고(`driver.rs:174-183`), 옮김기가 `thread/resume{threadId: "CL-1"}`을 쏜다.

실 codex는 그 스레드를 모르니 RPC 오류로 거절한다 → `Pending::Thread`의 err →
`fail_result` → **전환 후 첫 턴이 오류 카드로 죽는다.** (내 스텁은 `thread/start`만
기다리게 두었으므로 T3 20초 무응답으로 떨어졌다 — 어느 쪽이든 턴은 못 돈다.)

**반대 방향도 같다.** `driver.rs:103`은 `resume`을 조건 없이 `--resume={r}`로 밀어 넣으므로
Codex→Claude 전환은 `claude.exe`에 **codex threadId**를 준다.

`runtime.rs`를 0줄로 두는 것이 이 라운드의 설계 명제였고, **바로 그 명제가 이 구멍을 만들었다.**
`IdentityField::EngineKind`는 이미 존재하는데 `t17_respawn`이 그것을 보고 스레드를 갈지 않는다.

제안 diff(경계는 리드 판단 — 상태기계 한 줄이거나 셸 한 줄이다):

```rust
// crates/ccg-engine/src/runtime.rs — t17_respawn 안, t1_spawn 앞
if identity.contains(&IdentityField::EngineKind) {
    // 엔진이 갈리면 세션 신원도 갈린다 — Claude의 session_id는 codex threadId가 아니다.
    self.thread.session_id = None;
}
```

재생 잠금도 같이: `codex_replay`에 "claude 세션이 있는 채팅을 codex로 스폰하면
`thread/start`가 나간다(`thread/resume` 아님)" 한 개.

### 4.2 `error` 통지의 turnId 게이트 3종이 통째로 빠졌다

2.6.2 `engine.ts:606-609`는 `error` 통지에 게이트 셋을 건다:

```ts
if (errTurnId && this.endedTurnIds.has(errTurnId)) return   // ① 마감한 턴
if (errTurnId && !this.activeTurnId) return                  // ② 시작 창
if (errTurnId && this.activeTurnId && errTurnId !== this.activeTurnId) return  // ③ 남의 턴
```

3.0 `transcode.rs:727-741`에는 **셋 다 없다.** `ended_turns`는 `on_turn_completed`에서만 본다.
그 결과(전부 실측 재현):

| | 시나리오 | 결과 | 2.6.2 |
|---|---|---|---|
| a2 | `turn/completed{failed}` **먼저**, 늦은 `error` 나중 | **result 2장** | 1장(①) |
| a3 | 성공한 턴 뒤 늦은 `error` | **result 2장**(성공 카드 + 실패 카드) | 1장(①) |
| a5 | 시작 창(턴 채택 전)에 옛 턴의 `error` | **result 1장** — 새 실행이 즉사 | 0장(②) |
| a6 | 지금 턴과 **다른** turnId의 `error` | **result 1장** — 지금 턴이 정착 | 0장(③) |
| g1 | 1턴 실패 정착 → 2턴 스트리밍 중 1턴의 늦은 `error` | **2턴이 즉사** | 0장 |

빌더가 고쳤다고 한 결함 ①은 **관측한 한 갈래(error→completed)만** 막혔다.
2.6.2 주석이 그 자리에 남긴 문장이 정확히 이 위험을 적고 있다 —
*"시작 창에서 받아주면 새 실행이 이전 턴의 오류로 즉사한다."*

`turn/completed` 쪽에도 대칭 구멍이 있다:

| | 시나리오 | 결과 | 2.6.2 |
|---|---|---|---|
| a4 | 같은 `turn/completed` 두 번 | **result 2장** | 1장(`endedTurnIds`를 settle에서 채운다) |
| g2 | 1턴의 늦은 `completed{interrupted}`가 2턴 중 도착 | **2턴이 `aborted_by_user`로 정착** | 무시(engine.ts:597-598) |

제안: `on_turn_completed`가 정착 시 `ended_turns.insert(id)`를 하고(지금은 **읽기만** 한다),
`error` 분기 맨 앞에 위 게이트 셋을 그대로 옮긴다.

### 4.3 stale `turn_id` — 다음 턴의 Esc가 옛 턴을 겨눈다 (g3)

`turn_id`는 `on_turn_completed`/`fail_result`에서만 지워진다. 그런데 **상태기계가 스스로
마감하는 길이 있다** — 보고서 §7이 *의도적으로 다르게 한 것*으로 적은 **무음 턴**
(T8→T10 ≈22초 → T11)이 정확히 그 길이다. 그 뒤 프로세스는 살아 있고(Resident) 다음 턴이
같은 옮김기를 쓴다:

```
[g3] 2턴(tu-2)이 도는 중 Esc → turn/interrupt {"threadId":"th-1","turnId":"tu-1"}
```

`turn/start` 응답의 채택이 `if self.turn_id.is_none()`로 막혀 **tu-2가 영영 안 앉는다.**
실서버는 `-32600 no active turn to interrupt`로 거절하고(§3 실측으로 그 메시지를 확인했다),
`Interrupting`이 6초를 기다린 뒤 **T15 하드 취소 = 프로세스 kill**로 떨어진다.
Claude의 소프트 중단 파리티가 Codex에서만 깨진다.

제안: `turn/start` 응답·`turn/started`의 채택 조건에서 `is_none()` 가드를 빼거나
(2.6.2는 `activeRunId` 가드로 대신한다 — `engine.ts:1662-1663`), 상태기계의 턴 마감을
드라이버가 알 수 있는 신호를 하나 둔다.

### 4.5 서브에이전트 사이드체인 — 닫는 프레임이 없다 (i1·i2)

표의 `(서브에이전트 스레드의 알림)` 행은 `engine.ts:740-828`을 출처로 든다. 그 범위에서
2.6.2는 **4종**을 다룬다(`turn/started`·`item/started`·`item/completed`·`turn/completed`).
3.0 `on_agent_notification`은 **2종**뿐이고 나머지는 `_ => vec![]`다.

```
[i1] subAgentActivity{started}로 Task 행이 열린 뒤
     서브에이전트 스레드의 turn/completed → 프레임 0  ← 행이 안 닫힌다
```

2.6.2 주석이 *"턴 완료가 곧 작업 완료(+소요)"*라고 적은 **주 종결 경로**가 빠졌다.
남은 종결 경로 둘(`subAgentActivity{clos*}` · `collabAgentToolCall.agentsStates`)이 안 오면
Task 도구 행이 원장에 **영구 running**으로 남는다 — 스피너가 안 멈추고 턴 정착이 늘어진다.
(보고서 §7 #6이 "재생만·실물 미관측"으로 등급을 매긴 자리이긴 하다. 다만 그 등급은
"실물을 못 봤다"이지 "옮김이 반쪽"은 아니었다.)

### 4.6 실패 경로 UI — 카드는 한 장, 안내는 정확히 **두 배** (`failui`)

실 0.149.0이 뱉은 프레임 그대로를 가짜 app-server로 재생해 화면까지 밀었다.

```
result 카드 1장 · text "unexpected status 401 Unauthorized: Missing bearer or …"
state Idle · 컴포저 해제 ✓
notification 프레임 10장 → notice 이벤트 20건 → 화면 "Reconnecting" 18줄
```

**"결과 카드 한 장" 주장은 참이다.** 그런데 안내가 정확히 2배로 나온다.
귀속을 따로 쟀다 — Claude 가짜 CLI로 `system/notification` 한 장을 흘려도 **2건**이다.

```
{"claudeNoticeEvents":2,"claudeNoticeInDom":2}
```

원인은 **셸의 이중 경로**다: `wire.rs:870`이 raw 프레임을 `notice`로 옮기고,
동시에 상태기계의 `Frame::Notification → Event::Notice`(`runtime.rs:2099`)를
`hub.rs:867`이 또 `notice`로 팬아웃한다. 둘 다 `73ddb58`(M4 이전)에서 왔다 —
**M4의 결함이 아니라 M4가 처음 크게 드러낸 셸의 결함**이다. Claude는 이 프레임을
거의 안 보내서 여태 안 보였고, Codex는 재시도마다 보낸다(9회 → 18줄).

| **모르는 통지 6종**(신버전 가정) | ✅ 전부 침묵. 그 뒤 정상 스트림이 화면까지 도달(`NEWVER-SURVIVED`) |
| **모르는 서버 요청** | ✅ `-32000 unsupported client request: …`로 **답을 보낸다**(서버가 안 멈춘다) |
| **망가진 프레임 14종**(타입 뒤바꿈·null·배열·음수) | ✅ 패닉 0. `panic="abort"` 릴리스라 여기 한 방이면 앱이 통째로 죽는데, 버텼다 |
| 질문 답 개수 불일치 | ✅ 없는 자리는 빈 배열로 채운다 |
| 턴 없는 중단 · 통지 없는 중단 | ✅ 옮김기가 스스로 마감하지 않는다(상태기계 캡에 맡기는 설계대로) |
| 수용량 초과 | ✅ 안내 한 줄 + `turn/completed`가 카드 **1장**으로 정착 |

한 군데만 흠: `transcode.rs:822`의 `d_in + d_out`이 **체크드 덧셈이 아니다**.
`u64::MAX` 토큰 두 개면 디버그 패닉(릴리스는 랩). 서버가 그런 숫자를 줄 일은 없지만
`saturating_add` 한 글자로 끝나는 자리다. **위생.**

## 5. 옮김표 감사 — 44행 중 5행이 실스펙과 어긋난다

게이트(`frame_map_is_fully_replayed`)는 **`wire` 문자열 키만** 센다 — 재생이
`cover("...")`를 손으로 부르는 장부일 뿐이고 `to`·`src` 열은 **아무도 안 본다**.
그래서 표가 틀려도 44/44는 초록이다. 행별로 `engine.ts`와 대조했다(39행 정확):

| 행 | 표 | 실제 |
|---|---|---|
| `item/started{fileChange}` | `assistant{tool_use **Edit**}` (647-651) | `codex_file_change` (transcode.rs:884). 보고서 §2가 *"Edit이면 diff 조립기가 빈 변경을 만든다"*고 일부러 바꾼 이름인데 표만 옛것 |
| `item/started{mcpToolCall}` | `assistant{tool_use **<tool>**}` (652-654) | `mcp__{server}__{tool}`. **코드가 옳다**(wire.rs `tool_label`이 `mcp__`로 가른다) — 표가 낡았다 |
| `error{willRetry:false}` | `result{is_error}` (620-627) | 그 범위의 수용량 분기가 빠졌고(코드는 안내 한 줄로 **다르게** 구현), **바로 위 606-609의 turnId 게이트 3종은 이식조차 안 됐다**(§4.2) |
| `(서브에이전트 스레드의 알림)` | 740-828 | 4종 중 `turn/started`·`turn/completed` 둘이 없다(§4.5) |
| `item/completed{commandExecution}` | `user{tool_result + exit}` (843-896) | 그 범위의 bg 분기(851-877) — `stopped` 사유·출력 되살림이 없다(§4.4) |

**표가 진실이고 코드가 표를 따른다**가 이 모듈의 규약이라면, 지금은 그 반대가 세 번 일어났다.
값싼 보강 하나: 게이트에 "`src`의 줄 범위가 `engine.ts`에 실재하는가"와
"`to`에 적힌 프레임 타입이 그 시나리오의 산출에 실제로 있는가"를 더한다.
