**임무**: 빌더의 "뜨고, 일하고, 사라진다"를 **믿지 않고** 독립 재실행하고, 행복 경로 밖을 민다.

값까지 같다**(§2, 32/32). 그런데 행복 경로 바로 옆에서 **완료된 답변이 조용히·영구히

**심각도순 결론 4줄**

1. 팝아웃 창에서 답을 다 읽고 **닫으면**, 마지막 답변이 그리드와 `chats-v3/*.json`에서
   **사라진다**. 스트리밍 중에 닫으면 스레드 **한가운데 구멍**이 난다
   (턴 종료 회차 2/2 · 스트리밍 회차 2/2 재현, 두 갈래 모두 디스크 확인). (S1)
2. X가 종료가 아니게 됐는데 **알릴 수단도, 끌 수단도, 아이콘을 볼 수단도 없다.**
   이 기계의 알림 영역에는 앱 아이콘이 하나도 노출돼 있지 않다(측정). (S2 / §4)
3. `app.exit(0)` 뒤 **트레이 아이콘이 알림 영역에 남는다** — 2.6.2가 `tray?.destroy()`로
   명시적으로 고쳐 둔 자리다(코드 대조 + 크레이트 문서). (S3)
4. UI 언어를 en으로 둬도 **트레이 메뉴만 한국어**다. `tray.rs`가 ui-prefs 키를
   `"lang"`으로 읽는다 — 3.0의 나머지 Rust는 전부 `"ui.lang"`이다. (S4)

## 3. 공격 — 행복 경로 밖

하네스: `docs/critic/tools/critic-m8-attack.mjs` (A1~A9) · 산출물 `docs/critic/m8-r1-attack.json`.
가짜 CLI 대본은 **한 턴을 세 조각으로** 뱉는다(`MARK-ONE` → 2.6s → `MARK-TWO` → 2.6s →
`MARK-THREE` → `result`). 되감기를 눈금으로 재기 위해서다.

### 3.1 S1 — **팝아웃을 닫으면 그리드가 되감긴다** (치명 · 4/4 재현 · 디스크 확인)

팝아웃 창의 페르시스트는 600ms 디바운스다(`PanelWindow.tsx:140`). 창이 닫히면 셸이
그 **마지막 페르시스트**를 `ma:panel-closed`로 그리드에 돌려주고, 그리드는
`applyPanelFlush` → `sessions[slot].load(sanitizeSnapshot(f.snapshot))` — **전체 교체**다
(`MultiAgent.tsx:1551`).

문제는 그리드가 그동안 **놀고 있지 않다**는 것이다. `sessions[0..5]`는 팝아웃 여부와
무관하게 항상 그 `panelId`의 `ma:event`를 구독한다(`MultiAgent.tsx:1034-1040`), 그리고
`hub.rs`의 `app.emit`은 전 창 브로드캐스트다. 즉 **그리드의 스레드는 언제나 팝아웃의
마지막 페르시스트보다 같거나 더 새롭다.** 그 위에 낡은 스냅샷을 `load`로 덮는다.

| 회차 | 닫은 시점 | 창이 보여 주던 것 | 복귀분 | 닫은 직후 그리드 | **최종 그리드** | **디스크(`chats-v3/ma-*.json`)** |
|---|---|---|---|---|---|---|
| A1-mid ① | `MARK-TWO` 도착 직후(<600ms) | ONE·TWO | `messages:2` | ONE | **ONE · THREE** | (미측정 — 스캔 경로 누락) |
| A1-mid ② | 〃 | ONE·TWO | `messages:2` | ONE | **ONE · THREE** | **`["MARK-ONE","MARK-THREE"]`** |
| A1-end ① | `MARK-THREE`+`result` 뒤 124ms | ONE·TWO·THREE | `messages:3` | ONE·TWO | **ONE · TWO** | (미측정) |
| A1-end ② | 〃 뒤 137ms | ONE·TWO·THREE | `messages:3` | ONE·TWO | **ONE · TWO** | **`["MARK-ONE","MARK-TWO"]`** (홈 직접 열람) |

디스크 원본(`--keep` 회차):

```
chats-v3/ma-a4d9c75f-…-0.json
  user      "되감기 시험"
  assistant "MARK-ONE 첫 조각"
  assistant "MARK-TWO 둘째 조각"          ← MARK-THREE 없음. 앱을 다시 켜도 없다.
```

두 가지 얼굴이 있다.

- **턴 종료 직후 닫기**(A1-end) — 사용자가 창에서 **답을 다 읽고 창을 닫는**, 가장 자연스러운
  동작이다. 그 답변이 화면에서도 디스크에서도 사라진다. 뒤에 오는 이벤트가 없으므로
  **영구 손실**이다.
- **스트리밍 중 닫기**(A1-mid) — 되감긴 뒤에도 라이브 구독은 살아 있어 `MARK-THREE`가
  이어 붙는다. 결과는 `ONE → THREE`, 즉 **스레드 한가운데가 뚫린 대화**가 디스크에 남는다.
  "토큰 유실"은 없다(엔진은 멀쩡하다). 유실되는 것은 **표시된 답변 자체**다.

**리포트와의 격차.** §10 #4는 이 자리를 *"턴 종료 600ms 안에 창을 닫으면 복귀분이 부트
상태 · 낮음 · 2.6.2부터의 규약"*으로 적었다. 세 군데가 사실과 다르다.
⑴ 복귀분은 "부트 상태"가 아니라 **직전 디바운스분**이고, 그래서 증상이 "빈 화면"이 아니라
**부분 손실**이라 눈치채기 어렵다. ⑵ 무게는 낮음이 아니라 **데이터 소실**이다.
⑶ 2.6.2 파리티인 것은 맞다(`src/renderer/src/components/MultiAgent.tsx:1222-1239`가 글자까지
같고, 2.6.2도 `index.ts:368-374`로 그리드에 미러한다) — 그러나 **3.0에서는 한 줄로 막힌다**
(§7-1). 그리고 같은 라운드의 `ipc/windows.rs:22`에 이미 **닫기 전 마지막 저장 요청**
(`chat:flush-req`, ★R4)이라는 대칭 규약이 있는데 팝아웃에는 안 걸었다.

### 3.2 S2 — 팝아웃을 띄운 채 다이얼을 줄이면 **창이 고아가 된다** (중)

`reconcileChatRefs`는 *"보이는 자리 집합을 바꾸는 **모든** 전이는 `setVisible`을 지나고,
`setVisible`은 반드시 `reconcileChatRefs`를 부른다"*를 규약으로 선언하고
포커스·이름편집·크게보기·서브에이전트·뷰어를 정리한다(`MultiAgent.tsx:1174-1185`).
**M8이 새로 만든 자리 묶임 표면(팝아웃 OS 창)은 그 관문에 등록되지 않았다.**

실측(A2, 4패널 · 자리 1을 팝아웃 · 포커스는 자리 0에 두고 다이얼 4→1):

```
gridPanels      1        ← 자리 1은 접혔다
ghostAfter      false    ← 그리드에 그 창을 가리키는 표식이 하나도 없다
popStillOpen    true     ← "패널 — AgentCodeGUI" 창은 화면에 그대로 떠 있다
surface.popout  [{ label:"panel-1", panelId:"…::1" }]
```

창은 살아서 턴도 돈다(실행은 chatId 소유). 다만 **그 창을 그리드에서 되찾을 표식이 없다**.
사용자가 이미 실물 버그로 제보한 「고아 상태(유령 UI)」와 같은 부류이고, M-LOGIC이 그
때문에 만든 관문을 **바로 그 관문이 못 보는 표면**으로 우회한다.

완화 사정 둘: ⑴ 접힘 팝오버/사이드바에서 그 자리를 1번으로 되올리면 유령 셀이 다시
붙는다(A2 `restoredTitle`에서 "축소 대상"이 제자리로 복귀). ⑵ 창을 닫으면 복귀분은
접힌 자리로 정상 적용된다(`slotOfPanelId`는 접힘 여부를 안 본다) — **데이터는 안 잃는다.**
그래서 치명이 아니라 중이다.

### 3.3 S3 — **완전히 종료 뒤에도 트레이 아이콘이 남는다** (중 · 코드 대조)

`tray.rs:50`은 아이콘을 `static TRAY: OnceLock<TrayIcon>`에 담는다. 세 사실이 겹친다.

1. `tray_icon-0.24.1`의 `TrayIcon`은 `tray: Rc<RefCell<…>>`이고 크레이트 문서가 못 박는다 —
   *"This type is reference-counted and **the icon is removed when the last instance is
   dropped**"*(`src/lib.rs:340-347`). 제거(`NIM_DELETE`)는 **Drop에서만** 돈다.
2. tauri의 `cleanup_before_exit()`는 `manager.tray.icons`를 비운다(`app.rs:1108-1110`) —
   그건 **tauri가 쥔 사본 하나**일 뿐이다. 우리 static의 사본은 그대로 남는다.
3. Rust는 `static`을 **절대 drop하지 않는다.** 그러므로 `NIM_DELETE`는 영영 안 나간다.

2.6.2는 이 자리를 알고 명시적으로 고쳐 뒀다:

```ts
// src/main/index.ts:2174
tray?.destroy() // Windows는 죽은 프로세스의 트레이 아이콘이 호버 전까지 남는다 — 즉시 제거
```

즉 **2.6.2가 고쳐 둔 것을 3.0이 되돌렸다.** 증상: '완전히 종료' 뒤에도 알림 영역에 죽은
아이콘이 남고, 눌러도 아무 일이 없다가 사용자가 그 위를 지나가면 조용히 사라진다.

> **왜 실측이 아니라 코드 대조인가**: 알림 영역 아이콘 열거는 explorer.exe에
> `VirtualAllocEx`/`ReadProcessMemory`를 걸어야 하고(남의 프로세스에 **쓰기**),
> Win11의 오버플로 XAML 섬은 열려 있을 때만 UIA 트리가 생긴다(내 UIA 열거 결과:
> 숨김 상태에서 자식 0). 셰브런을 클릭하는 것은 "OS 입력은 우리가 띄운 hwnd에만" 규칙
> 위반이라 하지 않았다. 위 3단 근거는 전부 소스·문서 인용이고, 반증하려면 한 줄이면 된다
> (§7-3의 수정이 들어가면 Drop이 돈다).

### 3.4 S4 — UI 언어가 en인데 **트레이 메뉴만 한국어** (소 · 실측)

```
A7: ui-prefs { "ui.lang": "en" } 로 부팅 → 트레이 메뉴 창
    ["AgentCodeGUI 열기", "완전히 종료"]      ← 기대: ["Open AgentCodeGUI", "Quit completely"]
```

원인은 키 한 글자다.

```rust
// src-tauri/src/tray.rs:158 (items) · :299 (native_menu)
let en = ccg_store::prefs::read_ui_prefs().get("lang").and_then(Value::as_str) == Some("en");
```

3.0의 다른 Rust는 전부 `"ui.lang"`을 읽는다 — `ipc/stores.rs:94`·`:109`,
`crates/ccg-fs/src/lib.rs:60`. 렌더러의 원본도 `app/src/lib/i18n.ts:17 LANG_PREF = 'ui.lang'`.
2.6.2도 `src/main/lang.ts` 헤더가 *"값은 ui-prefs('ui.lang')가 원본"*이라 적어 두었다.
`tray.rs`만 `"lang"`이다 → **트레이 메뉴는 영어로 절대 안 바뀐다**(네이티브 폴백도 같이).

### 3.5 S5 — 토스트: 폭주·경합·자리 (전부 방어, 관측 하나 남김)

| 공격 | 결과 |
|---|---|
| 연속 알림 **10건** | 창 1개 · 집계 **10행** · `notify.count=10` · 126ms · 카드 높이 410px(작업 영역 안, 클램프 정상) |
| 자리 (듀얼 모니터) | 커서가 있던 **DISPLAY1**(x=2560~5120) 우하단 `x=4752`. 계산값 `2560+2560−360−16=4744` + 프레임리스 창의 **비가시 8px 리사이즈 테두리** = 정확히 일치. 즉 자리 계산은 **두 번째 모니터에서도 맞다**(DPI 동일 조건) |
| **포커스 회복만으로** 소멸 | 10건 전부 소멸 · `pending=0` — 빌더 T6이 실제로는 못 재는 경로다(§6-2) |

`push()→ensure()`가 파기 대기 중인 창을 "있다"고 보고 조기 반환할 수 있는 창(파기는
이벤트 루프로 넘어간다)은 코드상 존재하지만, 4가지 지연으로 밀어도 재현되지 않았다.
**결함으로 세지 않는다.**

### 3.6 S6 — 트레이: 숨김·복원·두 번째 실행·종료 (전부 방어)

| 공격 | 결과 |
|---|---|
| X → 숨김 | 가시 창 0 · 프로세스 생존 |
| 숨김 중 알림 → 카드 클릭 | 본창 복원 ✓ |
| 숨김 중 두 번째 실행 | `exit=0` **109ms** · 기존 창 전면 **388ms** |
| 숨김 중 트레이 메뉴 열기 | 창 생성 ✓ |
| 숨김 중 '완전히 종료' | 프로세스 사망 ✓ |
| 트레이 메뉴 반복 열기 **36회**(12 + 24, 절반은 숨김 상태, 절반은 토스트 창 생성/파기와 경합) | 항목 렌더 **36/36** · 최초 행 등장 123~202ms |

**남기는 관측 하나.** A5의 첫 회차(숨김 상태·직전에 토스트 생성/파기 + 두 번째 인스턴스
기동이 겹친 회차)에서 **메뉴 창은 떴는데 항목이 4초 넘게 0개**였다(`menuItems: []`).
그 뒤 36회 반복에서는 **한 번도 재현되지 않았다.** 결함으로 세지 않되 근거는 남긴다 —
`traymenu:show`의 재송신 예산이 **180/500ms 두 번**인 데 반해(`tray.rs:209`) 토스트는
**180/500/1200ms 세 번 + 마지막 시도 폴백**이다(`notify.rs:289-302`). 그리고 36회 실측에서
**행이 실제로 뜬 시각이 123~202ms** — 즉 `page-load` 직후의 첫 emit은 **대개 놓치고**
180ms 재송신이 살리고 있다. 500ms까지 여유가 두 번뿐인 구조는 부하가 걸리면 얇다.
트레이 메뉴는 '완전히 종료'의 **유일한 경로**라 빈 카드의 대가가 토스트보다 크다(§4).

### 3.7 S7 — 여러 창 동시 · 크래시 복구 (전부 방어)

| 공격 | 결과 |
|---|---|
| 팝아웃 2 + 추가 채팅 창 1 + 메인 | 라벨 `["session-1","main","panel-1","panel-2"]` · `#mapanel` 페이지 2 · **프로세스 5 불변**(창 1개일 때와 같다) |
| 그중 하나만 닫기 | 남은 팝아웃 1 정상(`panel-2`), 레지스트리도 1 |
| 팝아웃 띄운 채 `Page.crash` | `mapanel` 페이지 **1**(중복 없음) · 팝아웃 스레드 `ONE·TWO·THREE` 온전 · **그리드 유령 표식 복원 ✓** · 로그 `process-failed → recover-begin → reloaded×3 → page-load×2 → mounted → recover-done` |
| 유리 감시 목록에 팝아웃 편입 | ✅ §5 |

> **자기 정정**: 이 항목은 처음 세 회차에서 "복구 뒤 그리드에 유령 표식이 없다"로 **실패**로
> 찍혔다. 원인은 **내 하네스**였다 — 메인 창을 `findTarget(port,'index.html')`로 골랐는데
> 메인 창의 URL은 `http://tauri.localhost/`(‘index.html’이 **없다**)이고 팝아웃이
> `index.html#mapanel`이라, 부분일치가 **팝아웃 페이지를 메인 창으로 착각**했다. 타깃 선택을
> "URL에 `.html`이 없는 페이지"로 고치자 곧바로 통과했다. **빌더 하네스도 같은 자리를
> 밟는다** — §6-4.

## 4. 「트레이 풍선 안내 없음」 위험도 판정 + 대안

리포트 §10 #1: *"X가 종료가 아니게 된 것을 사용자에게 알리는 유일한 안내가 지금 없다 · 중"*.

### 4.1 위험도: **중이 아니라 상(上)**

혼자면 중이다. 그런데 **세 개가 겹친다.**

| 겹치는 것 | 근거 |
|---|---|
| ① 안내가 없다 | 2.6.2는 첫 숨김에 `tray.displayBalloon("앱이 트레이에서 계속 실행돼요 · 아이콘을 누르면 다시 열려요")`(`index.ts:941-951`). 3.0은 없다 |
| ② 끄는 UI가 없다 | `tray.closeToTray`는 Rust만 읽는다(리포트 §10 #2). **2.6.2에는 이 설정 자체가 없었다** — 즉 3.0은 스위치를 만들고 손잡이를 안 달았다. 사용자가 `ui-prefs.json`을 손으로 고치는 것 말고 방법이 없다 |
| ③ 아이콘이 기본으로 안 보인다 | 이 기계의 알림 영역을 UIA로 열거하면 **앱 아이콘이 하나도 노출돼 있지 않다** — `SystemTray.NormalButton "숨겨진 아이콘 표시"` 셰브런 뒤에 전부 들어가 있다(Win11 기본). "아이콘을 누르면 다시 열려요"의 그 아이콘이 **셰브런 두 번 뒤**에 있다 |

그래서 실제 사용자 경험은 이렇다. X를 누른다 → 창이 사라진다 → **아무 안내도 없다** →
작업 표시줄에도 없다 → 알림 영역에도 (겉보기엔) 없다 → "껐구나" 하고 넘어간다.
그런데 프로세스는 살아서 `.instance-lock`을 쥐고, 진행 중 턴·워크플로·셸·CLI 자식
프로세스를 계속 돌린다(그게 이 기능의 **목적**이다). 요금이 나가고 CPU가 돌고, 사용자는
모른다. 되찾는 경로는 3.0이 이번에 연 "exe 다시 실행 → 창 전면"(M1 §7-3, 실측 388ms)
하나뿐인데 **그 경로가 있다는 것도 아무도 안 알려 준다.**

그리고 **끄는 경로가 사실상 없다**:

| 사용자가 시도할 법한 것 | 3.0에서 실제로 일어나는 일 |
|---|---|
| 타이틀바 X | 숨김 |
| Alt+F4 | 숨김(같은 `CloseRequested`) |
| 작업 표시줄 우클릭 → 창 닫기 | WM_CLOSE → 숨김 |
| 설정에서 끄기 | **UI 없음** |
| 트레이 아이콘 우클릭 → 완전히 종료 | 셰브런 뒤 아이콘을 찾아야 도달 |
| 작업 관리자 | 강제 종료(진행 중 턴 유실) |

즉 **"완전히 종료"에 도달하는 정상 경로가 겉보기엔 0개**다. 데이터 소실은 없지만 신뢰
비용이 크고, 백그라운드 상주가 이 앱의 셀링 포인트라 **그 기능의 첫인상 전체가 여기 걸린다.**

### 4.2 대안 — 값싼 순서로

**(A) 토스트 창 재활용 — 권장.** `notify.rs`가 이미 "불투명 카드 · 항상 위 ·
`WS_EX_NOACTIVATE`로 포커스 안 뺏음 · 우하단 · 클릭하면 라우팅"을 갖고 있다. 첫 숨김 때
항목을 하나 밀어 넣으면 그게 곧 풍선이고, **2.6.2보다 낫다**(풍선은 클릭해도 아무 일이
없지만 이 카드는 클릭 = 창 복원).

```rust
// win.rs — CloseRequested 안, hide() 직후
if tray::hide_on_close() {
    api.prevent_close();
    if let Some(w) = handle.get_webview_window(MAIN) { let _ = w.hide(); }
    tray::note_first_hide(&handle);   // ← 추가
}

// tray.rs
/// 처음 숨을 때 한 번만 — "X는 종료가 아니다"를 알리는 유일한 자리.
/// 2.6.2는 tray.displayBalloon이었다(index.ts:941). Tauri/tray-icon에 대응 API가 없어
/// **이미 있는 토스트 창**을 쓴다 — 포커스를 안 뺏고, 클릭하면 창이 돌아온다.
pub fn note_first_hide(app: &AppHandle) {
    let mut p = ccg_store::prefs::read_ui_prefs();
    if p.get("tray.noticeShown").and_then(Value::as_bool) == Some(true) { return }
    if let Some(o) = p.as_object_mut() { o.insert("tray.noticeShown".into(), json!(true)); }
    let _ = ccg_store::prefs::write_ui_prefs(&p);
    let en = p.get("ui.lang").and_then(Value::as_str) == Some("en");
    super::notify::system_notice(app, json!({
        "kind": "info",
        "title": "AgentCodeGUI",
        "preview": if en { "Still running in the tray · click the icon to reopen" }
                   else { "앱이 트레이에서 계속 실행돼요 · 아이콘을 누르면 다시 열려요" },
        "target": { "surface": "single", "id": "" }
    }));
}
```

`notify::system_notice`는 `event()`에서 두 가지만 다르게 한다: ⑴ `enabled()`(`notify.toast`)
게이트를 **타지 않는다**(채팅 알림이 아니라 시스템 안내다) ⑵ 포커스 판정을 건너뛴다(숨긴
직후라 어차피 비포커스). 소유 창은 `MAIN` 그대로 두면 **사용자가 창을 되찾는 순간 스스로
사라진다** — 수명이 정확히 맞다. `notify::open`의 기존 경로가 `show_main`을 태우므로
"클릭 = 복원"도 공짜다.
비용: `app/src/toast.ts`의 `NotifyKind`에 `info` 한 줄(안 넣으면 카드 제목이 "답변 도착"으로
나온다 — 이 한 줄만 `app/` 경계를 넘는다).

**(B) 첫 X에 확인 카드(가장 발견성이 높다).** 첫 숨김 시 `.set-dialog` 카드로
「X는 앱을 트레이로 숨깁니다 — [트레이로 숨기기] [완전히 종료] [다시 묻지 않기]」.
§4.1의 "끄는 경로가 없다"까지 한꺼번에 닫는다. 대신 `app/` 작업이 필요하고, 네이티브
`confirm` 금지 규약(메모리: *"Native dialogs wedge CM → use card"*)을 지켜야 한다.

**(C) `Shell_NotifyIcon(NIM_MODIFY, NIF_INFO)` 직접 호출 — 리포트 판단이 맞다, 비권장.**
`tray-icon-0.24.1`을 확인했다: `NIF_INFO`/풍선 관련 코드가 **없고**, 필요한 `hwnd`와
`internal_id`는 `platform_impl::TrayIcon`의 **비공개 필드**다(`platform_impl/windows/mod.rs:69-72`).
밖에서 부르려면 크레이트가 만든 히든 창을 클래스명으로 찾아 uID를 추측해야 한다 — 깨지기 쉽다.
**리포트 §10 #1의 기술적 진단은 정확하다.** 다툴 것은 무게와 대안뿐이다.

**(D) `tauri-plugin-notification`(WinRT 토스트).** 정공법으로 보이지만 Windows 토스트는
AppUserModelID(설치된 바로 가기)를 요구하고 3.0은 `bundle.active=false`라 설치본이 없다 —
표시되지 않을 공산이 크다. 설치본이 생긴 뒤의 선택지로 남겨 둘 것.

**함께 처리해야 할 것**: 설정 › 트레이 스위치(`tray.closeToTray`)를 노출한다. 안내와
옵트아웃은 한 쌍이다 — 안내만 넣으면 "그렇군, 그런데 끌 수가 없네"가 된다.

## 5. 방어 계약 검증 — 팝아웃 `arm` · 토스트 예외

### 5.1 팝아웃에 유리·크래시가 실제로 걸리나 — **걸린다. 그런데 리포트의 증거로는 모른다.**

리포트 §6 D1은 팝아웃 창 문서의 부팅 스냅샷 `{ok:true, windows:1, backdrops:[3]}`을
"팝아웃에 유리 방어가 걸린다"의 근거로 든다. 그 스냅샷은 `popout::open()`이
`boot_script()`를 만드는 시점 = **`glass::arm(app,&win)`보다 앞**에서 찍힌다
(`popout.rs:164` vs `:174`). 그래서 `windows:1`은 **메인 창 하나만 감시 중**이라는 뜻이고,
그 문서 자신은 아직 목록에 없다. D2의 백드롭 3도 `.effects(Acrylic)`가 창을 만들 때
건 값이라 `arm`의 증거가 아니다. **두 값 모두 "팝아웃이 감시 대상이다"를 증명하지 않는다.**

내가 다른 눈금으로 증명했다(A8): 팝아웃을 **두 개** 열고 **두 번째** 창의 부팅 스냅샷을 읽는다.
`glass::health_detail`의 `windows`는 `WINDOWS` 목록 길이이므로, 첫 팝아웃이 `arm`을 탔다면
두 번째 창이 볼 때 2여야 한다.

```
pop1 boot: { windows: 1, backdrops: [3] }        (메인만)
pop2 boot: { windows: 2, backdrops: [3, 3] }     ← 첫 팝아웃이 감시 목록에 있고 백드롭도 섰다
```

**결론: 계약 성립.** 팝아웃은 `shared_env` + `crash::arm` + `glass::arm`(재단언·되읽기 포함)
+ 크래시 재생성 편입까지 전부 탄다(§3.7의 크래시 회차가 재생성/재로드 쪽도 확인).

### 5.2 토스트·트레이 메뉴의 `crash::arm` 예외 — **결정은 옳고, 적어 둔 사유 ②는 안 맞는다**

리포트 §6이 든 이유 둘:
1. *"오버레이의 올바른 복구는 다시 세우기가 아니라 치우기"* — 맞다. 그리고
   `win::reset_shown()`이 `notify::drop_toast()`를 부르고, 재생성 경로는
   `a.webview_windows()` 전체를 destroy하므로 트레이 메뉴 창까지 실제로 치워진다(코드 확인).
2. *"`note_page_load`를 그 창에서 부르면 **토스트 로드가 메인 창의 복구 검증을 통과시킨다**"* —
   **이 경로는 성립하지 않는다.** `wait_recovered()`는 `MOUNTED_AT != 0`이면 **마운트
   하트비트만** 본다(`crash.rs:563-576`). 마운트는 `splash.js`가 쏘고 `splash.js`는
   `create_main`에만 주입된다(`win.rs:193`) — 즉 이 빌드에서 `MOUNTED_AT`은 항상 0이 아니고
   검증은 **언제나 mount 기준**이다. 토스트가 `note_page_load`를 불러 `ALIVE_AT`을 올려도
   복구 검증은 통과하지 않는다.

   대신 **진짜 오염 경로는 따로 있다**: `is_duplicate()`가 `ALIVE_AT <= last`로 "같은 사건의
   중복이냐"를 가른다(`crash.rs:383-388`). 토스트 로드가 `ALIVE_AT`을 올리면 **중복 이벤트가
   새 크래시로 승격**돼 복구가 두 번 돈다. 결정은 그대로 옳지만, 사유는 이쪽으로 고쳐 적어야
   다음 사람이 상수를 만질 때 잘못된 지도를 보지 않는다.

### 5.3 그 밖에 확인한 것

- `crash.rs`의 복구는 `w.destroy()`라 `CloseRequested`를 안 거친다 → 복구가 "숨기기"로
  새지 않는다(리포트 §4.1 주장 — 코드로 확인).
- `reload-all` 경로(렌더러 사망 = 흔한 쪽)는 토스트·트레이 메뉴 창도 함께 `reload()`한다.
  토스트는 `on_page_load`에서 `push()`를 다시 돌려 스스로 복원되고, 트레이 메뉴는 항목을
  다시 받는다. **유령으로 남지 않는다**(코드 + §3.7 로그의 `reloaded×3`).
- `traymenu:action`은 발신 창이 `MENU_WIN`인지 검사한다(`ipc/windows.rs:230`) — 좋다.
  **`traymenu:resize`에는 그 검사가 없다.** 2.6.2는 있었다
  (`index.ts:853` `e.sender !== win.webContents`). 지금은 아무 렌더러 창이나
  `traymenu:resize`를 불러 메뉴 창을 **낡은 앵커 자리에 강제로 띄우고 포커스를 뺏을 수** 있고,
  그 순간 `MENU_SHOWN=true`가 서서 blur 소멸 규칙이 조기 발효된다. 실사용 영향은 작지만
  **2.6.2에 있던 가드가 이식 중 빠진 것**이라 적어 둔다.
- `win:surface-debug`는 계약면 밖 진단 채널인데 **어떤 창에서든 아무 게이트 없이** 부를 수
  있고 `["traymenu-open"]`은 실제 UI를 띄운다. 하네스 전용이라면 `CCG_*` 환경 변수나
  디버그 빌드로 잠그는 게 맞다(리스크는 낮음 — 로컬 렌더러만 부를 수 있다).
