## 3. ★ `ready` 격차의 귀속 — 보고서 §8-1은 틀렸다 (지시 ①)

보고서: *"페이로드 직렬화가 아니라 **첫 `ipc_call`의 워밍업**이다(blocking 풀 기동/채널
초기화 의심)."* → 이 문장이 맞다면 처방은 싸다(아무 채널이나 한 번 미리 부르면 된다).

### 3.1 반증 실험 — 팔의 **순서를 바꾼다**

`docs/critic/tools/m7-ipcwarm.mjs`. 문서 시작(`addScriptToEvaluateOnNewDocument`)에서 직렬로:
`A = app:get-version`(비블로킹 경로) · `B = lsp:cached-tokens`(**`spawn_blocking` 경로**) ·
`N = zzz:critic-none`(미구현) 각 8회. 순서만 바꿔 두 번 부팅.

```
순서 A→B→N   A0=11.1  A1=41.8  A2=127.8  A3=51.7  A4=6.3  A5..A7=0.7~0.9
             B0=1.0   B1..B7=0.7~20.4          N0=0.9 …            (A가 다 먹었다)
순서 B→A→N   B0=68.4  B1=148.6 B2=30.2  B3=2.0  B4..B7=0.7~1.3
             A0=0.6   A1..A7=0.6~0.9           N0=0.6 …            (B가 다 먹었다)
```

- **첫 `spawn_blocking` 호출이 비싼 게 아니다**: A가 먼저 간 주행에서 *생애 첫* blocking 채널
  호출 `B0`은 **1.0ms**다. blocking 풀 기동설 기각.
- **첫 `invoke`가 비싼 것도 아니다**: 비싼 것은 **문서 시작부터 ~230~250ms 동안의 창**이고,
  그 창에 걸린 호출이 누구든 그 비용을 문다. 두 주행에서 값이 정상으로 내려앉는 시각이
  각각 `at≈239ms` · `at≈249ms`로 **같다**.
- 따라서 **선워밍(더미 호출 한 번)은 처방이 아니다.** 더미가 대신 느려질 뿐, 진짜 호출도
  같은 창 안에 있다. (보고서가 §8-1에서 본 "첫 `cachedTokens` 124ms"는 내 A2=127.8ms와
  같은 현상 — *첫 호출*이라서가 아니라 *그 시각*이라서다.)

> 결과: `docs/critic/m7-r1-ipcwarm-ABN.json` · `-BAN.json`

### 3.2 그럼 200ms는 어디 있나 — 경계 시각을 전부 박았다 (n=7 대 7)

`docs/critic/tools/m7-ready.mjs`. 문서 시작에 걸어 `window.api.lsp` 등장 → 첫 `lsp:status`
발신 → 그 응답 → `ready`까지의 **네 시각**을 전부 남긴다.

| p50 (n=7) | electron 2.6.2 | tauri 3.0.0 | 차 |
|---|---:|---:|---:|
| 프로브 설치(문서 시작 기준) | 81.7 | 77.2 | — |
| `window.api.lsp` 등장 | **81.8** | **122.8** | **+41.0** |
| 첫 `lsp:status` 왕복(=지연 스폰) | **12.3** | **50.4** | **+38.1** |
| 첫 status → `ready` | 126 | 285 | **+159** |
| **`ready`** | **207.1** | **407.5** | **+200.4** |

세 조각의 정체:

1. **+41ms — 방아쇠가 늦게 당겨진다.** 2.6.2는 `window.api`가 preload(문서 시작)에 있고
   3.0은 **번들 실행 뒤**에 생긴다(`app/src/api/shim.ts`). `lsp:status`가 곧 지연 스폰의
   방아쇠라, 3.0은 41ms 늦게 서버를 시작한다. 서버가 느린 게 아니다.
2. **+38ms — 첫 status가 `CreateProcess`를 붙들고 있다.** `manager::ensure`는
   `Server::spawn`(동기 `Command::spawn`)을 **호출 스레드에서** 돈다. 2.6.2 `ensure`는
   Node `spawn()`이라 즉시 돌아온다(`manager.ts:2456`).
3. **+159ms — 앱 계층의 initialize 왕복.** 크레이트 단독 프로브는 같은 구간이 105ms다
   (보고서 §7과 일치) — 즉 앱 껍데기에서 ~180ms가 더 붙는다. 여기까지가 R2의 몫.

### 3.3 그래서 뭘 고치면 싼가 — 제안 diff (제품 수정 없음, 제안만)

**(a) 방아쇠를 렌더러 밖으로** — `prewarm`은 렌더러가 필요 없다. 셸이 창을 만들 때
마지막으로 쓴 cwd로 한 번 부르면 +41ms가 통째로 사라진다.

```rust
// src-tauri/src/main.rs (창 생성 직후, 이미 cwd를 아는 자리)
+ // 코드 인텔리전스 지연 스폰의 방아쇠를 렌더러 번들이 뜨기 전으로 당긴다.
+ // (렌더러의 App.tsx:834 prewarm은 그대로 둔다 — 멱등이고 cwd가 바뀔 수 있다)
+ if let Some(cwd) = last_project_cwd() {
+     std::thread::spawn(move || ccg_lsp::prewarm(&cwd));
+ }
```

**(b) 첫 status가 프로세스 생성을 안 물게** — `ensure`가 스폰을 백그라운드로 넘기고
`Starting`을 즉시 돌려준다. +38ms가 사라지고 **C-4(경쟁 스폰)도 같이 사라진다**.

```rust
// crates/ccg-lsp/src/manager.rs — ensure()
- let spawned = Server::spawn(spec, root);          // 호출 스레드가 CreateProcess를 문다
+ // 자리를 먼저 잠그고(같은 키의 두 번째 진입은 여기서 막힌다) 스폰은 스레드로.
+ // 렌더러는 어차피 status 폴링으로 ready를 따로 본다.
+ let spawned = spawn_in_background_and_register(spec, root);
```

> (a)만으로 ~41ms, (a)+(b)로 ~79ms. 남는 ~120ms는 앱 계층 initialize라 R2 과제 그대로다.
> **선워밍 diff는 제안하지 않는다 — §3.1이 그 처방을 기각했다.**

### 3.4 곁다리 — "두 주행에서 범위가 겹치지 않으니 노이즈가 아니다"는 n=2 논증이다

n=7로 늘리면 electron 205 / 206 / 205 / 207 / 208 / 237 / **486**, tauri 383~494로
**범위는 겹친다**(2.6.2 1/7 표본). 결론(중앙값 격차 200ms는 실재)은 맞지만 근거 문장은
표본 2개짜리다. 판정은 중앙값으로 쓰는 편이 안전하다.

## 4. 공격 (지시 ②)

### C-1 [치명 · 2.6.2 대비 회귀] 언어 서버가 죽으면 **영영** 안 살아나고, `status`는 계속 `ready`라고 말한다

보고서 §5는 *앱이 죽으면 서버가 남는가*만 쟀다. 반대 방향은 아무도 안 쟀다 —
tsserver OOM·크래시·작업 관리자 오조작은 사용자에게 더 흔하다.

**절차**(`docs/critic/tools/m7-kill.mjs`): 앱 부팅 → `ready` → 라이브 토큰 10,925 확인 →
**내 앱의 자손 중 언어 서버 PID만** `taskkill /T /F` → 45초 동안 렌더러에서
`status`·`semanticTokens`·`hover`·`projectStatus`를 폴링.

| | electron 2.6.2 | **tauri 3.0.0** |
|---|---|---|
| kill 뒤 관측된 `lsp:status` | `error` → `starting` → `ready` | **`ready` 하나뿐 (45s 내내)** |
| `lsp:project-status` | `idle` → `ready` | **`ready` 하나뿐** |
| 시맨틱 토큰 회복 | **30.6s** | **회복 없음** |
| 호버 회복 | 예 | **아니오** |
| 서버 재기동 | **32.9s**(새 PID) | **없음** |

3.0의 값은 "느리다"가 아니라 "**틀린 상태를 자신 있게 보고한다**"다. 크레이트 계층에서도
같다(가짜 서버가 ready 뒤 자살 → 40초 동안 `status="ready"`, 토큰 0, `live_count=1`,
프로세스 재시작 0).

**기전**(코드 대조, 세 줄):

```rust
// rpc.rs: 서버 stdout EOF → dispose() → shared.dead = true.  ★ Server.state.status는 그대로 Ready
// manager.rs ensure(): if s.raw_status() != Status::Error { s.touch(); return Ok(s.clone()) }
```

## 5. `ServerSpec` 종이 시험 — "Python은 값만 다르다"를 실제로 써 봤다 (지시 ③)

### 5.1 pyright 스펙 초안

`pyright@^1.1.410`이 이미 `package.json` 의존이므로 `Provision::Bundled` + `Launch::Node`가 성립한다.

```rust
ServerSpec {
    id: "py", label: "Pyright", langs: "Python", exts_display: ".py .pyi",
    kind: Provision::Bundled, requires: None,
    exts: &[("py", "python"), ("pyi", "python")],
    launch: Launch::Node { module: &["pyright", "langserver.index.js"], args: &["--stdio"] },
    root: RootRule::ProjectCwd,
    init_options: no_init_options,
    workspace_folders: no_workspace_folders,
    after_initialized: None,
    awaits_project_init: false,
    declare_watched_files: false,
    reprime: Reprime::None,
    watch_exts: &["py", "pyi"],
    idle_ttl_ms: 10 * 60_000,
    cache_version: 1,
}
```

여기까지는 **정말로 값만 다르다.** 그런데 이 스펙으로는 담을 수 없는 축이 나온다.

| 빠진 축 | 왜 필요한가 | 지금 어디를 열어야 하나 |
|---|---|---|
| **서버 설정 응답**(`workspace/configuration`) | pyright는 `python`/`python.analysis`를 이 경로로 묻는다. 지금 답은 규약 위반 `[]`(C-5). 인터프리터·venv 지정도 여기다 | **`rpc.rs`** ← 게이트 안 |
| **`workspace/didChangeConfiguration` 푸시** | 설정 변경 반영 | `server.rs` 또는 스펙 신규 필드 |
| `Provision::Download` + `Launch::Node` 조합 | `shipped_module`은 `node_modules`만 본다. 내려받은 **JS** 서버는 `<앱 홈>/lsp/bin`에 놓이는데 그쪽은 `Launch::Exe`만 본다 | `launch.rs`(게이트 밖) |
| 프리웜 언어 감지 | `lib.rs::detect_project_spec`이 `"ts"/"py"/"cs"/"cpp"` **문자열과 마커 파일명을 하드코딩**한다. py/cs/cpp는 **미리 적어 둬서** 공짜지만, 다섯 번째 언어(Rust·Go·Java)는 `lib.rs`를 연다 | `lib.rs` |

> 보고서의 게이트 문장은 *"`server.rs`/`manager.rs`/`rpc.rs`가 언어 특례 때문에 열리면 설계 실패"* 다.
> **pyright 한 언어에서 이미 `rpc.rs`가 열린다.** 나머지 셋은 게이트 밖이지만 "스펙 1항목" 주장과는 어긋난다.

### 5.2 Roslyn 함정 필드 3종 — 2.6.2 실규약과 대조

| 필드 | 보고서의 설명 | 2.6.2 코드 | 판정 |
|---|---|---|---|
| `declare_watched_files: false` | "선언하면 서버 폴백 워처가 꺼진다" | manager.ts:2573-2578 주석과 **정확히 일치**. 단 2.6.2는 이걸 **전역 결정**으로 두고 `workspace/didChangeWatchedFiles` **통지는 계속 보낸다**("pyright류를 위한 최선 노력") | **일치.** 다만 3.0에는 통지를 보내는 쪽이 아예 없다(C-7) |
| `Reprime::WorkspaceSymbol { quiet_gap_ms: 3000 }` | "프라임은 스냅샷 → 3초 조용 간격" | `primeFullSemantics`는 규칙 **다섯 개**(최소 1.5s 오픈 갭·재대기 루프·프라임 중 무효화·히트 0 쿼리·프라미스 공유) | **불일치**(C-6) |
| `RootRule::ReferencingSolution { project_ext, solution_exts, ttl_ms }` | "그 csproj를 **참조하는** sln(UE 거대 sln 회피)" | `csRootFor`(manager.ts:421-500)는 그 위에 ⓐ **"참조 프로젝트 수 최대, 동률이면 안쪽"**(도구가 떨군 단일 프로젝트 sln이 진짜 sln을 **가리는** 반대 방향 사고 — 보고서는 이 절반을 안 적었다) ⓑ MetadataAsSource 소유 서버 라우팅(`metadataAsSourceRoot` + `lastCsRoot`) ⓒ UnrealNetCore 합성 유닛(csproj의 `<Compile Include>` 맵) ⓓ UE 룰 프로젝트(`Build.cs`/`Target.cs`) ⓔ `csNoAutoSln` | **부족.** ⓐ~ⓔ는 세 필드로 표현 불가. 특히 ⓑ는 `definition()`이 **응답 URI를 보고 소유자를 기록**해야 성립하는데 3.0 `server.rs::definition`에는 그 훅이 없다 → **`server.rs`가 또 열린다** |

`root_for`는 `fn(&ServerSpec, &Path, &Path) -> PathBuf`(순수·무상태)다. ⓐ~ⓔ는 모듈 정적 상태와
서버 레지스트리 접근을 요구한다. `spec.rs` 안의 static으로 ⓐⓒⓓⓔ는 밀어 넣을 수 있지만
ⓑ는 엔진 협조가 필요하다.
