# R28b 「GIT」 갈래 확인 크리틱 R2 — 세 구멍은 진짜로 막혔다. 그런데 4MB 예산이 프롬프트의 95%를 말없이 지운다

판정: **불합격(pass=false)**.

체크리스트 5개는 전부 실측으로 섰다. 불합격 사유는 그 5번째 항목(**캡 동작**)을 재다가
나온 것이다 — 「파일별 24k · 총량 120k」 말고 **세 번째 캡**이 하나 더 있고, 그것이
아무 표시 없이 diff 본문을 지운다. 그리고 이 라운드가 「고쳤다」고 다시 쓴 장부(§6.4
「되돌아가는 단위」 표)에 **같은 종류의 새 오기**가 한 줄 들어갔다.

빌더 보고서·커밋 메시지는 근거로 쓰지 않았다. 아래 수치는 전부 이 크리틱이 새로 만든
독립 프로브(`ccg-fs`를 경로 의존으로 무는 레포 밖 릴리스 바이너리)와 실주행으로 잰 것이다.

| 항목 | 결과 |
|---|---|
| 1. 2,000파일 커밋(긴 경로·argv >32K) | **통과** — ok · 스폰 3 · 옛 방식은 같은 판에서 스폰 자체가 실패 |
| 2. 유니코드·공백 경로 / 훅 거부 롤백 | **통과** — 왕복 무손실 · 600경로 스테이징 0 |
| 3. AI diff 스폰 수 + 캡 | **★불합격** — 스폰은 다 맞다. **캡이 정직하지 않다**(§3.5) |
| 4. `cargo test -p ccg-fs` 무후퇴 + typecheck 3종 | **통과** — 88 통과·0 실패·2 ignored / 3종 exit 0 |
| 5. report.json 19행·자기모순·경고·viewport | **통과** — 두 리포트 자기일치, 경고 **5종 전부 실주행 유발** |

## 1. 체크리스트 1 — 2,000파일 커밋 (통과)

### 재현 조건이 진짜인가

파일 2,000개(추적 중 + 전부 수정), 경로는 한글·공백·4단계 서브폴더, 평균 116자.

```
argv 합계               233,461자    (Windows CreateProcess 한계 32,767자의 7.1배)
status 행 수            2,001행      ← UI가 실제로 그만큼 고를 수 있다(폴더 접기 없음)
옛 방식 git add -A -- …2000경로
        → SPAWN FAILED: 파일 이름이나 확장명이 너무 깁니다. (os error 206)
```

`os error 206`은 **프로세스가 뜨지도 못한** 것이다. 「고치기 전이면 같은 판에서 실패했음이
자명한가」 — 자명하다.

### 새 길

```
ok=true · 스폰 3회 · 커밋에 담긴 파일 정확히 2,000 · 커밋 수 3 · 제목 그대로
고르지 않은 「고르지 않은 파일.txt」는 미추적으로 그대로 남았다(1행)
소요 21,804 / 21,761 / 21,731 ms   (3연속, 편차 0.3%)
```

### 소요 시간 — 빌더 보고(831ms)·R1 크리틱(852ms)과 25배 다르다. 원인은 앱이 아니다

이 기계에서 **같은 픽스처를 생 git으로** 돌린 대조군(앱 코드 미경유):

| 픽스처 모양 | 고유 폴더 수 | argv 합계 | `git add`(stdin) | `git commit -F -` | 합 |
|---|---|---|---|---|---|
| 4단계 깊이 (내 판) | 2,000 | 233,461 | 8,772ms | 13,396ms | **22,168ms** |
| 2단계 깊이 | 77 | 184,181 | 8,509ms | 473ms | 8,982ms |
| 평면 | 1 | 116,000 | 8,522ms | 256ms | 8,778ms |

**앱 경로 21,731ms < 생 git 22,168ms.** 앱이 얹는 비용은 0이다. 차이는 전부 (a) 내 픽스처가
파일마다 고유 4단계 폴더를 만들어 트리 오브젝트를 2,000×4개 쓰게 한 것과 (b) 이 기계의
디스크/실시간 검사(파일 2,000개 `git add`에만 8.5초, CPU 부하는 7%)다. **831ms/852ms는 이
기계에서 재현되지 않지만, 그 차이는 앱 밖에 있다** — 판정에는 영향 없음(성공·스폰 3).

## 3. 체크리스트 3 — AI diff (스폰은 다 맞다 · **캡이 정직하지 않다**)

### 3.1 정상 경로 — 「몇 개든 1~2회」 실측

| 규모 | 갈래 | 새길 | 옛길(파일당) |
|---|---|---|---|
| 900파일 (argv 105,058 → 전 트리) | Ok | **2스폰 · 343ms** | 60표본 120스폰·2,948ms → 900 환산 **1,800스폰·44.2초** |

60표본 `(tag·add·del·변경 줄 텍스트 전체)` **불일치 0**.

### 3.2 구멍 ① unborn HEAD — 진짜로 닫혔다

```
300파일 · 커밋 없는 저장소
  새길   3스폰 · 1,443ms      (repo_root + 실패한 diff + rev-parse. 나머지는 디스크에서)
  옛길   30표본 90스폰·2,076ms → 300 환산 900스폰 · 20.8초
  답     300행 전부 tag:new · 30표본 옛길과 불일치 0
```

### 3.3 구멍 ② 전 트리 32MB 초과 — 반 가르기가 실제로 돈다

```
400파일 · 전 트리 diff 79,311,600바이트(캡 33,554,432의 2.4배)
  새길   9스폰 · 2,305ms
  답     400행 전부 정확히 (+4608 −4608) — 틀린 행 0
```

`#[ignore]` 테스트를 직접 돌려도 같은 자리가 나온다:
`[측정] 400파일 캡 초과: 1664ms · git 스폰 9회` · `[측정] 900파일 — 옛길 40471ms/1800스폰 · 새길 242ms/2스폰`.

### 3.4 구멍 ③ 미추적 폴더 행 — 거짓말이 사라졌다

```
status 행 : ["그냥 새 파일.txt", "새 폴더/", "seed.txt"]
porcelain : ? "새 폴더/"                      ← git이 실제로 한 줄로 접는다(확인)
새길      : ERR:내용을 읽을 수 없어요          ← 옛길과 같은 사유
프롬프트  : ### 새 폴더/ (diff 본문 없음: 내용을 읽을 수 없어요)
```

고치기 전 코드도 확인했다 — `43a1b36:crates/ccg-fs/src/git.rs:945`가 `p.exists()`다.
지금은 `p.is_file()`. R1이 잡은 `("edit", 0, 0)`은 여기서 나왔다.

### 3.5 ★ 불합격 — 세 번째 캡이 있다. 그리고 그 캡은 **아무 말도 안 하고 본문을 지운다**

`parse_bulk_patch`의 `BULK_TEXT_BUDGET = 4MB`는 **배치 전역** 카운터다(`stored`가 파일마다
리셋되지 않는다). `git diff`는 파일을 경로 순으로 뱉으므로, **앞쪽 큰 파일 몇 개가 4MB를
다 먹으면 그 뒤 파일들은 `add`/`del` 숫자만 남고 `lines`가 빈 채로** 돌아온다. 그 상태로
`serialize_diff`를 태우면 **본문도 사유도 없는 맨 헤더 한 줄**이 나간다.

현실적인 판으로 쟀다 — 재생성된 큰 파일 5개(각 ~1MB 변경) + 소스 파일 10개(각 ±40줄):

```
파일 15개 · 총량 캡(120,000자)에 **한 번도 안 닿는다**
  새길 프롬프트   838자
  옛길 프롬프트   15,838자
  본문이 조용히 사라진 파일: Source/mod00.rs … mod09.rs (10개 전부)

새길 꼬리:  ### Source/mod07.rs (+40 −40)\n\n### Source/mod08.rs (+40 −40)\n\n### Source/mod09.rs (+40 −40)
옛길 꼬리:  +let new_9_37 = 2;\n+let new_9_38 = 2;\n+let new_9_39 = 2;
```

다른 모양(4MB를 혼자 먹는 파일 1개 + 작은 파일 8개)도 같다: **374자 vs 38,776자**, 8개 전부
본문 증발.

무엇이 문제인가:

1. **모델이 못 본 것을 봤다고 가정한다.** AI 커밋 메시지는 소스 변경 내용을 **한 줄도 못 본 채**
   쓰인다. 헤더의 `(+40 −40)`은 정확하지만 그건 규모일 뿐이다.
2. **말을 안 한다.** 파일별 캡(24k)·총량 캡(120k)에 걸린 자리는 `— 본문 생략(파일이 너무 큼)`
   / `— 본문 생략(총량 상한)`을 붙인다. 이 자리만 **표시가 없다** — 사용자도 모델도 뭔가
   빠진 줄 모른다. `bulk_file_diffs`가 `unparsed` 신호까지 만들어 가며 피하려던 그
   「조용한 거짓말」이 여기서 그대로 난다.
3. **코드 주석이 정반대를 단언한다.** `git.rs:733-735`:
   > 넘으면 줄은 버리고 개수만 센다(**호출부의 예산은 12만 자라 프롬프트에 닿는 글자는
   > 이 상한에 영향받지 않는다**).

   측정: 838자 대 15,838자, 둘 다 12만 자 아래. **영향받는다.**
4. **장부에 없다.** `docs/renderer-divergence.md` §6.4의 분기 표는 스폰 수·diff 엔진·1.5MB
   초과 파일·안 바뀐 파일 네 줄뿐이고, 4MB 배치 전역 예산은 어디에도 없다.
5. **테스트가 못 잡는다.** `bulk_diffs_answer_the_same_as_one_call_per_file_in_two_spawns`도
   900파일 판도 파일당 변경 텍스트가 작아 4MB 근처에 못 간다. R1에서 들어온 상수라
   이 라운드가 만든 건 아니지만, **체크리스트 3이 묻는 「캡 동작」이 정확히 이 자리다.**

### 3.6 곁다리 — 파일별/총량 캡 자체는 옛길과 **바이트 동일**

4MB 예산에 안 닿는 판(21파일)에서:

```
새길 프롬프트 116,518자 · 파일 캡 1회 · 총량 캡 12회
옛길 프롬프트 116,518자 · 파일 캡 1회 · 총량 캡 12회
text_identical: true       ← 헤더뿐 아니라 문자열 전체가 같다
```

이 두 캡은 무후퇴다.

## 4. ★ 장부의 새 오기 — 「그 덩이만」은 거짓이다 (배치 전체다)

R1 크리틱이 잡은 것이 §6.4의 폴백 단위였다(「전부 '그 파일만'이라고 적었는데 unborn·캡
초과는 배치 전체다」). 이 라운드는 그 표를 다시 썼다. 그런데 **새로 넣은 마지막 줄이
같은 종류로 틀렸다**:

> `docs/renderer-divergence.md` §6.4 · `docs/parity-fix-git-r1.md` §2.5 · 커밋 `4c97d62` 메시지
> | 파일 **하나**가 혼자 32MB 초과 | — | **그 덩이만** `file_diff`가 사유를 낸다 |

실측 — 파일 201개, 그중 하나의 diff가 혼자 39,200,125바이트(캡의 1.17배):

```
bulk_file_diffs → 421 스폰 (파일당 2.09) · 14,622ms
                  giant.txt = ERR:파일이 너무 커요 — diff 표시는 1.5MB까지만
                  나머지 200행도 전부 옛길로 돌았다
```

코드가 그렇게 돼 있다. `diff_into`는 단일 파일 leaf에서 `DiffOut::Over`면 `false`를
돌리고, 그 `false`가 `&&`로 재귀 꼭대기까지 전파되어 `bulk_file_diffs`의
`if !diff_into(...) { return files.iter().map(file_diff) }`에 닿는다 — **배치 전체**다.
`bulk_file_diffs`의 rustdoc은 이걸 바르게 적어 뒀다(「배치 전체 — git 실패(unborn·캡 초과를
갈라도 안 되는 자리)」). **코드 주석과 장부가 서로 반대를 말한다.** 다음 파리티 감사가
읽는 것은 장부다.

(참고: 200파일에서 39MB짜리 diff 하나가 배치 전체를 파일당으로 끌어내리는 것 자체는
설계상 최후 그물이라 사고는 아니다. 사고는 **그 사실이 장부에 반대로 적힌 것**이다.)

## 8. 다음 라운드로 넘기는 것 (심각도 순)

1. **[치명] `BULK_TEXT_BUDGET`(4MB, 배치 전역)이 프롬프트 본문을 표시 없이 지운다.**
   `stored`를 **파일별**로 돌리거나(파일 하나가 예산을 다 먹어도 다음 파일은 살아남는다),
   최소한 예산에 걸려 `lines`가 빈 행에 **`unparsed` 같은 신호를 달아** 호출부가
   `— 본문 생략(수집 예산)`을 붙이게 할 것. 지금은 15파일 커밋에서 프롬프트가 838자 대
   15,838자로 갈리고 **아무도 그 사실을 모른다**. 그리고 `git.rs:733-735`의 「프롬프트에
   닿는 글자는 이 상한에 영향받지 않는다」는 지우거나 조건문으로 고칠 것.
   재현: 재생성 큰 파일 5개(각 ~1MB 변경) + 소스 10개 → 소스 10개 본문 전부 증발.
2. **[높음] §6.4의 「그 덩이만」을 「배치 전체」로.** `docs/renderer-divergence.md` §6.4 표 ·
   `docs/parity-fix-git-r1.md` §2.5 · `git.rs:915` 주변 주석 세 자리. R1이 잡은 것과
   **같은 종류의 오기가 그 수정 안에 다시 들어갔다** — 「되돌아가는 단위」는 이 갈래가
   두 라운드 연속으로 틀린 자리다.
3. **[중간] 4MB 예산과 세 캡을 §6.4 분기 표에 한 줄로 올릴 것.** 지금 장부에는 캡이
   두 개(24k·120k)만 있고, 실제로 프롬프트를 가장 크게 깎는 것은 장부에 없는 셋째다.
4. **[낮음] 「통짜 재주행」 문구.** electron 쪽은 `--merge` 합성이다(§6). 리포트에
   `mergedFrom`이 이미 적혀 있으므로 문장만 맞추면 된다.
5. **[낮음] 실앱 확인 숙제 유지.** 이 라운드의 Rust가 든 exe는 여전히 없다. 다음 정식
   빌드 뒤 2,000파일 커밋·AI 메시지 카드를 실제 UI에서 한 번.
