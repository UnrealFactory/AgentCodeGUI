# M5 R1 크리틱 — 계정 도메인 크레이트 `ccg-auth`

**대상**: `crates/ccg-auth`(2821045) · `docs/m5-report-r1.md`(102ccbc) · 브랜치 `feature/3.0.0-beta`
**절대 조건**: 사용자가 재로그인하지 않는다. 실계정 6건.
**독립 재현 도구**: 워크스페이스 **밖** 드라이버 크레이트(`%TEMP%/m5drive`, ccg-auth 공개 API만 호출)
+ 2.6.2 리더 하네스(`src/main/auth.ts` 원문 이식 · **Electron 42 safeStorage 실물**).
빌더의 프로브·테스트를 믿지 않고 **바깥에서 다시 잰다**.

---

## 0. 판정

**조건부 합격.** 승계의 핵심 4가지 — ① `accounts.json` 무손실 왕복 ② 실 credEnc 복호
③ 슬러그 일치 ④ 정션 물질화 — 는 **바깥 도구로 전부 재현됐고, 2.6.2가 우리 산출물을 읽는
것까지 실물로 확인**했다. 재로그인을 유발하는 결함은 **못 찾았다**.

깨진 것은 하나 — **오염가드(`verify::preflight`)가 계정 순서에 좌우된다.** 오염 쌍 중
`accounts.json`에서 앞에 있는 쪽은 **항상 통과**한다. 이 크레이트가 "1.6.1의 전환 되돌아감을
막는 장치"라고 내세운 바로 그 지점이고, 배선 전에 고쳐야 한다(§4-1).

| 축 | 결과 |
|---|---|
| 재로그인 위험 | **0건** — 읽기/쓰기/재암호화/물질화 전 경로에서 2.6.2 왕복 성립 |
| 보고서 수치 허위 | **0건** — 표본 수치를 전부 독립 재현(§1) |
| 깨진 것 | **1건**(오염가드 순서 의존) + 잔금 3건(§4) |
| 잔여 위험 | usage 파서 12/71 케이스 2.6.2와 불일치 — 게이지 숫자만, 계정은 무사(§3) |

## 2. 쓰기 경로 공격 — "2.6.2가 우리가 쓴 파일을 그대로 읽는가"

하네스: `src/main/auth.ts`의 `readStoreFile`/`decCreds`/`accountSlug`/`credsExpiresAt` +
`accountRunDir` 판정부를 **원문 이식**해 Electron 42 `safeStorage` 위에서 실행
(userData = 설치본 `Local State` 사본). 증거 → `docs/critic/m5-r1-writeback.json`.

| 3.0이 한 일 | 2.6.2가 읽은 결과 |
|---|---|
| `set_default_account`(비-기본으로 변경) | v3 · defaultEmail 반영 · **6/6 실행 가능** |
| `reorder_accounts`(역순) | 배열 순서 그대로 · **6/6 실행 가능** |
| `account_run_dir` → 폴더 토큰 갱신 → `sync_account_tokens`(**credEnc 재암호화**) | 재암호화 blob을 **실 safeStorage가 복호** · 스냅샷 키 `[creds,account,userID]` 보존 · 갱신 `expiresAt` 반영 · **6/6 실행 가능** |
| `import_account_from_dir`(로그인 완료 경로) | 7번째 계정을 읽고 실행 가능 · 레코드 키 순서 `email→subscriptionType→credEnc` |
| `remove_account` | 6건 복귀 · `shared/*` 원본 **전부 잔존** |

재암호화 왕복이 이 절의 핵심이다 — R2에서 api-config로 한 번 밟았던 "스킴이 갈려 롤백 시
계정이 죽는" 함정을 **실물 safeStorage로** 닫았다.

### 2.1 실 CLI가 그 폴더로 기동하는가 (보고서 미검증 항목)

`claude.exe auth status --json`을 `CLAUDE_CONFIG_DIR`만 바꿔 두 번 돌렸다.

```
빈 폴더      → {"loggedIn": false, "authMethod": "none"}
우리 물질화 폴더 → {"loggedIn": true, "authMethod": "claude.ai",
                  "email": "synthetic@example.com", "orgId": "<oauthAccount.organizationUuid>",
                  "subscriptionType": "max"}
```

**실계정이 아니라 합성 토큰으로 했다.** 실토큰으로 CLI를 돌리면 리프레시 회전이 일어나
사용자 실홈의 백업 refresh 토큰이 죽을 수 있고, 그게 정확히 우리가 막으려는 사고다.
합성으로도 목적은 달성된다 — CLI가 우리 `.credentials.json` + `.claude.json` 레이아웃을
**그 계정으로 인식**한다는 것. 실토큰 턴(resume 공유)은 **배선 크리틱 몫으로 남긴다.**

부산물 하나: **`auth status`는 읽기 전용이 아니다.** 실행 후 `.claude.json`에
`firstStartTime`·`migrationVersion`·`seenNotifications`·`opusProMigrationComplete`가 붙고
`backups/` 폴더가 생겼다. `verify.rs:22`의 "**읽기 전용**이다(파일을 쓰지 않는 것 실측)"는
**틀린 주석**이다. 다행히 `account_run_dir`이 기존 키를 보존 병합하므로 실피해는 없다.

## 3. 정션 — 관리자 없이 · 지워도 원본이 사는가

**이 머신 상태: 관리자 아님 + 개발자 모드 꺼짐.** 이 조건에서
`CreateSymbolicLinkW`는 `ERROR_PRIVILEGE_NOT_HELD`로 실패한다 — 즉 크레이트가 FSCTL을 직접
치는 이유가 실제로 유효하다. PowerShell `Get-Item`이 만들어진 링크를 **`LinkType: Junction`**
으로 판정했다(심링크 아님). 공격 8종 전부 통과 → `docs/critic/m5-r1-junction.json`.

| 공격 | 결과 |
|---|---|
| unlink **없이** 계정 폴더 `remove_dir_all` | 정션만 사라지고 **세션 기록 원본 잔존** (std가 리파스 포인트를 안 따라감 = 이중 방어 성립) |
| SHARED_DIRS 밖 **중첩** 정션(CLI가 판 것)까지 재귀 삭제 | 원본 잔존 |
| **조상을 가리키는 순환 정션** 생성 후 재귀 삭제 | 생성 OK · 폭주 없음 · 조상 파일 잔존 |
| 실폴더가 이미 있는 자리 | 그대로 둠(내용 보존) + 나머지 이름은 정션 생성 = 2.6.2 규칙 |
| 대상 없음 | `Err(NotFound)` + **반쪽 빈 폴더 안 남김** (canonicalize가 `create_dir`보다 앞이라 그렇다 — 순서가 바뀌면 "이미 있음"으로 영영 정션이 안 생기는 조용한 죽음이 된다) |
| 링크 자리에 파일 | `Err(AlreadyExists)` + 파일 온전 |
| `unlink(실폴더)` | no-op + 내용 온전 |
| 대상이 또 정션 | 체인 **평탄화**(2.6.2는 리터럴 경로 저장). 동작 동등, 표기만 다름 |

## 4. 깨진 것 / 잔금

### 4-1. **[깨짐] 오염가드가 계정 순서에 좌우된다** — `verify.rs:177` / `claude.rs:561`

`preflight`는 `claude::token_owner`(`find_map` = **첫 일치**)로 오염을 판정한다. 그래서 같은
토큰을 문 두 계정 중 **`accounts.json`에서 앞에 있는 쪽은 자기 자신을 찾고 통과**한다.

```
스토어 [a, b]  →  preflight(a)=Probe(통과!)          preflight(b)=Contaminated("a")
드래그 재정렬 후 [b, a] →  preflight(a)=Contaminated("b")  preflight(b)=Probe(통과!)
```

(합성 오염으로 실측 — `docs/critic/m5-r1-contamination.json`)

- 같은 상황에서 `diagnose()`는 **양쪽 다** `collides_with`로 잡는다(지문→소유자 목록 맵).
  즉 진단은 맞고 **게이트만 틀렸다**.
- 통과하는 쪽이 "진짜 주인"이라는 보장이 전혀 없다. 순서는 사용자가 설정 → Account에서
  드래그로 바꾸는 값이다. 오염 항목이 앞에 있으면 그게 통과하고, 다음 실행에서 CLI가
  `oauthAccount`를 토큰 주인으로 자가 교정한다 = **1.6.1의 "전환이 되돌아감" 그대로.**
- 보고서 §4.2는 "`Contaminated`면 `probe`가 `None`"만 적었지 이 비대칭을 말하지 않는다.

**고치는 법**: `token_owner` 대신 지문→소유자 **목록**을 만들어 `owners.iter().find(|o| **o != email)`
로 판정한다(= `diagnose`가 이미 하는 그 로직). 곁다리로 `token_owner`는 **백업만** 비교하므로
폴더(`.credentials.json`) 쪽 오염은 못 본다 — 같이 손보면 좋다.

배선 전에 고치면 비용이 없다. 배선 후엔 "가끔 계정이 되돌아간다"라는 재현 안 되는 버그가 된다.

### 4-2. [잔금] `reorder_accounts`가 **중복 이메일 레코드를 유실**한다 — `claude.rs:254`

보고서 §7은 "**입력**에 같은 이메일이 두 번"만 의도적 차이로 적었다. 실제로는 **스토어에
같은 이메일 레코드가 둘**일 때 두 번째 레코드가 사라진다(암호화 토큰 백업이 통째로 날아간다).

```
스토어 3건 [dup(TOK-1), dup(TOK-2), ok(TOK-3)] → reorder(['ok','dup'])
  3.0   : 2건 (dup의 두 번째 = TOK-2 백업 소멸)
  2.6.2 : 3건 (참조 비교라 둘 다 남는다)
```

2.6.2의 정상 경로로는 중복 이메일이 안 생긴다(=현재 사용자 홈에는 없다). 그래서 잔금이지
결함은 아니다. 다만 **"드래그 한 번으로 credEnc가 사라진다"** 는 성질은 문서에 없어야 할 게
아니라 **없애야** 할 성질이다 — `next.push` 조건을 이메일이 아니라 인덱스로 잡으면 끝난다.

### 4-3. [잔금] usage 파서가 2.6.2와 **12/71 케이스**에서 다르다

응답 본문 71종을 두 파서에 같이 먹였다(2.6.2 파싱 블록 원문 이식 vs `ccg_auth::usage`).
전문 → `docs/critic/m5-r1-usage-diff.json`. **계정을 위협하는 건 하나도 없다**(전부 게이지
숫자·리셋 시각). 값어치 순:

| 입력 | 2.6.2 | 3.0 | 왜 문제인가 |
|---|---|---|---|
| `spend.enabled: 1` / `"yes"` | `enabled:true` | **`false`** | `as_bool()`이 JS `!!`가 아니다. 추가 크레딧 UI가 통째로 꺼진 것처럼 보인다 |
| `limits[].percent: "77"` / `true` | `weeklyFable.pct = 77` / `1` | **`0`** | `parse_usage_info`만 `as_f64` → `unwrap_or(0)`. **Fable 게이지가 0%로 뜬다**(= 한도가 텅 빈 줄 안다). `utilization`이 문자열로 온다는 걸 아는 API에서 `percent`만 숫자라고 믿을 근거가 없다 |
| `resets_at: "2026-08-20"` / `"…T15:00Z"` | 파싱됨 | **`null`** | `parse_iso8601_ms`가 `Date.parse` 대역보다 좁다(초 없음·날짜만 불가) |
| `resets_at: "…T15:00:00"`(존 없음) | **로컬시** | **UTC** | KST에서 9시간 어긋난 리셋 시각 |
| `utilization: "1e2"` / `"Infinity"` | 100 | **1 / 0** | `parse_float_prefix`가 지수 표기·`Infinity`를 모른다. 주석은 "JS `parseFloat` 그대로"라고 적혀 있다 |

앞 둘은 `as_bool`/`as_f64`를 JS 강제변환에 맞추면 각 한 줄이다.

### 4-4. [잔금] 관대성이 2.6.2보다 좁은 두 자리

- `read_store_file`: `version`이 **`3.0`(부동소수 표기)** 이면 JS는 `3.0 === 3`으로 통과하는데
  Rust는 `as_u64()` → `None` → **빈 스토어 = 계정 0건 = 재로그인 화면**(`claude.rs:83`).
  2.6.2가 그렇게 쓰는 일은 없지만, "스토어가 통째로 사라지는" 실패 모드치고는 `as_f64` 한 번이
  너무 싸다. (`"3"` 문자열은 양쪽 다 폐기 — 동등)
- `read_usage_cache`: `at` 누락·`pct`가 실수인 항목을 **버린다**(2.6.2는 `v && v.data`면 받음).
  2.6.2가 그렇게 쓰지 않으므로 무해. **보고서가 의도적 차이로 든 "4키 폴백형"은 실제로 읽힌다**
  — 확인했다. 다만 실홈 캐시 7항목은 전부 7키라 그 갈래는 **실홈 테스트가 안 밟는다**.

### 4-5. [메모] 테스트 커버리지 구멍(전부 파서 쪽)

`parse_usage_info`의 `weekly_fable` 갈래, `money`의 `{credits}` 래퍼·평범한 숫자·`cap→limit`
폴백, `to_ts`의 비-Z 오프셋 — 골든 JSON에 없다. §4-3의 불일치가 여기서 안 잡힌 이유다.
`real_account_folders_match_our_slug_and_junction_rules`는 "등록 계정 전부에 폴더가 있다"를
단정해서, 사용자가 계정을 추가만 하고 안 쓰면 **선의의 실패**로 빨개진다.

## 5. "의도적 차이" 타당성

| 차이 | 판정 |
|---|---|
| 계정 폴더 파일을 tmp→rename(2.6.2는 `writeFileSync`) | **타당·개선.** 잘린 `.credentials.json` = 로그아웃이라 원자성이 맞다 |
| `usage-cache.json`을 항상 7키로(2.6.2는 실패 시 4키) | **타당.** `protocol.ts:659`가 리셋 3필드를 `?`로 선언 = 두 형태 다 읽힌다(확인함) |
| Codex 창을 `label` 문자열 대신 `window_minutes`로 | **타당하되 배선 조건부.** 2.6.2 렌더러는 `'5h'`/`'Weekly'` **텍스트로** 시간창을 정렬한다. `window_label_en`을 배선이 반드시 써야 하고, 안 쓰면 정렬이 조용히 깨진다 |
| `reorder_accounts` 중복 제거 | **부분 타당** — §4-2. 입력 중복 제거는 맞지만 스토어 중복에서 레코드가 죽는다 |
