# R28 후속 — 사용자 직접 요청 2건 (08-24 접수)

현재 도는 R28 워크플로(빌더→크리틱)가 같은 파일을 만지는 중이라 **착지 직후** 별도 갈래로 실행한다.
두 건 다 2.6.2에서 사용자가 실사용 중 겪은 문제이고, 3.0에 그대로 이식됐거나(2번) 지금 구현 중인 자리(1번)다.

## 1. 한도 조회가 느리거나 안 됨 — 설정 Account 탭 + 채팅 쪽 계정 정보

**증상(사용자 보고)**: Account 눌렀을 때 한도 조회가 안 되거나 엄청 느릴 때가 있다. 채팅 쪽 계정 정보(계정 picker의 계정별 한도)도 마찬가지.

**원인(구조)**: 2.6.2 규약이 1200ms 직렬 × 계정 수 + 실 HTTP라, 계정이 N개면 첫 표시까지 수 초를 그냥 기다린다. 429/네트워크 실패면 「안 됨」으로 보인다. 3.0 T3(usage:get·auth:accounts-usage)가 지금 같은 규약으로 구현 중 — 규약(레이트 안전)은 유지하되 **UI가 그걸 기다리게 하면 안 된다**.

**고칠 것(3.0)**:
- **캐시 우선(stale-while-revalidate)**: 마지막으로 안 값(디스크 보존)을 즉시 그리고, 뒤에서 갱신. 첫 페인트가 HTTP를 기다리지 않게.
- 계정별 **로딩/실패 상태 분리** + 수동 재시도. 실패를 「데이터 없음」으로 뭉개지 않기.
- 1200ms 직렬·TTL(2분/5분/15초)·429 백오프 규약은 그대로(2.6.2 대조).
- 적용 표면 둘 다: 설정 ▸ Account 탭, 채팅 쪽 계정 picker(채팅별 계정 오버라이드).

**검증**: 계정 2개 이상 픽스처로 첫 페인트 시간(캐시 히트 시 <100ms급), 실패 주입 시 상태 표기·재시도 동작, TTL 준수.
**경계**: T3 구현부(src-tauri ipc usage + crates/ccg-auth) + 렌더러 두 표면. T3T4 갈래 착지 후 그 위에서.

## 2. Git 커밋이 파일 개수 많으면 실패

**증상(사용자 보고)**: 커밋할 때 파일 개수가 너무 많으면 안 된다고 한다.

**원인(확정)**: 선택 파일 전부를 **명령줄 인자**로 넘긴다.
- 2.6.2: `src/main/git.ts` `gitCommit` — `['add','-A','--',...files]`, 실패 롤백도 `['reset','--',...files]`.
- 3.0: `crates/ccg-fs/src/git.rs` `commit()` — 같은 패턴 그대로 이식됨(add_args/reset_args).
- Windows CreateProcess 명령줄 한계 32,767자 → 파일 수백 개·긴 경로면 스폰 자체가 실패.

**고칠 것(3.0 — 동결 2.6.2는 수정 금지)**: `crates/ccg-fs/src/git.rs`
- `git add -A --pathspec-from-file=- --pathspec-file-nul` — 경로를 **NUL 구분 stdin**으로. 롤백 reset도 동일.
- 커밋 메시지는 `commit -F -` (stdin)로 — 긴 본문·개행 보존 겸.
- 기존 오류 매핑(identity 미설정·nothing to commit 등) 동작 불변.
- 참고: `exec()`가 `stdin(Stdio::null())` 고정이라(git.rs:170) stdin 지원 변형이 필요.

**검증**: 임시 리포에 파일 2,000개(긴 경로 포함, 인자 합계 >32K 상당) 생성 → 커밋 성공. 유니코드·공백 경로. 훅 거부 시 스테이징 롤백이 여전히 도는지. 기존 ccg-fs git 테스트 무후퇴.
**경계**: crates/ccg-fs/src/git.rs (+필요시 ipc/git.rs). ※ T3T4 갈래가 git:ai-message로 같은 파일을 만질 수 있어 **워크플로 착지 후** 실행.
