# R28 후속 — 사용자 직접 요청 2건 (08-24 접수)

현재 도는 R28 워크플로(빌더→크리틱)가 같은 파일을 만지는 중이라 **착지 직후** 별도 갈래로 실행한다.
두 건 다 2.6.2에서 사용자가 실사용 중 겪은 문제이고, 3.0에 그대로 이식됐거나(2번) 지금 구현 중인 자리(1번)다.

## 1. 한도 조회가 느리거나 안 됨 — 설정 Account 탭 + 채팅 쪽 계정 정보

**증상(사용자 보고)**: Account 눌렀을 때 한도 조회가 안 되거나 엄청 느릴 때가 있다. 채팅 쪽 계정 정보(계정 picker의 계정별 한도)도 마찬가지.

**원인(구조)**: 2.6.2 규약이 1200ms 직렬 × 계정 수 + 실 HTTP라, 계정이 N개면 첫 표시까지 수 초를 그냥 기다린다. 429/네트워크 실패면 「안 됨」으로 보인다. 3.0 T3(usage:get·auth:accounts-usage)가 지금 같은 규약으로 구현 중 — 규약(레이트 안전)은 유지하되 **UI가 그걸 기다리게 하면 안 된다**.

**고칠 것(3.0)**:
- **캐시 우선(stale-while-revalidate)**: 마지막으로 안 값(디스크 보존)을 즉시 그리고, 뒤에서 갱신. 첫 페인트가 HTTP를 기다리지 않게.
- 계정별 **로딩/실패 상태 분리** + 수동 재시도. 실패를 「데이터 없음」으로 뭉개지 않기.
- 1200ms 직렬·TTL(2분/5분/15초)·429 백오프 규약은 그대로(2.6.2 대조).
- 적용 표면 둘 다: 설정 ▸ Account 탭, 채팅 쪽 계정 picker(채팅별 계정 오버라이드).

**성능 최적화(사용자 추가 요청)**:
- **디스크 캐시 부팅 로드**: 앱 재시작 직후에도 첫 페인트는 저장된 마지막 값으로 즉시.
- **선행 워밍**: 앱 시작·창 포커스 시 백그라운드로 미리 조회해, Account 탭을 열 때는 이미 따뜻한 캐시를 침.
- **우선순위 조회**: 활성(기본) 계정 먼저, 나머지는 뒤로 — 사용자가 보는 값이 제일 먼저 갱신.
- **단일 스토어 + 인플라이트 중복 제거**: Account 탭과 채팅 picker가 같은 조회를 공유(이중 HTTP 금지).
- **죽은 계정 격리**: 연속 실패 계정은 짧은 타임아웃+백오프로 건너뛰어 직렬 큐 전체를 막지 않게.

**검증**: 계정 2개 이상 픽스처로 첫 페인트 시간(캐시 히트 시 <100ms급), 콜드 부팅 직후 표시 시간, 실패 주입 시 상태 표기·재시도 동작, 두 표면 동시 오픈 시 HTTP 횟수(중복 0), TTL 준수.
**경계**: T3 구현부(src-tauri ipc usage + crates/ccg-auth) + 렌더러 두 표면. T3T4 갈래 착지 후 그 위에서.

## 2. Git 커밋이 파일 개수 많으면 실패

**증상(사용자 보고)**: 커밋할 때 파일 개수가 너무 많으면 안 된다고 한다.

**원인(확정)**: 선택 파일 전부를 **명령줄 인자**로 넘긴다.
- 2.6.2: `src/main/git.ts` `gitCommit` — `['add','-A','--',...files]`, 실패 롤백도 `['reset','--',...files]`.
- 3.0: `crates/ccg-fs/src/git.rs` `commit()` — 같은 패턴 그대로 이식됨(add_args/reset_args).
- Windows CreateProcess 명령줄 한계 32,767자 → 파일 수백 개·긴 경로면 스폰 자체가 실패.

**고칠 것(3.0 — 동결 2.6.2는 수정 금지)**: `crates/ccg-fs/src/git.rs`
- `git add -A --pathspec-from-file=- --pathspec-file-nul` — 경로를 **NUL 구분 stdin**으로. 롤백 reset도 동일.
- 커밋 메시지는 `commit -F -` (stdin)로 — 긴 본문·개행 보존 겸.
- 기존 오류 매핑(identity 미설정·nothing to commit 등) 동작 불변.
- 참고: `exec()`가 `stdin(Stdio::null())` 고정이라(git.rs:170) stdin 지원 변형이 필요.

**성능 최적화(사용자 추가 요청)**:
- **AI 커밋 메시지의 diff 수집을 스폰 1회로**: 2.6.2는 파일마다 `gitFileDiff`를 직렬 호출(N개 파일=N번 git 스폰 — 대량 커밋에서 수 초). 3.0은 `git diff -- <stdin pathspec>` **한 번**으로 전 파일을 받아 파싱하며 파일별/총량 캡 적용.
- **상태·커밋 흐름 스폰 수 절감**: 커밋 전후 status 재조회 등 연속 git 호출을 한 사이클로 정리(불필요 재스폰 제거).
- **대량 스테이징 계측**: 2,000파일 add가 stdin 방식에서 단일 스폰으로 도는지, 소요 시간 실측 보고.

**검증**: 임시 리포에 파일 2,000개(긴 경로 포함, 인자 합계 >32K 상당) 생성 → 커밋 성공 + 소요 시간. AI 메시지 생성의 git 스폰 횟수(파일 N개에 1~2회) 실측. 유니코드·공백 경로. 훅 거부 시 스테이징 롤백이 여전히 도는지. 기존 ccg-fs git 테스트 무후퇴.
**경계**: crates/ccg-fs/src/git.rs (+필요시 ipc/git.rs). ※ T3T4 갈래가 git:ai-message로 같은 파일을 만질 수 있어 **워크플로 착지 후** 실행.

## 3. 계정 「사용 중」 표시 — 세션이 물고 있는 계정을 picker에서 구분 (신기능, 08-24 접수)

**요청(사용자)**: 현재 세션에서 쓰고 있는 계정은 다른 곳에서 쓰면 안 되니, 계정 목록에서 구분되면 좋겠다. (스크린샷: 계정 picker의 lmg5663x 목록 — 어느 계정이 사용 중인지 표시가 없음)

**왜**: 같은 계정을 두 세션이 동시에 쓰면 같은 한도를 나눠 태우고, 계정 물질화(CLAUDE_CONFIG_DIR)·토큰 리프레시가 겹치면 되싱크 위험(M11이 고친 그 계열)도 있다. 지금은 사용자가 머릿속으로 기억해야 한다.

**설계**:
- **판정 소스(단일)**: 스토어에서 「계정 → 물고 있는 자리들」 역인덱스 계산. 물고 있다 = 채팅별 오버라이드 or 기본 계정으로 **살아있는 세션**(busy 턴 중이거나 상주 CLI 생존)이 바인딩된 상태. '완료' 표시 규칙과 같은 결로 effectiveStatus/bgActive를 단일 소스로 재사용.
- **UI**: picker 행과 설정 ▸ Account 목록 행에 「사용 중」 칩 + 어디인지(「2번 자리」·「추가 창」·「본채팅」, 여럿이면 개수). 톤은 경고(주황 계열)로 구분만 — **선택 차단은 안 한다**(사용자가 알고 고르는 건 존중). 이미 그 계정을 쓰는 자리에서 열면 「이 채팅」으로 표기.
- **갱신**: 세션 시작/종료·오버라이드 변경·busy 전이에 반응(스토어 팬아웃 경로 재사용 — poc-store-fanout 규약 주의).
- 적용 표면: 채팅 계정 picker(본채팅·멀티·추가 창) + 설정 ▸ Account 탭.

**검증**: 자리 2개에 같은 계정 물리고 picker를 열어 칩·위치 표기 확인, 세션 종료 시 칩 소멸(유예 포함), 오버라이드 바꿀 때 즉시 갱신, busy 아닌 상주-생존 상태도 「사용 중」으로 잡히는지.
**경계**: app/ 렌더러(picker·Account 탭·스토어) + 필요시 Rust 세션 상태 노출. 1번(한도 조회) 후속과 같은 표면이라 **같은 갈래에서 함께** 구현.
