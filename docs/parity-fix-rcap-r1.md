# R28c 「RCAP」 R1 — 재개의 **출구에 상한을 달고**, 사용자가 누를 버튼을 만든다

빌더: RCAP 갈래 · 2026-08-25 · `feature/3.0.0-beta`
과녁: RVERD 확인 크리틱 R1(`docs/critic/r28b-rverd-critic-r1.md`) **§3.1 최대 격차 + §3.2**

크리틱이 적은 지시 세 줄을 그대로 옮긴다:

> `LimitHold`에 재발사 계수(엔진 `attempts` 짝)를 넣고, 상한을 넘긴 표는 `ready`를 켜되
> **소진 effect가 쏘지 않게** 한다(엔진 `auto_paused` 짝). 그 표의 배너에는
> `LimitHoldBar`의 비-`managed` 갈래에 **「이어가기」 버튼이 없으므로 그것부터 만들어야 한다.**

셋 다 넣었고, 크리틱이 쓴 것과 **같은 대본**으로 다시 쟀다.

---

## 0. 한 문단 결론

**주기가 끊겼다.** 크리틱이 5시간 창 하나에서 잰 **눈감은 재발사 27회**가 **2회**가 되고,
세 번째 대기표는 아무것도 태우지 않은 채 **32분에 멎어** 사용자의 버튼을 기다린다.
고친 자리는 크리틱이 지목한 그대로다: 상한이 `probes`(재확인)만 세고 있었고 그건 **한 대기표
안에서만** 사는 값이라, 쏜 턴이 같은 한도로 또 죽으면 새 표가 백지로 서서 주기가 영원히 돌았다.
`LimitHold.attempts`(재발사)를 표에 실어 대기표 **사이를** 건너게 하고, 상한을 넘긴 표는
`ready + autoPaused`로 착지시킨 뒤 배너에 「이어가기」를 놨다 — 엔진이 `runtime.rs`에서 하는
착지와 글자 그대로 같다. **한 앱 안에서 같은 상황의 답이 하나**가 됐다.

| 무엇 | 수정 전(`63bf667` — 크리틱 실측) | 수정 후(내 실측) |
|---|---|---|
| 5시간 창 하나의 눈감은 재발사 | **27회**(11·22·32…290분) | **2회**(10.75분·21.5분) |
| 마지막 대기표 | `probes:1`로 살아 있다(끝이 없다) | **`ready + autoPaused`** · 32분에 멎음 |
| 그 표의 타이머 | 계속 돈다 | **0개**(아무것도 안 태운다) |
| 비-`managed` 배너의 버튼 | **✕ 하나** | **「이어가기」 + ✕** |
| 누른 재개의 대가 | (버튼이 없다) | 계수 0으로 복귀 — 다음 표는 백지 |
| `poc-limit-resume.mjs` | 164 통과 / 0 실패 | **197 통과 / 0 실패**(기존 164개 그대로 + 33개) |

## 1. 무엇을 고쳤나

### 1.1 재발사 계수 — `LimitHold.attempts` (`app/src/lib/limitResume.ts`)

`probes`와 **세는 대상이 다르다.** probes 한 칸은 *재확인*(usage 조회 1회)이고 attempts 한
칸은 *재발사*(CLI 턴 1회)다. 그래서 상한도 둘로 갈랐다.

* `MAX_RECHECKS = 2` — R28b까지 `MAX_AUTO_ATTEMPTS`라는 이름을 쓰던 그 상수. **이름만 엔진과
  같고 세는 대상이 달랐다**는 것이 크리틱 §3.1의 지적이라, 세는 것의 이름으로 바꿨다.
* `MAX_AUTO_ATTEMPTS = 2` — **새로 든 재발사 상한.** 엔진 `crates/ccg-engine/src/limit.rs`의
  같은 이름·같은 값·같은 뜻이다.

`resumeVerdict`의 착지 ③에 한 줄이 붙었다:

```ts
if ((hold.attempts ?? 0) >= MAX_AUTO_ATTEMPTS) return { kind: 'ready', paused: true }
return { kind: 'ready' }
```

**조회가 "풀렸다"고 말해도 접는다.** 그 말은 이미 두 번 틀렸기 때문이다 — 두 번의 재발사가
같은 한도로 죽었다는 것이 이 자리에서 얻을 수 있는 가장 신선한 증거다(조회보다 신선하다:
실제로 CLI를 태워 본 결과다). 엔진도 같은 이유로 `attempts >= MAX_AUTO_ATTEMPTS`를
`LimitVerdict::Clear` **뒤에** 둔다.

### 1.2 계수를 표에 물려주는 자리 (`app/src/lib/useLimitResume.ts`)

대기표는 **발사와 함께 걷힌다**(소진 effect가 `setHold(null)` 후 보낸다). 그래서 표 바깥에
값을 들고 있을 자리가 하나 필요하다 — 엔진의 `ChatRuntime::auto_resume_streak`에 해당하는
`firesRef`다. 장전이 그 값을 물려받는다:

```ts
at: Date.now(),
...(firesRef.current > 0 ? { attempts: firesRef.current } : {})
```

0으로 되돌아가는 자리는 **문 하나**로 모았다 — `setHold(null)`이다. ✕(대기 취소)·`/clear`·
폴더 변경·사용자의 직접 전송(busy 상승 에지)·「이어가기」가 전부 그 문을 지나고, 전부
"사람 손이 닿았다"는 뜻이다(엔진 `enqueue`의 `origin == User → streak = 0` 짝).
**예외는 자동 발사 하나**이고 그 두 자리는 그 줄 *뒤에* 계수를 자기 값으로 다시 놓는다.
여기에 하나 더 있다: 한도가 **아닌** 이유로 턴이 끝나면 연쇄가 끊긴다(엔진의
`!limited && hold.is_none()` 짝) — 이걸 안 하면 어제 쌓인 계수 2가 오늘 처음 서는 대기표를
태어나자마자 「자동 멈춤」으로 만든다.

### 1.3 소진 effect의 문 (`useLimitResume.ts` — 크리틱이 지목한 189-198)

```ts
if (!cur?.ready || cur.autoPaused || !o.enabled || o.busy || o.managed) return
```

`autoPaused`가 켜진 표는 `ready`지만 **여기서 막힌다.** 타이머 effect는 이미 `ready`에서 멎으므로
이 표는 아무것도 태우지 않고 버튼만 기다린다 — 엔진의 `auto_paused` 착지와 같다.

### 1.4 사용자가 누를 출구 (`app/src/components/Chat.tsx` — 3342-3377의 그 갈래)

버튼 조건은 순수 함수로 뺐다(`canPressContinue`). 엔진 축의 짝인 `resumeOwner.ts`의
`canPressResume`과 규칙이 같다: **아무도 안 쏘는 `ready`에만 버튼을 준다.** 렌더러에서 그
조건은 `autoPaused` 하나다 — 그 밖의 `ready`는 소진 effect가 같은 커밋에서 삼켜 전송으로
바꾸므로, 버튼을 두면 누를 게 없는 버튼(침묵 no-op · M-LOGIC P7)이 된다.

문장은 엔진이 같은 착지에서 쓰는 공지와 **같은 말**로 맞췄다:
「자동으로 이어서 보낸 turn이 계속 한도에 막혔어요 — 눌러서 이어가기」.
클래스도 `managed` 갈래와 같다(`.lh-go` · `.limit-hold.ready`) — CSS는 한 줄도 안 늘었다.
`.ready`는 **접힌 표에만** 붙였다: 그냥 `ready`는 곧 전송으로 바뀌는 찰나라 기존 모양을
건드리지 않는다.

훅은 `resumeNow`를 새로 내놓는다(엔진 `resume_now`의 짝). **계수를 0으로 되돌리는 것이
요점이다** — 안 되돌리면 이 발사가 또 죽었을 때 새 표가 `attempts:3`으로 서서 *누르자마자
다시 자동 멈춤*이 되고, 버튼은 한 번 쓰고 버리는 것이 된다.

## 2. 실측 — 크리틱과 **같은 대본**으로

`scripts/poc-limit-resume.mjs`에 I절을 붙였다. 판은 크리틱 §3.1과 같다: **시각 미상 대기표**
(codex 한도 문구엔 `…|epoch` 꼬리가 없다) + 조회가 계속 실패 + 쏜 턴이 같은 한도로 또 죽는다.
실제 훅(`useLimitResume.ts`)을 **한 글자도 안 고치고** 최소 훅 런타임 위에서 구동하고,
가짜 시계로 5시간을 돌린다. 대기표 하나의 벽시계는 `PROBE_MS 600s + 15s + 30s = 645s`다.

**대조군은 진짜 R28b다** — `git show 63bf667:app/src/lib/{limitResume,useLimitResume}.ts`를
%TEMP%에 꺼내 같은 대본을 먹였다(레포는 안 건드린다).

```
A/B — 5시간 눈감은 재발사: R28b(63bf667) 27회 · 마지막 290분  →  HEAD 2회 · 32분에 자동 정지
```

**27과 290분은 크리틱이 적은 값과 정확히 같다**(크리틱: "27회 — 11·22·32…290분").
같은 자를 쓴다는 증거로 그 숫자를 그대로 재현한 뒤에 고친 값을 잰다.

| 단언(I절) | 값 |
|---|---|
| 5시간 눈감은 재발사 | **2회** (`sent:2`) |
| 발사 시각 | **645,000ms · 1,290,000ms**(대기표당 600+15+30) |
| 세 번째 표 | `ready:true · autoPaused:true · attempts:2` |
| 접힌 표의 타이머 | **0개** |
| 그 뒤 5틱 더 | 발사 **0** |
| 멎은 시각 | **32분**(5시간을 다 쓰지 않는다) |
| 대조군 27발의 간격 | 645초 정각 · 마지막 표는 살아 있다(`autoPaused` 없음) |

「이어가기」와 계수 리셋도 실훅으로 쟀다:

| 단언 | 값 |
|---|---|
| 접힌 표에서 `resumeNow()` | 표 소진 · **전송 1회**(문구 = '이어서', 세션 있음) |
| 누른 뒤 다시 죽으면 | 새 표는 **백지**(`attempts` 없음) — 버튼이 일회용이 아니다 |
| 한도가 **아닌** 착지 뒤 | 새 표는 백지 |
| 대기 중 사용자가 직접 전송 | 표가 걷히고 새 표는 백지 |
| ✕(대기 취소) 뒤 | 새 표는 백지 |
| `canPressContinue` | 접힌 표만 `true`(그냥 `ready`·대기 중·표 없음 = `false`) |

### 무후퇴

기존 164개 단언은 **한 개도 지우거나 고치지 않았다**(하네스 diff의 삭제 줄 4개는 전부
`mountArmed` 배관 — `mod` 인자와 `api` 게터를 더한 자리다). 197 = 164 + 33.

```

npm run typecheck (node·web) + typecheck:app  → 3종 초록

```

## 3. 커밋 메시지 정정 — `63bf667`의 두 문구

크리틱 §3.2가 요구한 정정을 기록한다. 이 갈래는 커밋 메시지를 사실로 취급하는 규약이므로,
지난 라운드의 두 문장이 실물과 어긋난 자리를 명시한다.

**① "3회차에 ready(이어가기 버튼 + 자동 재개 출구)" — 「이어가기 버튼」은 없었다.**
렌더러가 든 대기표에서 `ready`는 소진 effect(`useLimitResume.ts:189-198`)가 **그 즉시** 삼켜
전송으로 바꿨고, `LimitHoldBar`의 비-`managed` 갈래(`Chat.tsx:3342-3377`)에는 **✕ 하나뿐**이었다
(「이어가기」는 `managed` 갈래에만 있었다). 즉 R28b가 만든 것은 **자동 발사 출구 하나**이고
사용자가 누를 출구는 없었다. 보고서 `docs/parity-fix-rverd-r1.md` §1.1은 이 사실을 바르게
적었는데 커밋 메시지만 반대로 적혀 있었다. **이번 라운드에서 그 버튼을 실제로 만들었으므로,
그 문장은 「R28c부터 참」이다.**

**② "눈감고 한 번 쏜다" — 「한 번」이 아니라 「한 대기표당 한 번」이었다.**
대기표는 쏜 턴이 같은 한도로 죽을 때마다 다시 서고, 새 표는 백지(`probes:0`)였다. 그래서
실제 횟수는 **5시간에 27회**다(위 대조군 주행이 그 27을 재현했다). 정확한 문장은
*"한 대기표당 한 번 쏘고, 대기표는 645초마다 다시 선다"*이며, **이번 라운드에서 그 주기에
상한(2)이 생겨 이제 「5시간에 두 번」이 참이다.**

## 4. 남은 것 · 안 한 것

* **라이브 주행은 안 했다.** 접힌 표에 실제로 도달하려면 실 CLI를 두 번 태우고 21분을 기다려야
  한다(645초 × 2). 대신 **실제 훅 소스를 그대로 구동하는 A/B**로 쟀고 대조군은 진짜 `63bf667`
  판이다. 배너는 타입 검사 + 판정 함수(`canPressContinue`)까지만 봤고 **픽셀은 안 봤다** —
  버튼의 클래스·자리는 `managed` 갈래(이미 화면에 있는 것)와 같은 문법을 그대로 썼다.
* **경계 밖 5파일에 배선 hunk가 들어갔다.** 지시의 [경계]는 `limitResume.ts`·`useLimitResume.ts`·
  `Chat.tsx`·하네스였는데, **버튼이 실제로 눌리려면** 배너를 그리는 네 표면이 핸들러를 넘겨야
  한다. 각각 최소 hunk다: `App.tsx`(1줄) · `SessionWindow.tsx`(1줄) · `PanelWindow.tsx`(1줄) ·
  `MultiAgent.tsx`(prop 선언·구조분해·`useEvent` 정의·JSX 2곳). 안 넘겼으면 버튼이 영영 안
  그려지는 죽은 코드가 된다.
* **`enabled`가 꺼진 표에는 여전히 버튼이 없다.** 토글이 꺼져 있으면 타이머 자체가 안 돌아
  `ready`에 닿지 못하기 때문이고, 그 상태의 배너는 이미 "토글을 켜라"고 말한다. 이 라운드의
  과녁이 아니라 손대지 않았다.
* **크리틱 §3.3(전역 codex 설치본의 빈 창)·§3.4(`resync_plan` 락)는 이 갈래의 자리가 아니다** —
  뿌리가 CRIT 갈래(`is_file()` 문지기)와 `ccg-auth`에 있다. 다만 §3.3이 참인 동안 27회를 맞던
  바로 그 사용자가 이제 **2회 뒤 버튼**을 받는다는 점은 여기서 닫혔다.
