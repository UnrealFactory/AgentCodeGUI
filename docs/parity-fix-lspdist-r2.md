## 0. 한 줄

크리틱이 **가장 큰 격차**로 꼽은 것을 닫았다: **고정 판 `node.exe`가 설치기에 실린다**

그리고 크리틱이 「구멍」이라 부른 그물 둘(C3 매니페스트 계약 · C4 cwd 못)을
**돌연변이 6종이 전부 붉어질 때까지** 다시 짰다.

판정문의 **중 5 · 낮음 4를 전부 닫았다** — 코드로 닫은 것 셋(C3·C4 + 최대 격차),

## 2. 최대 격차를 어떻게 닫았나 — 판 고정 다운로드

R1은 이 일을 **크기가 아니라 재현성** 때문에 미뤘다: 손에 있던 방법이 「빌더 PC의
`node.exe` 복사」뿐이라 설치기가 **빌드한 사람의 node 판**에 따라 달라졌다.
R2는 그 사유를 정면으로 없앤다.

### 2.1 파이프라인

```
scripts/tauri-build.mjs
  NODE_PIN = { version: 'v24.20.0', sha256: '5c976096…c707b5', bytes: 93381448 }
        │
        ├─ 캐시가 있고 sha256·크기가 핀과 같다        → 그대로 쓴다
        ├─ 다르다(1바이트만 상해도)                    → 버리고 다시 받는다
        └─ 받는다 → **임시 파일** → sha256 검증 → 통과해야 제자리로 rename
                                     └ 실패 → 사유를 말하고 exit 1 (cargo를 켜기 전에)
        ▼
  src-tauri/lsp-runtime/node.exe        (.gitignore — 89.06MB는 커밋 못 한다)
        ▼  tauri.conf.json  "lsp-runtime/node.exe": "node.exe"
  $INSTDIR\node.exe                      (installer.nsi:6948의 File /a 한 줄)
        ▼  crates/ccg-lsp/src/launch.rs::node_exe() ②
  언어 서버가 그 node로 뜬다
```

**서명 키 래퍼와 같은 규약**: 일찍, 사유를 말하고 실패한다. 검증 안 된 바이너리를
사용자 PC에 싣느니 빌드를 안 만드는 쪽이다. 오프라인 빌더를 위한 문도 열어 뒀다 —
그 자리에 파일을 직접 두면 해시를 **다시 검증**하고 통과시킨다.

`node scripts/tauri-build.mjs stage`로 **굽지 않고 런타임만** 받을 수 있다(하네스·개발자용,
서명 키를 안 묻는다).

### 2.2 런처: 배포본에서 PATH를 끊는다

| 칸 | 자리 | 누가 쓰나 |
|---|---|---|
| ① | `CCG_LSP_NODE` | 벤치·포터블·하네스 |
| ② | **exe 폴더 / `exe/resources`** | **배포본**(스테이징한 고정 판) |
| ③ | exe **조상**의 `src-tauri/lsp-runtime/node.exe` | 개발·벤치 — 같은 산출물을 레포 안에서 문다 |
| ④ | PATH — **exe가 cargo 산출 폴더일 때만** | 스테이징 전의 `cargo run` 개발자 |

크리틱과 조율자가 요구한 것은 **「PATH 폴백 금지 — 결정론」**이고, 동시에
**「개발 실행은 기존대로」**다. 둘을 같이 만족시키는 값이 ④의 게이트다:
판정을 **`.cargo-lock`**(cargo가 프로필 폴더에 두는 잠금 파일)의 존재로 한다 —
`tauri_utils::platform::resource_dir`가 「개발 중인가」를 가르는 데 쓰는 바로 그 신호다.
NSIS가 깐 `$INSTDIR`에는 그 파일이 없다. 그래서 ④는 **exe 경로의 함수**이지 환경의
함수가 아니고, 배포본은 **구조적으로** 거기 못 간다
(테스트 `path_fallback_is_unreachable_for_a_deployed_exe`).

> **★R3 정정(확인 크리틱 R2-L2)** — 이 문단은 **상류를 반만 가져왔고 인용도 부정확했다.**
> `tauri_utils::platform`(2.9.3)은 `is_cargo_output_directory`를 **단독으로 안 쓴다** —
> `target` 폴더명 조건을 **AND로 더** 걸고 주석에 *"This ensures the check is safer so it
> doesn't affect apps in production"*이라 적어 뒀다. 게다가 **Windows에서는
> `cfg!(target_os = "windows")`가 먼저 단락되어 상류가 `.cargo-lock`을 아예 안 본다** —
> 그러니 「그 신호」라는 서술은 이 플랫폼에서 성립하지 않았다.
> 대가는 실측됐다(크리틱 G6): `$INSTDIR`에 **0바이트 `.cargo-lock`**을 심으면 PATH 칸이
> 열려 미끼 node를 물었다. **R3이 상류의 조건을 마저 가져와 닫았다**(단, 이 레포는
> `target-lspdist`처럼 접미사 붙은 타깃 폴더를 쓰므로 `starts_with("target")`).
> 실측은 `-r3.md` §3.2.

> **정직하게**: 이건 「PATH를 지웠다」가 아니라 **「배포본에서 PATH를 도달 불가로 만들었다」**이다.
> 둘의 차이가 중요한 곳은 하나뿐 — 사이드카가 **없어진** 설치본(백신 격리 등)이다. 그 경우
> 이제 PATH로 조용히 살아나지 않고 **소리 내어 죽는다.** 그 교환은 의도한 것이다(§6.1).

| 파일 | 변화 |

| `crates/ccg-lsp/tests/cwd_is_never_consulted.rs` | **신설** — 진짜로 cwd를 바꿔 놓고 `shipped_module()`에 묻는 통합 테스트 |

엔진 파일(`manager.rs`·`rpc.rs`·`server.rs`)은 **0줄**이다.

**확장점 기준은 안 깼다.** 새 언어 = `SPECS` 1항목 + (Node 서버면) 매니페스트 1줄.
달라진 것은 **그 1줄을 빠뜨렸을 때 붉어지는 범위**다 — R1은 패키지를 통째로 빼야
붉어졌고, 이제는 **파일 하나만 빠져도** 붉어진다. 런타임도 같은 계약 안에 들어왔다:
`Launch::Node` 스펙이 하나라도 있으면 매니페스트에 node 런타임이 있어야 한다.

## 4. 실측

### 4.1 풋프린트 — node를 실은 값

| | 설치기(NSIS·lzma) | 설치 폴더 | 파일 수 |
|---|---:|---:|---:|
| 3.0 R1(모듈만) | 8,971,808 B (8.56MB) | 약 65MB | 5,428 |
| **3.0 R2(모듈+런타임)** | **32,410,863 B (30.91MB)** | **150MB**(실측 `du`) | **5,429** |
| 차(R1→R2) | **+23,439,055 B (+22.35MB)** | +85MB | +1 (`node.exe`) |
| 2.6.2(분모) | 165,119,775 B (157.47MB) | 650MB | 8,139 |
| **2.6.2 대비** | **19.6%** | **23.1%** | 66.7% |

> 파일 수는 `node_modules` 5,426 + `AgentCodeGUI3.exe` + `uninstall.exe`(+R2는 `node.exe`).
> `150MB`는 배포 모사 폴더의 `du` 실측이라 NSIS가 만드는 `uninstall.exe`가 빠져 있다(수백 KB).

- 적재물 실측(생성된 `installer.nsi`의 `File /a` 줄): **5,427 항목** =
  `node_modules` 5,426파일(43.53MB) + **`node.exe` 1개(89.06MB)**.
  `node.exe`는 `installer.nsi:6948`에 `File /a "/oname=node.exe"` 한 줄로 들어간다.
- 설치기 증가분 22.35MB는 R1이 lzma로 예측한 **21.81MB**(v24.13.1 기준)와 같은 자리다
  (판이 24.13.1 → 24.20.0으로 올라 원본이 87.17 → 89.06MB가 됐다).
- **「2.6.2 대비 대폭 감소」는 유지된다**: 설치기 157.5MB → 30.9MB(80.4% 감소),
  설치 폴더 650MB → 150MB(76.9% 감소). R1의 5.4%/10.0%보다는 무거워졌고, 그 값이
  **「전제 0」을 사는 가격**이다.
- **자동 업데이트 비용**: 매 업데이트가 8.6MB → **30.9MB**를 받아 간다(NSIS 설치기 통째).
  2.6.2는 157.5MB였다.

### 4.2 ★ 최대 격차 — PATH에 node 없는 기계

크리틱 §1.2가 쟀던 그 표를 같은 모양으로 다시 잰다. PATH에서 `node.exe`가 있는
디렉터리를 전부 걷어낸 뒤(모사가 성립하는지 먼저 확인한다) 배포 모사에서 돌린다.

| 팔 | 크리틱 R1 실측 | **R2 실측** |
|---|---|---|
| `nonode/install-cwd` · ts | error · `node=null` | **ready · hover 6/6 · 토큰 1,565** |
| `nonode/install-cwd` · py | error · `node=null` | **ready · hover 6/6** |
| `nonode/project-cwd` · ts | error · `node=null` | **ready · hover 6/6 · 토큰 1,565** |
| `nonode/project-cwd` · py | error · `node=null` | **ready · hover 6/6** |

네 팔 모두 `resolve.node`가 **번들 사이드카**를 가리킨다
(`…\ccg-lspdist-r2\bundled\node.exe`) — PATH의 무언가를 우연히 문 것이 아니다.

**R1 회귀 가드**(PATH 정상 · 두 cwd): 두 언어 다 `ready`이고 `resolve.modules`와
`resolve.node`가 **두 팔에서 동일**하다. R1이 세운 결정론은 그대로다.

### 4.3 ★ 그물 — 돌연변이 6종이 전부 붉어진다

크리틱이 「초록이었다」고 실측한 두 칸을 포함해, 격리 사본에서 6종을 돌렸다
(제품 트리 무접촉을 매회 확인한다).

| # | 돌연변이 | R1 | **R2** | 무는 못 |
|---|---|---|---|---|
| C3-a | `"…/typescript/lib"` **한 줄만** 삭제 | **초록** ✖ | **red** ✅ | `every_bundled_file_is_covered_by_the_installer_manifest` |
| C3-b | `"…/tsls/package.json"` **한 줄만** 삭제 | **초록** ✖ | **red** ✅ | 〃 |
| R2-c | `"lsp-runtime/node.exe"` 한 줄 삭제 | (없던 계약) | **red** ✅ | 〃(런타임 계약) |
| C4-a | `module_roots_from`에 cwd 부활 | red ✅ | **red** ✅ | `the_search_chain_is_exactly_exe_shaped_and_has_no_cwd` |
| C4-b | **`module_roots()`**에 cwd 부활 | **초록** ✖ | **red** ✅ | `the_public_layer_adds_nothing_to_the_pure_chain` |
| C4-c | **`shipped_module()`**에 cwd 부활 | (미측정) | **red** ✅ | `tests/cwd_is_never_consulted.rs`(통합) |

- **C3의 처방**은 계약의 **단위를 내린 것**이다. `bundled_files()`가 내는 것은 이제
  패키지 이름이 아니라 **파일 경로**이고, 매니페스트의 어느 항목이 그 파일을 덮는지를
  경로로 검사한다(`dest == p` 또는 `p.startsWith(dest + "/")`).
  덤으로 **`<진입 패키지>/package.json`을 모든 `Launch::Node`에 자동으로** 건다 —
  R1 §5가 한 절을 통째로 쓴 ENOENT 함정을 **한 서버의 사고가 아니라 규칙**으로 올렸다.
  다음 언어는 그 함정을 밟을 기회 자체가 없다.
- **C4의 처방**은 못을 **층마다** 박은 것이다. 특히 C4-c는 **진짜로 프로세스 cwd를
  미끼 폴더로 바꿔 놓고** 공개 진입점에 묻는다 — 어느 층에 cwd가 되살아나든 붉어진다.
  통합 테스트(별도 프로세스)로 둔 이유는 `set_current_dir`가 프로세스 전역이라
  `--lib` 스레드 풀에 두면 옆 테스트를 조용히 흔들기 때문이다.
  위양성 방지로 **대조군**을 같이 둔다: 같은 자리를 `CCG_LSP_MODULES`로 주면 찾아야 한다
  (안 그러면 `None`이 「cwd를 안 본다」가 아니라 「아무것도 못 찾는다」의 결과일 수 있다).

### 4.4 스테이징 무결성

| 검사 | 결과 |
|---|---|
| **1바이트만** 바꾼 캐시(크기 동일)를 거절하는가 | **거절** ✅ — 크기가 아니라 sha256으로 판정 |
| 못 받으면 사유를 말하고 죽는가 | **exit 1** + 「LSP용 Node 런타임을 준비하지 못했다」 ✅ |
| 원상복구 뒤 다시 캐시 적중하는가 | ✅ (제품 트리 무손상) |

첫 줄이 중요하다 — 크기로만 거르는 구현이면 통과해 버린다.

### 4.5 메모리 — 안 움직였다(그리고 왜 재야 했나)

번들링은 **디스크의 일**이라 RAM은 안 움직여야 한다. 다만 이번에 헬퍼가 **다른 node 판**

## 5. 서술로 닫은 것 — R1 보고서에 박은 ★R2 정정 (문장은 안 지웠다)

`docs/parity-fix-lspdist-r1.md`에 정정 인용구 **8개**를 박았다. 틀린 문장을 지우면
다음 사람이 「무엇이 왜 틀렸는지」를 못 배우므로, 원문을 남기고 그 아래에 붙였다.

### 5.1 C1 — 「해소」가 아니라 「좁혀짐」이었다 (§0 · §4.3)
§1.6-A2의 문장은 「배포본이 LSP 없음/있음 **두 상태**를 갖는다」다. R1이 없앤 것은
**두 상태**이지 「없음」이 아니었다. R1의 결론 문장은 **「PATH에 node가 있는 기계에서」**를
지고 있어야 했다. 나머지 절반은 이 라운드가 닫았다(§4.2).

### 5.2 C2 — 「어차피 npm 필요」는 실행 경로에서 거짓 (§6.1)
`claude_bin()`은 ① `CCG_CLAUDE_BIN` → ② 앱 홈의 `claude.exe` → ③ **PATH의 `claude.exe`**
이고 셋 다 node를 안 지난다. codex도 `codex.cmd` shim을 **일부러 피한다**.
npm은 설치·목록에만 쓰인다. 결정적으로 같은 파일이 `…\.local\bin\claude.exe`
(**네이티브 설치기** 경로)를 적어 두고 있다 — **「엔진은 되는데 LSP만 죽는」 구성이
1급으로 지원된다**는 뜻이다. 그 기계의 사용자가 보는 증상은
「앱은 잘 되는데 코드에 색이 안 칠해진다」이고, 그건 §1.6-A2가 세 라운드를 먹은 그 증상과
**구별이 안 된다.** 이 완화 논거가 거짓이었다는 사실이 §4의 우선순위를 뒷받침한다.

### 5.3 C5 — 보조 논거 둘이 틀렸다 (§6.5)
- **(가)** `7 → 9`는 LSP가 아니라 **하네스가 연 창 2개**다(`windowCost.procsAdded = 2` ·
  `procDetail`은 창을 연 뒤에 찍힌다). 즉 2.6.2 정착 시점 7개의 LSP 유무는 **여전히 미확인**.
- **(나)** 「G1이 이 흠에 덜 민감하다」는 **거꾸로**다. 같은 규칙이 3.0에서는 125MB를 빼고
  2.6.2에서는 0을 뺀다(정규식이 `electron.exe`를 못 무니까). 2.6.2에 LSP가 들어 있었다면
  G1은 **3.0에 유리하게 기울어** 있고 거칠게 잡아도 0.74로 제안선을 넘길 수 있다.
  **G1은 가장 둔감한 수가 아니라 가장 오염되기 쉬운 수다.**
- 본론(「2.6.2 헬퍼 0」은 분류 산물)은 참이고 크리틱도 인정했다. 재측정은 여전히 경계 밖이라
  **안 했다** — 확대한 것은 「미확인」 딱지뿐이다.

### 5.4 L1 — `362`가 왜 나왔나 (§4.5)
`cargo test --workspace` 출력을 **`| tail -30`으로 잘라 보고** 화면에 남은 `test result:`
줄 **15개만 합산**했다. 테스트 바이너리가 **35개**라 스무 줄이 잘려 나갔다.
오늘 파서로 다시 세니 **795 / 0 / 14**다(크리틱은 R1 트리에서 787 — 그 사이 옆 갈래의
신설분과 이번 신설분이 더해졌다). 하위 주장은 전부 정확했으므로 **무후퇴 결론은 유효**하고
합계만 틀렸다. **교훈: 합계를 눈으로 세지 마라.**

### 5.5 L4 — 띠의 크기를 짝이 맞는 수로 갈아 끼웠다 (§4.4)
`153.2MB`는 exe도 세션도 다른 두 수(`0a3e5384…` 3회 ↔ `feaddb64…` 1회)의 차였다.
**띠의 존재는 참**이지만(§4.3의 옛 코드 팔이 독립으로 증명한다) 크기는 그 짝에서 나올 수
없다. 같은 exe·같은 세션의 짝으로 말할 수 있는 값은 **팔 A의 헬퍼 합 126.5MB**
(577.3 − 450.8)이고, 띠가 「헬퍼가 뜨느냐 마느냐」였으므로 그것이 곧 띠의 크기다.

### 5.6 L2 · L3
`resources 4줄` → **5개 항목**(R1 시점) · 지금은 **6개**. 2.6.2 파일 수 `8,141` → **8,139**.
둘 다 R1 보고서에 정정 표기. L2는 하필 「`package.json`을 빼먹어서 죽었다」를 적은
라운드의 항목 수 오기라 무해하지 않다 — 커밋 `ef03f73` 메시지에도 같은 오기가 있다.

## 6. 남은 것 — 정직하게

### 6.1 ★ 사이드카가 사라진 설치본은 이제 조용히 안 살아난다
PATH 폴백을 배포본에서 끊었으므로, `$INSTDIR\node.exe`가 **없어지면**(백신 격리·부분 설치·
사용자가 지움) TS·Python이 죽는다. R1이었다면 PATH의 아무 node나 물어 살아났을 것이다.
**의도한 교환이다** — 조용히 검증 안 된 판을 무는 것보다 소리 내어 죽는 편이 낫고,
실패 문자열이 그 경로를 지목한다.

> **★R3 정정(확인 크리틱 R2-C1)** — **뒷절은 거짓이었다.** `server.rs:139`는 R2에서 **한 줄도
> 안 바뀌었고**(마지막 변경은 R1의 `adcef10`), 그 문장은 여전히
> *"CCG_LSP_NODE · exe 옆 node.exe · **PATH** 순으로 찾는다"*였다. 이 문자열이 뜨는 상황은
> 정확히 **배포본 + 사이드카 유실**인데 거기서 PATH는 **안 본다**. 사슬 ③은 언급도 없었고
> 뒤진 경로도 하나도 안 실었다. 그 사용자는 「node를 설치하라」는 **헛수고**로 보내졌다.
> §1.6-A2가 세 라운드를 먹은 이유의 절반(*"실패가 조용했다"*)과 같은 병이고, R1이 모듈 쪽에
> `module_search_hint()`로 고친 것을 런타임 쪽에 **대칭으로 안 놓은** 결과다.
> **R3이 닫았다** — `launch::node_search_hint()`가 사슬과 **같은 목록**에서 문장을 만들고,
> `server.rs`가 그것을 그대로 쓴다. 실측은 `docs/parity-fix-lspdist-r3.md` §3.1. 다만 **89MB짜리 서명 없는 `node.exe`는 백신이
좋아하는 모양**이라는 것은 실재하는 위험이다(이번 라운드에서 백신 상호작용은 안 쟀다).
관측되면 되돌리는 비용은 낮다 — `node_exe_from`의 ④ 게이트 한 줄이다.

### 6.2 판 올리기가 수동이다
`NODE_PIN`을 사람이 고친다(버전 + sha256 + bytes 세 값). 자동 갱신은 안 만들었다 —
런타임 판올림은 **의도적인 결정**이어야 하고, 자동화하면 「어느 판이 사용자에게 갔는지」가
빌드 시각에 따라 달라진다. 대신 틀리면 **빌드가 죽는다**(해시 불일치).
`SHASUMS256.txt`와의 대조는 안 한다 — 핀이 틀리면 어차피 내려받은 파일의 해시가 안 맞는다.

### 6.3 유령 바이트는 그대로 (약 14.1MB)
`_tsc.js` 5.95 · 로케일 4.27 · pyright 소스맵 2.55 · `cli.mjs.map` 1.35MB
(크리틱 실측). R1과 같은 이유로 안 건드렸다 — 파일 목록 수기 관리 비용을 안 받았다.
이제 설치 폴더가 150MB라 비중은 9.4%로 더 작아졌다.

### 6.4 2.6.2 분모의 LSP 상태는 **여전히 미확인** (C5)
§5.3. 이번 라운드도 재측정 안 했다(경계 밖). §4.1의 풋프린트 비율은 **디스크 실측**이라
이 흠과 무관하지만, **메모리 비율(0.79~0.80 · G1 0.62)은 여전히 단서를 달아야 인용할 수
있다.** 다음 라운드 숙제: 헬퍼 분류를 이름이 아니라 **부모-자식 관계**로 바꾸거나,
2.6.2 팔을 LSP가 확실히 뜬 상태로 다시 재라.

### 6.5 설치기를 **실행해서** 검증하지는 않았다 (R1 §6.6과 같은 유보)
사용자 실앱이 깔려 있어 NSIS를 돌리면 그것을 건드린다. 배포 모사는 makensis에 넘어가는
`installer.nsi`의 `File /a` 줄을 복제해 만든다. `node.exe`도 그 줄로 확인했고
(`installer.nsi:6948`), 언인스톨 짝(`Delete "$INSTDIR\node.exe"`)도 생성돼 있다.
「설치기를 돌리면 그 배치가 된다」의 마지막 한 칸은 **깨끗한 VM의 일**로 남긴다.

### 6.6 `stage`가 `tauri:dev`에는 안 걸려 있다
`npm run tauri:dev`는 래퍼를 안 거치므로 런타임을 안 받는다. 그 경로는 ④(PATH · cargo
산출 폴더)가 받쳐 주고, 한 번이라도 `npm run tauri:build`(또는 `… stage`)를 돌린 개발자는
③이 받쳐 준다. **`package.json`은 이 라운드의 경계 밖**이라 `tauri:dev`에 스테이징을
끼우지 않았다 — 다음에 그 파일을 여는 사람이 한 줄 더하면 된다.

## 7. 재현

```bash
# ① 런타임만 받기(굽지 않는다 · 서명 키 안 묻는다)
node scripts/tauri-build.mjs stage

# ② 설치기(서명) — 공용 target/ 무접촉. 스테이징은 이 안에서 자동으로 돈다
CARGO_TARGET_DIR=target-lspdist npm run tauri:build

# ③ PoC — A(PATH에 node 없음 네 팔) · B(결정론 회귀) · C(돌연변이 6종) · D(스테이징 무결성)
node scripts/poc-lspdist-r2.mjs            # → bench/results/poc-lspdist-r2.json
#   돌연변이만 건너뛰려면 --skip-mutations (격리 사본에서 cargo test를 7번 돈다)

# ④ 메모리(기준 파일 무접촉 — --out 필수 · 포트 11000~11010)
SIM=%LOCALAPPDATA%\ccg-lspdist-r2-app      # exe + node_modules + node.exe
node bench/multi.mjs tauri --repeats=3 --tag=lspdistr2 --port=11003 \
     --exe="$SIM\AgentCodeGUI3.exe" --cwd="$SIM" \
     --out=multi-tauri-3.0.0-default-lspdistr2-instcwd.json

# ⑤ 무후퇴 — 합계는 **파서로** 센다(눈으로 세지 마라: L1)
CARGO_TARGET_DIR=target-lspdist cargo test --workspace 2>&1 | grep "^test result" | \
  node -e "let p=0,f=0,i=0,n=0;require('readline').createInterface({input:process.stdin})\
    .on('line',l=>{const m=/(\d+) passed; (\d+) failed; (\d+) ignored/.exec(l);\
      if(m){p+=+m[1];f+=+m[2];i+=+m[3];n++}}).on('close',()=>console.log(n,p,f,i))"
```

기준 결과 파일(`multi-tauri-3.0.0-default-r28jdecr1-*.json` ·
`multi-electron-2.6.2-default-r28jdecr1.json` · R1의 `-lspdist-*.json`)은 **덮지 마라.**
