# M1 R3 — 메모리·콜드 스타트 (실측 라운드)

라운드 3 · 2026-08-22 · 브랜치 `feature/3.0.0-beta` · 앞 라운드: `docs/m1-report.md`(R1)

자기 채점은 하지 않는다. **무엇을 했고, 무엇이 몇에서 몇이 됐고, 무엇이 아직 안 되는지**의
기록이다. 판정은 크리틱 몫.

## 0. 한 문단 요약

주 게이트(멀티 4패널 유휴)에서 **Private은 목표를 넘겼고(같은 빌드에서 GPU 프로세스를
분리한 팔 337.4 → 251.6MB, 목표 ≤253 — 다만 5회 중 1회는 258.4로 넘었다),
WS는 못 넘겼다(491.2 → 475.7MB, 목표 ≤356).** 콜드 스타트는 두 목표 모두 못 넘겼고
**구조적으로 못 넘긴다** — 프로세스 스폰부터 페이지 `timeOrigin`까지가 이미 202~240ms라
'첫 가시 창 ≤168ms'는 웹 콘텐츠를 한 픽셀도 그리지 않아도 불가능하다(§4).
가장 중요한 발견은 레버가 아니라 **분모**다: 4패널 × 120항목 UI를 통째로 지워도
유휴가 446 → 438MB밖에 안 내려간다 — **우리 앱 몫은 WS 8.4MB / Priv 24MB**이고
나머지 전부가 WebView2 런타임 바닥값이다(§3). 렌더러 다이어트로 갈 길이 없다는 뜻이고,
WS 목표에 닿는 유일한 실측 경로는 `--single-process`(WS 358.8 / Priv 211.3 / 3프로세스)인데
Microsoft 미지원 스위치라 기본값으로 삼지 않고 `CCG_SINGLE_PROCESS=1` 옵트인으로 뒀다(§5).

## 3. ★ 가장 중요한 실측 — "우리 앱은 8MB다"

`bench/gpuprobe.mjs tauri` — 살아 있는 4패널 앱에 오버라이드를 하나씩 누적으로 얹으며
역할별로 다시 잰 값(`bench/results/gpu-css-probe.json`):

| 단계 | 총 WS / Priv | gpu-process | renderer | JS 힙 |
|---|---|---|---|---|
| 0 기준(4패널 × 120항목) | 446.2 / 301.4 | 79.1 / 123 | 151.5 / 103.8 | 8.4MB |
| 1 `.blurwarm` 숨김 | 452.6 / 307.4 | 80.2 / 132.7 | 147.9 / 99.5 | 8.4 |
| 2 모든 `backdrop-filter` 제거 | 452.0 / 306.7 | 80.2 / 132.7 | 147.4 / 98.9 | 8.4 |
| 3 모든 `box-shadow` 제거 | 450.9 / 292.0 | 82.4 / 117 | 149.2 / 100.4 | 8.4 |
| 4 패널 1개만 표시 | 442.7 / 287.6 | 82.3 / 120.9 | 141.2 / 92.1 | 8.4 |
| 5 **`#root` 통째로 비움** | **437.8 / 277.1** | 80.9 / 113.9 | 137.7 / 88.7 | 8.4 |

**0 → 5 차이 = WS 8.4MB / Priv 24.3MB.** 이게 우리 UI 전부의 값이다.
`bench/heap.mjs`가 같은 말을 다른 각도로 한다: v8+Blink 힙 **24MB**, DOM 4,616노드
(패널당 1,117), 상위 항목은 우리 객체가 아니라 Blink 내부(FontCache 2.33MB,
ExternalStringData 2.03MB, InstructionStream 1.39MB). 우리 문자열 전부가 1.04MB다.

따라서:

- `docs/memory-strategy.md`의 **2군(렌더러 다이어트)은 죽은 길이다.** 번들을 반으로
  줄여도 유휴에서 되찾을 수 있는 건 한 자릿수 MB다.
- 번들 분할도 같은 이유로 기각했다. 진입 청크 972kB 중 `highlight.js/lib/common`
  157kB + `react-markdown` 123kB = 280kB인데(esbuild 단독 번들 실측), **둘 다 첫 렌더
  경로에 있다**(픽스처 메시지가 마크다운 + 코드펜스다). 지연 로드는 같은 일을 뒤로
  미룰 뿐이고, hljs를 언어 부분집합으로 좁히는 건 동작이 달라진다(파리티 위반).
- 남은 전장은 **웹 런타임의 프로세스/바닥값** 하나다.

## 4. 콜드 스타트 — 왜 목표에 못 닿는가

### 4.1 3단 분해 (`bench/boot.mjs`, `bench/results/boot-breakdown.json`)

| 구간 | Tauri 3.0 | Electron 2.6.2 |
|---|---|---|
| 스폰 → 페이지 `timeOrigin` (웹 런타임 기동) | **202~240ms** | **210ms** |
| `timeOrigin` → domInteractive | 22~30ms | 92.6ms |
| 재로드 경로의 `#root` 마운트(순수 페이지 비용) | 56ms | 36ms |
| 마운트 전 IPC 왕복 | **0회** (R3 이전 1회) | (측정 불가 — contextBridge) |

**첫 줄이 전부다.** 목표 winMs ≤168ms인데 웹 런타임 기동만 202~240ms다. 웹 콘텐츠를
한 픽셀도 안 그려도 목표를 못 넘긴다. rootMs ≤211도 같은 이유로 불가능하다
(기동 202 + 순수 페이지 56 = 258이 이론 하한).

Chromium(Electron)도 같은 210ms를 쓴다 — **"Tauri라서 런타임이 빨리 뜬다"는 근거가 없다.**
Electron이 336ms인 건 기동 뒤 메인 프로세스의 Node 부팅(domInteractive 92.6ms 등)이
붙기 때문이지 Chromium 기동이 느려서가 아니다.

프로세스 수를 줄이면 기동이 빨라진다는 것도 실측했다: `--single-process`에서
스폰 → `timeOrigin`이 **172ms**로 떨어진다(−39ms). 그래도 168 목표엔 못 닿는다.

### 4.2 R2의 창 표시 규약은 발화하지 않았다 (닭-달걀)

R2는 `splash.js`가 rAF를 두 번 기다렸다가 셸에 `win:first-paint`를 보내면 셸이 창을
보여주는 구조라고 적어 뒀다. 실측하니 **그 경로는 한 번도 실행되지 않았다**:

> 창이 숨겨져 있는 동안 WebView2는 프레임을 만들지 않는다 → rAF가 오지 않는다 →
> `win:first-paint`가 안 온다 → 창이 안 뜬다 → 여전히 프레임이 없다.

그래서 창은 늘 **안전망**(`PageLoadEvent::Finished` = `load` 이벤트)으로 떴다. 그리고
`load`는 index.html의 **원격 웹폰트 CSS 두 개를 기다린다**: 실측 DCL 61~66ms vs
load 109~119ms — 창 표시가 CDN 왕복 50ms에 묶여 있었고 오프라인이면 더 늦었다.
R2가 기록한 240ms와 오늘 같은 코드로 잰 313ms의 차이가 정확히 이 자리다.

**수정**: 스플래시 오버레이가 DOM에 들어가고 **렌더 차단 스타일시트가 다 도착한 순간**
(=다음 프레임이 곧 스플래시인 시점) 셸에 알린다. 4ms 폴링·120ms 상한, `Finished`는
안전망으로 유지. 결과: winMs 313 → 218(당시 빌드 기준), 그리고 네트워크 의존이 사라졌다.

### 4.3 채택하지 않은 콜드 스타트 레버 (측정하고 되돌린 것)

`app/vite.config.ts`의 `paintSplashBeforeApp` 플러그인 — 앱 번들 실행을 한 프레임 뒤로
미뤄 스플래시가 먼저 그려지게 한다. 실측(5회 중앙값):

| | winMs | rootMs | 스플래시 픽셀 |
|---|---|---|---|
| 켬 | 231 | 378 | ≈300ms |
| **끔(기본)** | 243 | **335** | ≈400ms |

창이 막 뜬 직후 합성기가 첫 표면을 만드는 데 60~90ms가 걸리는데 그동안 메인 스레드가
논다. "브랜드 스플래시를 100ms 일찍 보여주고 앱은 43ms 늦게 쓴다"는 교환이라 목표 지표
쪽(rootMs)을 택했다. 코드는 남겨 뒀다 — `CCG_DEFER_APP_SCRIPTS=1`로 빌드하면 켜진다.

## 5. 레버 — 채택·기각 (전부 실측)

전체 표: `bench/results/webview-flags.json` (25 레버 × 2회 중앙값, 멀티 4패널 픽스처,
CDP off, 25초 정착). 창 비용이 걸린 레버는 무대가 달라야 해서 `bench/multi.mjs`로 따로 쟀다.

### 5.1 채택 (2개)

| 스위치 | 실측 기여 | 값 |
|---|---|---|
| `--process-per-site` | **창당 114.7MB / +2프로세스 → 14.8MB / +0프로세스** (단독 팔, wry 기본값 위에서) | 없음 |
| `--in-process-gpu` | 멀티 유휴 **Priv 337.4 → 251.6MB**, WS 491.2 → 475.7, 프로세스 7 → 6. 스크롤 60fps·드랍 0%, **하드웨어 GPU 유지**(WebGL renderer = NVIDIA D3D11) | 콜드 win +48ms · root +9ms(첫 픽셀은 −84ms). GPU 드라이버 크래시 격리 상실. 되돌리기: `CCG_GPU_PROCESS=1` |

`--process-per-site`는 **단일 창 스윕에서는 기여 0으로 보였다**(창이 하나뿐이면 공유할
게 없다). 무대가 틀렸던 것이고, 이게 3.0이 Electron을 확실히 이기는 유일한 자리다.

### 5.2 기각 — R2가 채택해 두었으나 실측 무효 (15개)

| 레버 | 실측 | 왜 무효 |
|---|---|---|
| `SpareRendererForSitePerProcess` off | ws **+28** · priv **+111** · procs 7 | 프로세스가 안 줄어든다 = WebView2가 무시 |

| GPU | 하드웨어 유지(NVIDIA D3D11) | |
| 콜드 스타트 | **win 211 / paint 277 / root 326** — 모든 팔 중 최고 | |

**측정상으로는 전 지표에서 이긴다.** 그런데도 기본값으로 삼지 않은 이유:

1. `--single-process`는 Chromium이 "디버깅 전용"으로 못박은 스위치이고 WebView2는
   명시적으로 미지원이다.
2. WebView2는 **Evergreen(자동 갱신)** 이다. 다음 Edge 업데이트가 이 경로를 깨면
   **이미 배포된 앱이 전부 죽는다.** 우리가 고칠 수 있는 시점이 아니다.
3. 샌드박스와 렌더러 크래시 격리가 함께 사라진다(HTML 미리보기가 사용자 프로젝트의
   HTML을 렌더한다 — 완전히 신뢰할 수 있는 입력이 아니다).

채택 여부는 이 트레이드를 아는 사람이 정할 일이라 수치만 남긴다.

## 6. 하네스에서 고친 것 (숫자를 믿으려면 필요했던 것)

### 6.1 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`가 코드 인자를 **덮어쓴다**

`node bench/flags.mjs precedence`: 코드 인자에 `--remote-debugging-port=9411`,
환경변수에 `=9412`를 동시에 주고 어느 포트가 응답하는지로 갈랐다 → **9412만 응답**.
즉 누군가 그 환경변수를 세팅하면 `webview_args.rs`의 레버가 전부 조용히 사라진다.
R1이 벤치에서 그 변수로 CDP 포트를 넣던 방식이 위험했던 게 확인됐다(지금은 `CCG_CDP_PORT`).

### 6.2 스윕의 대조군만 프로필이 차가웠다

`flags.mjs`의 `seedHome()`이 홈을 통째로 지우므로 **그 뒤 첫 레버만** WebView2 프로필을
새로 만든다. A0가 맨 앞이었던 탓에 그 뒤 모든 레버가 약 −14MB씩 싸게 나오는 가짜 밴드가
생겼다. 수정: 스윕은 대조군을 한 번 버리는 워밍업으로 돌리고, 단일 레버 재측정에는
`--keep`(따뜻한 홈)을 쓴다. 따뜻한 A0 = 451/311 (차가운 A0 = 479/313).

### 6.3 홈 시드가 고정돼 있지 않았다

`coldstart.mjs`·`idlemem.mjs`가 홈을 시드하지 않아 **직전에 돌린 `multi.mjs`가 남긴
멀티 그리드 4패널 홈**에서 재는 사고가 났다. 실제로 밟았다: Electron 단일 채팅 유휴가
704.8MB / 7프로세스로 찍혔다(같은 픽스처로 다시 시드하니 659.6 / 7프로세스).
수정: 두 하네스 모두 `pair.mjs`와 같은 시드(단일 채팅 픽스처)를 강제한다(`--keep-home`으로 해제).

> 그래도 박제된 `idlemem-electron-2.6.2.json`(428.1 / 341.4 / **5프로세스**)은 재현되지
> 않는다 — 오늘 어느 모드로 재도 **7프로세스 · 626~660MB**다(크리틱의 recheck 파일과 일치).
> 지시대로 그 파일은 갱신하지 않았고, 재측정치는 `idlemem-nocdp.json`에 따로 남겼다.
> **주 게이트인 `multi-electron-2.6.2.json`은 재현된다**(712.8 → 730.1)는 것도 확인했다
> (`bench/results/r3-multi-electron-recheck.json`, 박제 파일은 손대지 않음).

### 6.4 `winMs`가 빈 창을 셀 수 있었다

`measureColdStart`에 **`paintMs`(웹 콘텐츠 첫 페인트를 스폰 시각 기준으로 환산)** 를 추가해
항상 함께 남긴다. 두 앱의 창 표시 규약이 다르므로(2.6.2는 별도 스플래시 창, 3.0은 창 안
오버레이) 이 숫자가 없으면 winMs끼리의 비교가 성립하지 않는다.

### 6.5 기타

- `measureIdle(role:true)` — 유휴 측정도 역할별로 쪼개 남긴다.
- `bench/boot.mjs` — 콜드 스타트 3단 분해 + **마운트 전 IPC 왕복 계수**(재로드 경로에
  `__TAURI_INTERNALS__.invoke` 래퍼를 심어 채널·시각까지 기록).
- `bench/gpuprobe.mjs` — 재빌드 없이 CSS 오버라이드를 누적으로 얹으며 역할별 재측정.
- `bench/flags.mjs` — 레버 25종, 역할별 합계, `--keep`, 조합 팔(Y군), 창 껍데기 팔(F군).

## 7. 렌더러/셸에서 바꾼 것

전부 `docs/renderer-divergence.md`에 한 줄까지 기록했다. 요약:

1. **부팅 페이로드 선주입** — `win.rs::boot_payload_script()`가 `ui-prefs:get`·`profile:get`·
   `app:get-version`을 `window.__CCG_BOOT`에 넣고, 심의 `call()`이 **인자 없는 호출에 한해
   채널당 한 번만** 소비한다. 마운트 전 IPC 왕복 1 → 0.
   - 큰 블롭(chats/ma)은 **일부러 안 넣었다**: document-start에 수백 KB짜리 JS 리터럴을
     파싱하면 첫 페인트가 오히려 늦고, 그 둘은 마운트 이후 조회라 rootMs에 영향이 없다.
2. **창 표시 규약**(§4.2) — `splash.js`가 렌더 차단 CSS 준비 시점에 알린다.
3. **`app/vite.config.ts`에 플러그인 1개 추가**(기본 꺼짐, §4.3).
4. 렌더러(`app/src`)에서 바뀐 파일은 **`api/shim.ts` 하나**(3.0 전용 파일). 이식한
   60개 .ts/.tsx와 `styles.css`는 여전히 한 글자도 안 바뀌었다.

## 8. 아직 안 되는 것 / 다음 라운드 재료

1. **유휴 WS 475.7 vs 목표 356 — 최대 격차.** 원인은 레버가 아니라 **WebView2 프로세스
   바닥값**이다(§3: 앱 몫 8.4MB). 남은 선택지는 셋뿐이고 전부 값이 있다:
   (a) `--single-process` 채택(§5.4 — 미지원·Evergreen 리스크),
   (b) WebView2 **고정 버전 런타임**으로 Evergreen 리스크를 없앤 뒤 (a)를 채택
       (설치 크기 +120MB · M12 설치기와 함께 판단할 일),
   (c) WS 지표 자체를 재정의(프로세스 간 공유 페이지 중복 계수 제거) — **측정 규약을
       바꿔 통과하는 건 이번 라운드에서 하지 않았다.**
2. **+추가 창 2개 521.1 vs 목표 467.** 창당 비용은 이미 0.20배인데(22.7 vs 112MB)
   바닥값 때문에 총합이 안 내려간다. 1번과 같은 뿌리.
3. **콜드 스타트 두 목표 모두 구조적 미달**(§4.1). 웹 런타임 기동 202~240ms가 하한이다.
   목표를 유지하려면 런타임 기동을 줄이는 수밖에 없고, 실측된 유일한 수단이
   `--single-process`(172ms)다.
4. **FPS 드랍 0%를 전 회차에서 못 보여줬다**(6회 중 1회 0.8%). 레버와 무관한 팔에서도
   같은 흔들림이 나서 앰비언트로 보지만, 판정 기준이 "0%"라 그대로 남긴다.
   반복 횟수를 늘린 FPS 게이트가 필요하다.
5. **`--in-process-gpu`의 크래시 격리 상실**은 값이다. GPU 드라이버 리셋(TDR)이 잦은
   기계에서 웹뷰가 통째로 죽을 수 있다 — 실사용 관찰이 필요하고, `CCG_GPU_PROCESS=1`이
   탈출구다.
6. **2.6.2 단일 채팅 기준값이 틀려 있다**(§6.3). 목표 수치가 그 값에서 파생됐다면 다시
   유도해야 한다. 주 게이트(멀티)는 재현되므로 이번 판정에는 영향이 없다.
7. 토스트·트레이 창이 3.0엔 아직 없다 — 지금 비교는 그만큼 3.0에 유리하다.
   2.6.2는 그 둘이 렌더러 2개(≈220MB)이고, 3.0에서 같은 걸 붙이면 `--process-per-site`
   덕에 **창당 22.7MB × 2 ≈ 45MB**로 붙는다(실측된 창 비용 기준 추정).
